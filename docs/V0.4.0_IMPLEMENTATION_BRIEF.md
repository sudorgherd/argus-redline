# ARGUS REDLINE v0.4.0 Implementation Brief

**Status:** Proposed implementation plan; no v0.4.0 behavior is implemented by this document.

**Planned release:** `v0.4.0` — Persistent Settings and Configuration Recovery

## 1. Release objective

ARGUS REDLINE v0.4.0 adds a small, versioned, recoverable local-settings system to the existing single-Hub/single-Node firmware. Approved display and diagnostic preferences will survive reboot and power loss without becoming a second authority for identity, radio, protocol, transaction, duplicate, input, or runtime decisions.

The release must prove that deterministic settings and recovery are testable without hardware, that an ESP32 NVS adapter does not leak Arduino into pure policy, and that storage/UI activity does not regress Protocol v0.1 radio traffic. Wire Protocol remains `1`; no setting is transmitted over LoRa.

- `DeviceConfig` owns compile-time local and peer identities.
- `Protocol` owns Wire Protocol 1 bytes, types, validation, and codec behavior.
- `HubTransactionState` owns Hub sequence, retry, ACK wait, deadline, and completion.
- `NodeDuplicateTracker` owns the volatile single-entry duplicate key and remembered ACK status.
- `RuntimeState::State` owns volatile presentation observations: readiness, health, phase, metrics, inbound packet, activity, counters, and error.
- `DeviceInput::Button` owns normalized debounce and semantic input.

- The two `main.cpp` files own Arduino, GPIO, `millis()`, display initialization, RadioLib, Serial, and orchestration.

### 2.2 Persistence gap

There is no Preferences, NVS, EEPROM, filesystem, settings schema, migration, or factory-reset code. Runtime diagnostics and UI state are volatile. Current defaults are a 30-second OLED timeout, Home initial screen, ThingPulse 128x64 contrast `0xCF` (207), enabled radio-transmit LED indication, visible diagnostics, and no separate button feedback.

## 3. Scope and non-goals

v0.4.0 includes only:

- Configuration Schema 1 for six local preferences;
- deterministic defaults, validation, and repair;
- bounded binary serialization and integrity checking;
- a narrow ESP32 Preferences/NVS adapter;
- recoverable two-slot commits and factory reset;
- missing, partial, corrupt, invalid, and unsupported-schema handling;
- a future migration contract;
- write coalescing and flash-wear rules;
- a local settings editor;
- applying settings to existing UI, OLED, diagnostics visibility, and LED presentation;
- native tests, builds, and physical persistence/radio regression.

Explicit non-goals:

- persistent device/peer/network/role identity or runtime provisioning;
- credentials, encryption, authentication, replay protection, or key storage;
- multi-Node coordination or registries;
- Host Protocol, ARGUS integration, or a computer settings service;
- new commands, opcodes, statuses, packet types, fields, or application transport;
- Node-originated events, capabilities, sensors, actuators, or arbitrary GPIO;
- configurable radio, retry, timeout, sequence, ACK, or duplicate policy;
- routing, repeaters, mesh, or store-and-forward;
- persistence of counters, packet history, metrics, errors, peer state, sequence, retries, or duplicate state;
- encrypted NVS, OTA migration, eFuse changes, or a custom partition table;
- a generic database, event bus, scheduler, dependency-injection layer, or settings framework.

## 4. Configuration Schema 1

### 4.1 In-memory value

Add a hardware-independent component:

```text
lib/device_settings/src/device_settings.h
test/test_device_settings/test_main.cpp
```

The value type should be equivalent to:

```cpp
namespace DeviceSettings {
constexpr uint16_t SCHEMA_VERSION = 1;
struct Settings {
    uint16_t displayTimeoutSeconds;
    uint8_t displayContrast;
    bool ledEnabled;
    bool diagnosticsEnabled;
    DefaultScreen defaultScreen;
    bool buttonFeedbackEnabled;
};
}
```

`DefaultScreen` is a settings-owned six-value enum corresponding exactly to
Home, Radio, Device, Last Packet, Diagnostics, and About. `DeviceUi` maps it at
the integration boundary; `device_settings` must not depend on `device_ui`.

The model uses fixed-size values, deterministic defaults, equality, and no allocation or strings. All fields are shared by Hub and Node; Schema 1 has no role-specific persisted field. Role and IDs never enter the record.

### 4.2 Types, ranges, defaults, and semantics

| Setting | Type/range | Default | Meaning |
|---|---|---:|---|
| Display timeout | `uint16_t`; `0` or `5..600` seconds | 30 | `0` means always awake; otherwise checked conversion to milliseconds |
| Display contrast | `uint8_t`; `16..255` | 207 | Applied after OLED initialization; 207 preserves the current driver initialization value |
| LED enabled | Boolean | true | Master gate for existing radio LED and optional button feedback |
| Diagnostics enabled | Boolean | true | Controls counter visibility only; the screen remains in order and collection continues |
| Default screen | Settings-owned `DefaultScreen`; six normal values | Home | Mapped to the initial UI screen after load |
| Button feedback | Boolean | false | Semantic permission for local acknowledgment of accepted input; the physical presentation is selected during the UI implementation step |

Timeout values 1–4 and 601+ are invalid, not rounded. Contrast below 16 is invalid rather than a normal “blank display” setting. Diagnostics disabled keeps the screen in the normal order and shows `DISABLED`, so navigation remains deterministic and the setting remains locally reversible; counters continue collecting. Button feedback remains semantic in Schema 1. Its eventual physical presentation must be nonblocking and must not delay radio work, but no LED pulse, duration, or other output is fixed by this schema.

### 4.3 Exact 24-byte record

Do not persist a compiler-native struct. Encode fixed little-endian bytes:

| Offset | Size | Field |
|---:|---:|---|
| 0 | 4 | Magic bytes `RLCF` (`0x52 0x4C 0x43 0x46`) |
| 4 | 2 | Schema version `1` |
| 6 | 2 | Record length `24` |
| 8 | 4 | Commit generation |
| 12 | 2 | Timeout seconds |
| 14 | 1 | Contrast |
| 15 | 1 | Default-screen raw value |
| 16 | 1 | Flags: bit 0 LED, bit 1 diagnostics, bit 2 button feedback |
| 17 | 3 | Reserved zero bytes |
| 20 | 4 | CRC-32/ISO-HDLC over bytes 0–19 |

CRC uses reflected polynomial `0xEDB88320`, initial `0xFFFFFFFF`, final XOR `0xFFFFFFFF`. It detects corruption; it is not authentication. Unknown flags, nonzero reserved bytes, wrong magic/length/CRC, invalid screen, or invalid ranges are never silently applied.

### 5.1 Storage-layout comparison and selection

| Layout | Strengths | Weaknesses |
|---|---|---|
| Individual NVS keys | Simple inspection and isolated field updates | Can expose mixed-generation settings after interruption, needs per-key schema/default/repair rules, and multiplies writes and partial-state combinations |
| Single versioned blob | One bounded codec, one CRC, and atomic logical settings snapshot | Overwriting the only copy removes application-level rollback when a write, read-back, or semantic validation fails |
| Dual-slot versioned blob | Keeps complete settings together and retains the last verified record while a new generation is written and checked | Uses two blobs, generation selection, CRC validation, and more recovery tests |

The dual-slot versioned blob is selected for Schema 1 because it is the smallest design that simultaneously prevents mixed-generation fields, provides a verified rollback record, and supports interruption recovery without relying on six independent updates. This comparison is the basis for fixing namespace `redline`, slots `cfg_a`/`cfg_b`, and the 24-byte generation/CRC record for v0.4.0.

A narrow `RecordStore` interface may expose only read/write/remove slot and reset-marker operations. It must not become a general key-value abstraction.

## 6. Load, validation, and recovery

Return a typed status including:

```text
LOADED
DEFAULTED_MISSING
LOADED_FALLBACK_SLOT
REPAIRED_SCHEMA_1
DEFAULTED_CORRUPT
UNSUPPORTED_SCHEMA
STORAGE_UNAVAILABLE
RESET_COMPLETED
```

Load order:

1. Complete a pending reset first.
2. Read both slots without modifying them.
3. Validate framing, CRC, schema, and fields independently.
4. Select the newest valid supported generation using wrap-safe serial comparison (`int32_t(a - b) > 0`); fewer than `INT32_MAX` commits may separate comparable records.
5. Equal generations with different payloads are ambiguous corruption and default rather than choosing by slot name.
6. Never combine fields from two records.

Recovery matrix:

| Condition | Runtime result | NVS action |
|---|---|---|
| No slots | Defaults | No automatic write |
| One valid Schema 1 slot | Load it | No mirror write |
| Two valid slots | Newest generation | No write |
| Newer partial/bad CRC; older valid | Older slot | Report fallback; no immediate write |
| Valid CRC/schema but invalid field | Repair only invalid fields in RAM immediately | Schedule at most one verified persistent repair that boot, only at a proven safe point or explicit Save |
| Both supported slots corrupt | Apply defaults in RAM immediately | Schedule at most one verified persistent repair that boot, only at a proven safe point or explicit Save |
| Valid unknown schema | Volatile defaults | Preserve data; require supported firmware or explicit reset |
| NVS unavailable | Volatile defaults | Report, do not spin or block radio |
| Reset marker | Complete reset idempotently | Remove marker only after verified defaults |

Runtime repair and persistent repair are separate operations. Validation must produce safe canonical RAM settings before radio or UI behavior consumes them. A persistent repair is optional deferred maintenance: it occurs only at a verified role-safe point, or as part of an explicit Save, and never merely to make RAM usable. If hardware characterization shows that NVS operations interfere with Node receive/ACK behavior, Node continues with repaired RAM values and defers persistence until explicit Save. First boot is not an error and uses volatile defaults without writing. Unsupported schema is not corruption and must not be overwritten automatically. Storage failure does not make radio unready. Unsupported/unavailable configuration may set overall presentation health `DEGRADED` while radio continues with defaults; expose a separate bounded configuration status rather than making runtime state a persistence authority.

## 7. Save and flash-endurance policy

Only explicit Save commits user changes:

1. Validate/canonicalize the complete draft.
2. If equal to the last loaded/saved settings, return `UNCHANGED` and write nothing.
3. Increment generation once and encode the complete record.
4. Write the inactive slot.
5. Read it back and verify length, CRC, schema, generation, and values.
6. Only then select it in memory; retain the previous slot as rollback data.

A failed commit leaves the previous slot authoritative and the draft unsaved. Rules:

- no writes merely because `loop()` ran or time passed;
- no writes from navigation, wake/sleep, metrics, counters, packets, errors, peer state, retry, sequence, or duplicate state;
- no first-boot write when defaults suffice;
- edits remain RAM-only until Save and coalesce into one blob;
- persistent automatic repair is attempted at most once per boot and only at a verified role-safe point; RAM repair is immediate and write-free;
- failed writes are not retried in a tight loop;
- no NVS operation occurs in ISR, transaction engine, input classifier, renderer, or packet callback;
- Hub writes only while IDLE and not awaiting ACK;
- Node writes only while LISTENING after pending radio completion is serviced;
- no standby, receive restart, or artificial delay is added solely for storage.

NVS is power-loss resistant, but flash operations may disable cache temporarily. Physical tests—not documentation—must prove an explicit save does not create systematic receive/ACK gaps.

## 8. Migration behavior

Schema 1 is the first REDLINE persistent schema; there is no legitimate Schema 0 payload. Establish a pure dispatcher:

```text
decode framing/CRC → identify schema → explicitly migrate supported older schema
→ validate current settings → commit current schema once
```

For v0.4.0, Schema 1 loads directly; missing/unversioned storage defaults and is not called migration; unknown older/newer schemas are preserved as unsupported. Never reinterpret unknown bytes. Future migrations require an explicit source decoder and tests and must become idempotent after one current-schema commit.

## 9. Factory reset and GPIO0

Factory reset affects only the `redline` ordinary-settings namespace. It never globally clears NVS or touches identity, calibration, credentials, bootloader data, or future provisioning.

Unlike ordinary first boot, which uses volatile defaults without writing, an explicitly confirmed factory reset intentionally creates one canonical default Schema 1 record. This makes completion durable and distinguishable from an interrupted reset.

Reset protocol; every operation returns a checked result and failure leaves a state that can be retried safely:

1. Write `rst_pend=true`, read it back, and abort before removal if either operation fails.
2. Remove `cfg_a` and verify it is absent; on failure retain the marker and stop for recovery.
3. Remove `cfg_b` and verify it is absent; on failure retain the marker and stop for recovery.
4. Write canonical defaults to `cfg_a`, generation 1, then read back and validate the complete Schema 1 record; on failure retain the marker and retry recovery later.
5. Remove `rst_pend` and verify it is absent; if removal or verification fails, the next recovery pass revalidates/recreates the canonical record before trying marker removal again.
6. Apply defaults and return Home.

Power failure at any point leaves the marker so the next boot completes reset. Marker-write failure aborts before deleting settings.

GPIO0 is an ESP32-S3 strap pin, and v0.3.0 hardware tests showed a held reset enters bootloader behavior before firmware can run. Therefore factory reset must never use “hold GPIO0 during reset” or infer reset from the startup-held sample.

Approved runtime entry behavior:

- Long press on the normal About screen enters the modal settings editor.
- Long press on every other normal screen retains the v0.3.0 return-Home behavior.
- Do not add `VERY_LONG_PRESS` to `DeviceInput` for v0.4.0 unless later implementation evidence demonstrates that the approved interaction cannot be implemented safely with the existing semantic events.
- Short press selects the next field/action; long press cycles/activates it.
- Draft edits are RAM-only.
- `SAVE` commits and exits; `CANCEL` discards without a write.
- `FACTORY RESET` arms visibly; a second long within 10 seconds confirms. Short press, modal exit, or timeout cancels without writing.
- Display inactivity discards the draft and follows normal OLED-off behavior.

Editor presets:

```text
Timeout: 0, 15, 30, 60, 120, 300, 600 seconds
Contrast: 32, 64, 128, 207, 255
LED / Diagnostics / Button feedback: OFF, ON
Default screen: HOME, RADIO, DEVICE, LAST PACKET, DIAGNOSTICS, ABOUT
Actions: SAVE, CANCEL, FACTORY RESET
```

Arbitrary valid stored values remain valid; editing advances deterministically to the next preset.

## 10. Runtime and UI integration boundaries

- `DeviceSettings::Settings` owns current ordinary preferences.
- A settings manager owns generation, slot, draft/dirty state, results, and repair scheduling.
- The ESP32 adapter owns only Preferences calls and exact keys.
- Runtime state may mirror configuration status but does not validate/save settings.
- `DeviceUi` owns modal editor policy plus existing navigation/timeout/wake scheduling.
- `HeltecDisplay` applies contrast and renders bounded settings/confirmation snapshots; it never reads NVS.
- Firmware owns safe service timing and physical LED arbitration.

Boot order for both roles:

1. Initialize Serial and GPIO as today.
2. Initialize Vext, OLED reset, and display as today.
3. Load settings.
4. Apply contrast and configure UI timeout/default screen.
5. Initialize radio and establish existing ready state.
6. Render with configuration status visible.

Storage failure must not prevent radio initialization. Timeout reconfiguration resets inactivity from apply time. Default screen applies at boot/reset, not unexpectedly on Save. Contrast may preview immediately, with Cancel restoring the loaded value. Diagnostics disable changes presentation only: Diagnostics stays in the circular screen order, renders `DISABLED`, and counters continue collecting. Button feedback is a semantic setting; its physical presentation is chosen and verified during the UI step and must be nonblocking.

No setting is consulted by Protocol, ACK evaluation, Hub transaction state, Node command evaluation, duplicate tracking, addressing, or RadioLib configuration.

## 17. Risks and unresolved decisions

### Fixed decisions

- Exactly six shared ordinary settings; no identity/security data.
- After comparison with individual keys and a single blob, use namespace `redline`, dual slots `cfg_a`/`cfg_b`, and marker `rst_pend`.
- Explicit 24-byte dual-slot generation/CRC record with a retained verified rollback record.
- No first-boot write, unknown-schema overwrite, periodic persistence, or boot-held reset.
- Factory reset intentionally writes and verifies one canonical default Schema 1 record.
- Runtime repair is immediate and write-free; persistent repair waits for a verified safe point or explicit Save.
- About long press enters settings; long press elsewhere retains return-Home behavior; no `VERY_LONG_PRESS` is planned.
- Disabled Diagnostics remains in the navigation order, displays `DISABLED`, and continues counter collection.
- Runtime diagnostics remain volatile.

### Human approval before relevant steps

1. During the UI step, approve the exact physical presentation for semantic button feedback and verify any selected V4.3 output polarity/visibility; do not encode a pulse duration into the stored setting.
2. Use the hardware-storage-characterization result to approve each role's safe persistent-repair point. If Node flash writes create gaps, defer persistent repair until explicit Save rather than altering radio order.
3. Confirm unsupported-schema UX: degraded/defaults plus explicit reset, never downgrade overwrite.
4. Choose a narrow NVS corruption fixture/preloaded image; do not add production Serial/radio injection commands.

Technical risks include flash cache interruption, generation half-range assumptions, unreadable contrast preview, reset-marker ordering, Preferences failure loops, accidental writes from input chatter, and GPIO0 bootloader selection before firmware runs.

## 19. Definition of done

v0.4.0 is done when both physical roles can load, display, edit, save, reboot with, recover, and factory-reset the six ordinary settings without continuous flash writes or regression of the v0.3.0 radio/UI system.

It proves Configuration Schema 1, deterministic recovery, bounded local editing, storage-independent native policy, and physical reset/power-loss/radio coexistence on V4.3. It does not prove persistent identity, provisioning, credentials/security, multiple Nodes, application transport, Host Protocol, capabilities/events, routing/repeaters/mesh/store-and-forward, ARGUS integration, or production/life-safety readiness.
