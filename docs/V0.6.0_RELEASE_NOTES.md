# ARGUS REDLINE v0.6.0 Release Notes

**Structured Operations, Responses, and Host Protocol**

ARGUS REDLINE v0.6.0 adds the first bounded machine-readable Host Protocol, structured REDLINE operations and responses, and a complete computer-to-Hub-to-Node-to-computer transaction path while preserving the direct single-Hub/single-Node architecture and Wire Protocol 1 compatibility.

## Highlights

- Added developmental Host Protocol `0.1` over bounded COBS-framed USB CDC with CRC-16/CCITT-FALSE integrity checking and deterministic malformed-frame recovery.
- Added HELLO negotiation that reports firmware, Host Protocol, Wire Protocol, Configuration Schema, hardware profile, role, device ID, supported categories/features, and bounded operation capacity independently.
- Added structured operations: `PING`, `GET_DEVICE_INFO`, `GET_STATUS`, `GET_CAPABILITIES`, `DESCRIBE_CAPABILITY`, `READ_CAPABILITY`, `SET_INDICATOR`, `RUN_PROCEDURE`, and `GET_DIAGNOSTICS`.
- Added Wire Protocol 1 `RESPONSE=0x04` as an additive packet type while preserving the existing six-byte header, 32-byte maximum packet, and previously assigned values.
- Separated ACK admission from operation completion: ACK admits or rejects the transaction; RESPONSE carries the terminal structured operation result.
- Added a bounded Hub radio bridge mapping one accepted Host request to one structured radio transaction and one correlated Host response.
- Added one active Host operation plus one fixed retained completed result with exact retry replay, `BUSY`, `MISMATCH`, replacement, disconnect/reconnect continuity, and no duplicate physical execution.
- Preserved the v0.5 capability registry, typed values/results, authorization and interlock gates, role-safe hardware dispatch, and v0.5.1 duplicate-cache admission ordering.
- Preserved autonomous legacy `TEST=0x64` radio behavior alongside Host Protocol operation.
- Added separate bounded Host Protocol diagnostics and a deterministic Python Host reference/test utility.
- Promoted the qualified Arduino-ESP32 3.3.9 / ESP-IDF 5.5.4 framework generation into the production `tx` and `rx` environments.

## Framework migration

Physical Step 15 qualification on the earlier Arduino-ESP32 2.0.17 generation exposed intermittent Host-response delivery loss below REDLINE HostTransport.

Qualification-only tracing proved that affected requests could complete the LoRa COMMAND/ACK/RESPONSE path, generate and submit the correct Host response, report available USB write capacity, and return the full requested byte count from `Serial.write()` while the Windows Host received no correlated frame.

A narrow HWCDC backport was tested and rejected because it did not eliminate the failure. The project then qualified the complete Arduino-ESP32 3.3.9 / ESP-IDF 5.5.4 generation. The migrated candidate passed the bounded M3-M6 framework/USB qualification envelope and the complete restarted Step 15.

This establishes that the full framework migration eliminated the previously reproducible Host-delivery failure behavior within the completed qualification envelope. It does not claim that one unique old-framework defect was proven to be the sole cause of every earlier timeout.

## Compatibility

- Firmware release: `v0.6.0`.
- Host Protocol: developmental `0.1`.
- Wire Protocol: `1`.
- Configuration Schema: `1`.
- Hardware profile: `HELTEC_V4`.
- Wire packet maximum remains 32 bytes.
- Existing Wire Protocol 1 TEST/ACK behavior and numeric assignments remain preserved.
- `RESPONSE` is an additive Wire Protocol 1 packet type.
- Host request IDs remain independent from Wire sequence ownership.
- Configuration persistence format remains Schema 1.
- The v0.5.1 canonical duplicate identity remains source + sequence + opcode + payload length + meaningful payload bytes, and complete structural admission still precedes duplicate-cache lookup or mutation.

## Security disposition

Wire Protocol 1 remains unauthenticated and unencrypted.

Production unauthenticated RF authority is therefore deliberately restricted. General remote `SET_INDICATOR` and `RUN_PROCEDURE` authority is not enabled merely because those operations exist. F-02 peer authentication, F-03 authentication-first discard/response governance, and F-04 authenticated persistent freshness/replay protection remain deferred requirements for the authenticated-transport milestone.

Host Protocol 0.1 also does not provide cryptographic user identity merely because a computer is physically connected by USB.

## Known limitations

- One Hub and one Node remain the physically qualified topology.
- Node-originated EVENT delivery is not implemented.
- Persistent device identity and controlled provisioning are not implemented.
- Authenticated/encrypted RF transport and persistent replay protection are not implemented.
- Stable multi-client host-service/API behavior remains a later milestone.
- General opaque application transport is not implemented.
- Remote production side-effect authority remains restricted.
- Production analog capability remains fail-closed as `HARDWARE_UNAVAILABLE`.
- Sleep/power lifecycle behavior is not qualified in this milestone.
- RF jamming protection is not provided.
- No independent external security audit is claimed.
- ARGUS REDLINE remains experimental and is not suitable for life-safety reliance.
