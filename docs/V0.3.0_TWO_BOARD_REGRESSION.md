# ARGUS REDLINE v0.3.0 Two-Board Regression

**Result:** PASS WITH LIMITED SUBTEST

All core v0.3.0 physical release gates passed. Controlled physical duplicate
reproduction was not completed; mandatory native coverage and source audit
remain the evidence for duplicate behavior.

| Role | Board | Test port | USB identifier | Device ID |
|---|---|---|---|---:|

## Software identity and metadata bridge

The physical regression used the behavior-complete build before Step 13:

- Firmware metadata: `v0.2.0`
- Wire Protocol: `1`
- Hardware profile: `HELTEC_V4`

Step 13 changes only the authoritative firmware identifier to `v0.3.0`, its
native-test expectation, and documentation. It does not change runtime,
transport, UI, radio, packet, or hardware behavior. Final software validation
covers the metadata-only release candidate. The literal `v0.3.0` startup string
was not claimed as physically observed during this regression.

## Physical results

- Both uploads passed and both boards booted normally when GPIO0 was not held.
- Shared RG Home screens rendered correctly as `TX | READY` and `RX | READY`.
- No clipping, corruption, flicker, frozen display, or reset loop was observed.
- Short presses navigated both roles without skipped or duplicate movement.
- Long press returned directly Home on both roles.
- Both OLEDs turned off after approximately 30 seconds of inactivity.
- Wake preserved the selected screen and did not navigate; the wake gesture's
  release/short tail was suppressed, and the next distinct short press worked.
- Radio traffic continued while both displays were off and did not wake them.
- Hub commands, Node ACKs, sequence advancement, and metrics continued without
  unexpected retries, timeout, reset, or alternating packet loss.
- Node interruption produced the expected bounded retry failure, and restoring
  the Node produced automatic recovery without resetting the Hub.
- Approximately ten minutes of concurrent UI and radio operation completed
  without observed reset, hang, receive gap, frozen OLED, lost button response,
  recurring unexpected retry, alternating loss, or sequence anomaly.

## Baseline serial evidence

The simultaneous capture contained 14 consecutive successful transactions,
sequences 9–22.

- Hub COMMAND: type 1, source 1, destination 16, opcode 100, payload length 0.
- Node ACK: type 2, source 16, destination 1, matching sequence, opcode 100,
  payload length 1.
- Hub reported `ACK MATCHED` and Node reported `COMMAND OK`.
- Hub RSSI ranged from -37 to -38 dBm; SNR ranged from 10.75 to 12.75 dB.
- Node RSSI ranged from -37 to -38 dBm; SNR ranged from 10.75 to 11.75 dB.

Early startup serial metadata was not retained because monitoring began after
the upload-triggered reboot. Firmware metadata, Wire Protocol, and hardware
profile were verified through source, native tests, and builds.

## Retry and recovery evidence

Sequences 53, 54, and 55 each exhibited:

1. Initial command transmission.
2. ACK timeout.
3. Retry 1/2 using the same sequence.
4. ACK timeout.
5. Retry 2/2 using the same sequence.
6. ACK timeout.
7. Terminal `COMMAND FAILED`.

No third retransmission or infinite retry occurred. Sequence advanced after
each terminal failure. After restoring the Node, sequence 56 received a
matching ACK, and sequences 57 and 58 also succeeded. No Hub reset was needed,
and peer/health recovery was consistent with the approved transaction-result
presentation model.

## GPIO0 boot-strap behavior

Holding GPIO0 during reset prevented normal application startup on both V4.3
boards. OLED and normal LED activity stopped until GPIO0 was released and the
board was reset normally. This is consistent with ESP32-S3 ROM bootloader strap
behavior and is not classified as an ARGUS REDLINE firmware defect. Firmware
startup-held suppression cannot execute when boot-strapping prevents the
application from starting.

## Limited subtests

- Controlled physical duplicate reproduction: **NOT COMPLETED**. No synthetic
  firmware behavior or packet-injection tooling was introduced. Native tests

- Physical malformed/unsupported packet injection: **NOT PERFORMED**. No new
  packet-injection tooling was created; native tests and source audit remain the
  evidence.

These limitations do not block v0.3.0.

## Final gate

All core physical release gates passed. Step 12 classification is **PASS WITH
