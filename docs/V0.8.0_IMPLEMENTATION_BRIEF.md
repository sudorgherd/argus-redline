# ARGUS REDLINE v0.8.0 Implementation and Qualification Brief

**Documentation/design status:** COMPLETE — implementation contract ready for review

**Implementation status:** NOT STARTED

**Target:** `v0.8.0` — Persistent Identity and Controlled Provisioning

**Entry baseline:** released firmware `v0.7.0`, Wire Protocol `1`,
Configuration Schema `1`, Host Protocol `0.2` with minor-1 compatibility,
hardware profile `HELTEC_V4`

**Roadmap authority:** `ARGUS_REDLINE_VERSIONED_DEVELOPMENT_ROADMAP.md`

**Supporting authorities:** `PROJECT_OVERVIEW.md`,
`V0.7.0_EVENT_RELIABILITY_DESIGN.md`, `HOST_PROTOCOL_0.2.md`,
`HOST_PROTOCOL_0.3.md`, and `ARGUS_REDLINE_SECURITY_REVIEW_2026-08-14.md`

## 1. Status and purpose

This brief turns the v0.8.0 roadmap milestone into an implementation,
validation, bench-integration, physical-qualification, and release contract.
It does not implement v0.8.0, change current firmware metadata, or authorize a
release.

v0.8.0 replaces the ordinary production dependency on compile-time Hub/Node
identity with one common HELTEC_V4 image. An operator deliberately provisions
that image over a physically attached USB connection while a local physical
gesture has opened a bounded provisioning window. The resulting role and
addressing context is transactionally persisted and is immutable during
ordinary runtime.

The milestone creates stable local identity state for the next authenticated-
transport milestone. It does not make that identity cryptographically
authentic. It also does not expand the qualified topology beyond one Hub and
one Node.

Each implementation stage below is a small reviewable batch. A failure stops
advancement and is corrected at its owning codec, store, lifecycle, Host,
runtime, or integration layer. Historical qualification evidence remains
chronological and is never rewritten into a pass.

## 2. Authoritative roadmap boundary

The required development order remains:

```text
persistent identity and controlled provisioning
-> authenticated transport and replay protection
-> multiple direct Nodes
```

v0.8.0 MUST:

- remove operational role, local device ID, and peer device ID from ordinary
  production build flags;
- define independently versioned Identity Schema `1`;
- provide explicit unprovisioned, provisioning, provisioned, invalid/degraded,
  and reset-pending behavior;
- use controlled local USB provisioning;
- persist the device ID, role, label, network ID, peer/authorized-Hub ID,
  hardware profile, capability profile, and provisioning generation;
- keep protected identity reset separate from ordinary settings reset;
- define transactional recovery, reprovisioning, and full factory reset; and
- freeze the boundary that later credentials and authenticated transport will
  consume.

v0.8.0 MUST NOT pull forward authenticated/encrypted RF, replay protection,
multiple Nodes, routing, repeaters, relays, or mesh behavior.

## 3. Current v0.7.0 baseline

The released source is authoritative. Its relevant properties are:

| Dimension | v0.7.0 behavior |
|---|---|
| Production roles | separate `tx`/`src-tx` Hub and `rx`/`src-rx` Node images |
| Operational addressing | `ARGUS_LOCAL_DEVICE_ID` and `ARGUS_PEER_DEVICE_ID` compile flags through `include/device_config.h` |
| Runtime identity | immutable `RuntimeState::State` snapshot constructed from the selected role and compile-time IDs |
| Ordinary settings | Configuration Schema 1, dual-slot CRC-protected records in NVS namespace `redline` |
| Event persistence | separate Node custody and Hub ledger records in NVS namespace `red_evt` |
| Event identity | `Source_Device_ID + Event_Epoch + Event_ID`; persistent and stable across retry/reboot |
| Host | developmental Protocol 0.2, retaining exact minor-1 behavior |
| Wire | Protocol 1; `COMMAND`, `ACK`, `ERROR`, `RESPONSE`, and `EVENT` codec support |
| Qualified topology | one HELTEC_V4 Hub and one HELTEC_V4 Node |
| Security | RF is unauthenticated and unencrypted; F-02, F-03, and F-04 remain open |

Configuration Schema 1 is for ordinary user preferences. The existing
settings factory reset intentionally affects only that domain. Event storage
has independent record schemas and recovery rules. Neither is an appropriate
authority for protected device provisioning.

The v0.7.0 capability registry and hardware handler are already common
HELTEC_V4 code. Role-specific orchestration, radio behavior, Event ownership,
and Host advertisement remain split between the two production mains.

## 4. v0.8.0 objectives

1. Produce one byte-identical ordinary production `firmware.bin` that can be
   flashed to either qualified HELTEC_V4 board.
2. Boot a virgin or deliberately reset device into a radio-silent,
   visibly unprovisioned state.
3. Require local physical presence plus an attached USB Host operation before
   any protected identity mutation.
4. Persist one validated single-peer identity record transactionally.
5. Resolve role and addressing from that record exactly once at boot; do not
   support casual live role switching.
6. Prevent incomplete, unknown, corrupt, or context-inconsistent provisioning
   from enabling normal RF operation.
7. Prevent a new logical identity from inheriting Node custody, Hub ledger,
   Event epoch/ID metadata, or other transport state from a prior identity.
8. Preserve Configuration Schema 1 settings behavior and all v0.7 transport,
   Event, capability, UI-responsiveness, and Host compatibility contracts.
9. Expose bounded, non-secret provisioning status and failure diagnostics.
10. Leave a precise storage and interface boundary for v0.9 credentials without
    inventing or provisioning credentials in v0.8.0.

## 5. Explicit non-goals

v0.8.0 does not include:

- cryptographic device credentials, keys, certificates, authenticated
  identities, AEAD, confidentiality, key rotation, revocation, or secure
  enrollment;
- F-02, F-03, or F-04 remediation;
- an RF provisioning packet, opcode, mode, or discovery service;
- more than one configured peer, Hub registry, multi-Node scheduling,
  collision policy, routing, repeater, relay, or mesh behavior;
- dynamic role changes during normal radio operation;
- remote or unattended reprovisioning;
- a general NVS database, interactive shell, arbitrary key/value editor, or
  network-management service;
- changes to Event families, custody geometry, retry policy, admission,
  polling, consumption, or Wire packet geometry;
- changes to radio frequency, transmit power, raw GPIO assignments, or the
  qualified HELTEC_V4 hardware profile; or
- Secure Boot, flash encryption, encrypted NVS, eFuse mutation, or production
  credential protection.

## 6. Terminology

| Term | Meaning in v0.8.0 |
|---|---|
| Hardware identity | Read-only ESP32-S3 factory identity exposed by the USB serial/JTAG interface (the six-byte MAC/USB serial used in qualification). It identifies the attached board operationally but is not the REDLINE address or a secret. |
| REDLINE device ID | Nonzero, non-broadcast `uint8_t` Wire source/destination routing value. Valid range is `0x01..0xFE`; `0x00` and `0xFF` are reserved. |
| Role | Exactly `HUB` or `NODE`, selected by the protected record and fixed for one ordinary boot. |
| Peer ID | The sole directly configured peer. For a Node this is the authorized-Hub routing ID; for a Hub it is the one configured Node routing ID. “Authorized” is an allowlist term, not cryptographic authentication. |
| Network ID | Nonzero `uint32_t` administrative/domain identifier persisted and reported locally. Wire Protocol 1 does not carry or enforce it. It is future authenticated-transport binding material, not current RF isolation. |
| Human label | Optional 0..16-byte printable ASCII operator label; presentation metadata only, never addressing or authorization. |
| Hardware profile | `HELTEC_V4=1`, still fixed by the physical image target and verified against the record. |
| Capability profile | Provisioned selector for a registry compiled into this image. v0.8.0 supports only `HELTEC_V4_BASE=1`; unknown values fail closed. |
| Record generation | Dual-copy storage ordering counter, advanced for every protected-record mutation. |
| Provisioning generation | Nonzero logical generation advanced by each successful provisioning/reprovisioning transaction. It is diagnostic/future binding context, not a security nonce. |
| Provisioning window | Volatile, time-bounded local state opened by a physical UI confirmation. Only within it may USB mutation requests be accepted. |
| Common image | One ordinary HELTEC_V4 production binary containing both role runtimes and no operational role/local/peer build flags. |

Global duplicate-ID discovery is not claimed. In the v0.8 single-pair scope,
duplicate detection means that a record with equal local/peer IDs is rejected,
reserved IDs are rejected, the provisioning tool refuses inconsistent pair
assignments, and physical qualification verifies complementary Hub/Node
records. Detecting conflicts among multiple simultaneously reachable Nodes is
part of the later multi-Node milestone.

## 7. Threat and security boundary

Provisioning is local/attached but not cryptographically authenticated. Its
v0.8 trust assumption is:

```text
physical possession of the board
+ an explicit local confirmation gesture
+ a directly attached USB Host
+ exact hardware-identity targeting
= authority to provision during a short maintenance window
```

This prevents ordinary radio traffic and casual serial traffic outside the
window from changing identity. It does not protect against a malicious local
computer while the operator has deliberately opened that window, physical
attack, flash extraction/modification, or compromised firmware.

The mutating Host request MUST include the expected six-byte hardware identity
and MUST fail if it does not match the running board. This is a wrong-device
guard, not authentication. No RF input may enter the provisioning service, set
its state, extend its window, or mutate protected storage.

Security findings remain exactly open:

- **F-02:** public source/destination metadata remains forgeable and is not
  cryptographic peer identity;
- **F-03:** unauthenticated traffic can still induce protocol response work;
- **F-04:** the eight-bit transaction sequence remains unauthenticated and is
  not persistent replay freshness.

The future secure-storage domain SHOULD be a separate `red_sec` namespace and
schema bound to network ID, local ID, peer ID, role, and provisioning
generation. v0.8.0 MUST NOT create that namespace, reserve fake key bytes in
the identity record, accept credentials, or advertise secure transport. The
v0.9 design must independently define key type, lifecycle, protection,
rollback/freshness behavior, and Wire versioning.

## 8. Persistent identity model

The minimum authoritative runtime identity is:

```text
role
local_device_id
peer_device_id
network_id
hardware_profile
capability_profile
provisioning_generation
human_label (presentation only)
```

The physical hardware identity is observed directly and is not copied into the
durable record as the REDLINE identity. The record belongs to the NVS of the
physical board on which it is stored. Host status reports both so tooling can
correlate them.

### 8.1 Invariants

- Role is exactly Hub or Node.
- Local and peer IDs are in `0x01..0xFE` and differ.
- Network ID and provisioning generation are nonzero.
- Hardware profile equals the compiled HELTEC_V4 profile.
- Capability profile is present in the compiled bounded profile registry.
- Label length is at most 16; used bytes are printable ASCII; unused bytes are
  zero.
- Reserved fields and unknown flags are zero.
- A valid provisioned snapshot is immutable during ordinary runtime.
- No setting, capability operation, Wire packet, Event, or RF state transition
  mutates it.
- The Node accepts ordinary Wire traffic only from its configured peer and to
  its local ID; the Hub does the complementary check. These remain structural
  routing checks, not authentication.
- An invalid or pending identity never enables radio operation.
- Provisioning generations and record generations never silently wrap. An
  ambiguous/exhausted generation fails closed and requires deliberate full
  factory reset/reprovisioning.

## 9. Provisioning record and Identity Schema 1

Use a dedicated NVS namespace `red_id`, separate from `redline` settings and
`red_evt` Event state. Keys `id_a` and `id_b` hold dual copies of one exact
64-byte record. A narrow adapter exposes exact-size read/write/remove and
commit/read-back operations; it is not a general preferences facade.

All multi-byte values are unsigned little-endian. Never serialize a compiler
struct.

| Offset | Size | Field |
|---:|---:|---|
| 0 | 4 | magic `0x31494C52` (`RLI1` on storage) |
| 4 | 2 | Identity Schema `1` |
| 6 | 2 | record length `64` |
| 8 | 4 | record generation |
| 12 | 4 | provisioning generation |
| 16 | 1 | durable record state |
| 17 | 1 | transaction kind |
| 18 | 1 | role |
| 19 | 1 | local device ID |
| 20 | 1 | peer device ID |
| 21 | 1 | hardware profile |
| 22 | 1 | capability profile |
| 23 | 1 | label length |
| 24 | 4 | network ID |
| 28 | 16 | label bytes, unused tail zero |
| 44 | 16 | reserved zero |
| 60 | 4 | CRC-32/ISO-HDLC over bytes 0..59 |

Durable states are:

```text
UNPROVISIONED = 0x01
PENDING       = 0x02
PROVISIONED   = 0x03
```

Transaction kinds are `NONE=0`, `APPLY=1`, and `FULL_RESET=2`.
`PROVISIONED` and `UNPROVISIONED` require `NONE`. A `PENDING/APPLY` record
contains the complete validated target identity. A `PENDING/FULL_RESET` record
has canonical zero identity fields. Other combinations invalidate that copy.

A virgin device with both identity keys missing is unprovisioned. A committed
UNPROVISIONED record is the canonical completed-full-reset state. Unknown
schema, bad CRC, malformed length/type, nonzero reserved bytes, invalid field
combinations, equal-generation conflicting copies, or half-range generation
ambiguity is not treated as virgin: it yields `INVALID_PROVISIONING`, preserves
bytes, and keeps RF disabled.

Generation selection uses the existing wrap-safe half-range pattern. Every
write targets the inactive/older copy, commits, reads back, decodes, and
byte-compares before publication. A failed write/readback/verification never
changes the authoritative in-RAM identity. No periodic identity writes occur.

## 10. Provisioning lifecycle and state machine

Runtime states are:

```text
UNPROVISIONED
PROVISIONING_ALLOWED
PROVISIONING_COMMITTING
PROVISIONED_HUB
PROVISIONED_NODE
INVALID_PROVISIONING
RESET_COMMITTING
REBOOT_REQUIRED
```

`PROVISIONING_ALLOWED`, committing states, and `REBOOT_REQUIRED` are runtime
presentation/control states. The three record states above are the durable
recovery authority.

### 10.1 First boot

1. Initialize USB Host transport, input, display, and identity storage only.
2. Recover and validate Identity Schema 1.
3. If both slots are absent or canonical UNPROVISIONED is selected, present
   UNPROVISIONED and leave LoRa uninitialized/radio-silent.
4. If a valid PROVISIONED record is selected, resolve runtime role/addressing,
   recover only the matching role's transport state, then initialize radio and
   enter ordinary operation.
5. If PENDING is selected, enter recovery before radio initialization.
6. If storage is invalid/unsupported/unavailable, present
   INVALID_PROVISIONING, permit read-only Host status, and fail closed.

### 10.2 Apply/reprovision transaction

After physical entry and full request validation:

```text
wait for foreground radio/Host/storage safe point
-> stop new ordinary Host/RF work and restore/quiesce radio
-> write and verify PENDING/APPLY target record
-> erase and verify all Node and Hub Event-domain keys/metadata
-> write and verify PROVISIONED target record
-> publish SUCCESS/REBOOT_REQUIRED
-> remain radio-silent until reboot
```

The current identity remains authoritative until PENDING is verified. Once a
PENDING transaction is authoritative it cannot be cancelled; boot or foreground
recovery completes it idempotently. This ordering means Event state is never
cleared without a durable intention naming the replacement identity.

If final identity commit fails, the device preserves PENDING, reports storage
failure, remains radio-silent, and retries only through the bounded recovery
path on explicit reboot/service—not in a tight write loop. It never reports
provisioning success.

An APPLY request byte-identical to the current protected record, including
label, returns `UNCHANGED` and performs no write or Event erase. Every actual
reprovisioning change advances provisioning generation and deliberately clears
the complete Event domain before activation. Existing ordinary settings are
preserved.

### 10.3 Interrupted provisioning recovery

- Torn PENDING write: the prior valid PROVISIONED/UNPROVISIONED record remains
  authoritative; no Event erasure has begun.
- Valid PENDING/APPLY: radio remains off; clear/verify Event state and commit
  the exact carried target as PROVISIONED.
- Torn Event clearing: PENDING remains; repeat the idempotent complete-domain
  clear and verification.
- Torn final PROVISIONED write: select PENDING and retry the final commit.
- Unknown/corrupt PENDING with no unambiguous older authority: preserve data,
  enter INVALID_PROVISIONING, and require deliberate full reset through the
  physically gated recovery surface.

No partially written target becomes a runtime identity.

## 11. Controlled provisioning entry and exit

Provisioning requires both local physical and Host participation.

### 11.1 Physical entry

- Do not use GPIO0 held during reset; it is an ESP32-S3 boot strap.
- On UNPROVISIONED or INVALID_PROVISIONING presentation, an awake
  `VERY_LONG_PRESS` arms entry, and a second awake `VERY_LONG_PRESS` within the
  existing bounded confirmation interval opens the provisioning window.
- On a provisioned device, add a protected `DEVICE MANAGEMENT` action to the
  existing modal settings UI. It is not an ordinary setting and never writes
  Configuration Schema 1. Selecting `REPROVISION` or `FULL FACTORY RESET`
  requires the same two-step confirmation.
- Wake-only input remains ineligible. Ordinary short/long navigation and Event
  producer rules remain unchanged.
- Entry waits for a production-defined safe point: no active radio ownership,
  no incomplete Host response, and no settings/Event NVS mutation. It then
  blocks new RF transactions and opens a 120-second volatile window.

The UI shows the requested destructive scope and current Node custody / Hub
ACTIVE and CONSUMED counts before confirmation. It does not imply those records
are already deleted.

### 11.2 Host mutation gate

Within the window, one attached Host may submit a complete bounded APPLY or
FULL_RESET request. The request must name the observed hardware identity.
Malformed requests do not extend the window. Ordinary RF cannot open or use
the service. When the window expires without a durable PENDING commit, the
device cancels the volatile mode and resumes its prior provisioned runtime (or
returns to UNPROVISIONED/INVALID presentation).

The window closes on successful commit, explicit volatile cancellation,
timeout, disconnect before commit, or reboot. Disconnect after PENDING commit
does not cancel recovery.

## 12. Factory reset and reprovisioning

The UI and documentation distinguish three operations:

| Operation | Ordinary settings | Protected identity | Event domain | Result |
|---|---|---|---|---|
| Reset Settings | reset to canonical Configuration Schema 1 defaults | preserved | preserved | current v0.7 behavior |
| Reprovision | preserved | replaced | all Node/Hub records and metadata cleared | new identity active after reboot |
| Full Factory Reset | reset to canonical defaults | canonical UNPROVISIONED | all Node/Hub records and metadata cleared | provisioning required after reboot |

Full reset ordering is:

```text
write/verify PENDING/FULL_RESET
-> complete existing recoverable settings reset
-> clear/verify Event domain
-> write/verify canonical UNPROVISIONED identity record
-> report SUCCESS/REBOOT_REQUIRED
```

Every step is idempotent after reboot. If any step fails, PENDING remains,
radio stays disabled, and the error is observable. The implementation removes
only ARGUS-owned keys; it never erases the NVS partition globally.

Factory reset/reprovisioning intentionally destroys unresolved Node Events,
Hub ACTIVE custody, CONSUMED proofs, Event allocator metadata, and Hub ordinal
metadata. The UI and Host request require an explicit `ACK_EVENT_ERASURE` bit
when any Event-domain key is present. Without it the request is rejected and
nothing is changed. This is deliberate administrative data loss, not normal
Event reclamation.

Volatile runtime/diagnostic counters restart on reboot. No separate persistent
diagnostic history is added. The hardware identity, bootloader/eFuse state, and
firmware image are never erased by these operations.

## 13. Runtime role and address resolution

One immutable validated `ProvisioningSnapshot` is created during boot and
supplied to runtime construction. `RuntimeState`, Host snapshots, Wire packet
builders/validators, Event stores, radio arbitration, UI, and capability
dispatch consume this snapshot rather than `DeviceConfig::LOCAL_ID` or
`PEER_ID`.

Provisioned Hub behavior uses:

```text
role = HUB
Wire source = local_device_id
accepted Node source / destination target = peer_device_id
Hub Event ledger context = local_device_id + peer_device_id
Host radio bridge enabled
Host Event service enabled for minor 2/3
```

Provisioned Node behavior uses:

```text
role = NODE
Wire source = local_device_id
accepted Hub source / destination target = peer_device_id
Node Event Source_Device_ID and custody context = local_device_id
authorized-Hub routing check = peer_device_id
Host radio bridge and Hub Event service disabled
```

The network ID is reported but has no Wire 1 field and therefore cannot filter
or authenticate RF packets. Hardware/capability profiles select only compiled,
validated registries. Unsupported profiles prevent radio initialization.

Unprovisioned, PENDING, invalid, or storage-unavailable devices provide bounded
local Host provisioning/status service and UI only. They do not initialize
LoRa, schedule TEST, accept COMMAND/EVENT, transmit ACK/RESPONSE/admission ACK,
or produce Events.

## 14. Interaction with v0.7.0 Event identity and persistent state

Source_Device_ID is part of canonical Event identity. Event_Epoch and Event_ID
belong to the Node custody context under which they were allocated. Hub ledger
records and admission ordinals likewise belong to one configured pair.

Therefore:

- no Node Event, allocator reservation, Hub ACTIVE record, CONSUMED proof, or
  admission ordinal is migrated to a new provisioning generation;
- any successful first provisioning, actual reprovisioning, role change, local
  ID change, peer change, network change, hardware/capability-profile change,
  or label change uses the deliberate Event-domain clearing transaction;
- an unchanged APPLY is a no-op and preserves Event state;
- Event state is cleared before the replacement identity becomes
  authoritative;
- a PENDING record blocks Event recovery and transmission;
- after provisioning, the empty Node store adopts a new nonzero Event epoch
  through its existing entropy/durable allocator path; and
- the empty Hub ledger initializes a fresh admission-ordinal context.

This deliberately conservative rule avoids deciding whether a metadata-only
change is safe while durable custody exists. A future release may define a
narrow label-only update separate from provisioning; v0.8.0 does not.

Normal reboot with an unchanged PROVISIONED record retains Event custody,
ledger records, epochs, IDs, attempts, lifetime debit/checkpoints, admission
ordinals, and ACTIVE/CONSUMED semantics exactly as v0.7.0 specifies.

## 15. Host Protocol impact

Provisioning needs an additive Host surface. Host Protocol 0.1 is frozen and
0.2 is the released Event-capable contract, so v0.8.0 introduces developmental
Host Protocol **0.3** rather than changing either older minor.

### 15.1 Compatibility

- Provisioned devices accept minor-1 frames with exact 0.1 behavior.
- Provisioned devices accept minor-2 frames with exact 0.2 behavior.
- Minor-3 frames add provisioning vocabulary; each frame's own minor remains
  authoritative and HELLO creates no connection state.
- Minor-1/2 HELLO responses from a provisioned device remain byte-exact and
  advertise no provisioning category/feature bits.
- An unprovisioned/invalid/PENDING device supports the minor-3 provisioning
  surface only. A legacy HELLO has no truthful legacy role/device encoding and
  receives the existing `PROTOCOL_ERROR/UNSUPPORTED_MINOR`; it never receives
  fabricated Hub/Node identity.

`docs/HOST_PROTOCOL_0.3.md` is the normative authority for minor-3 framing,
HELLO advertisement, numeric registries, targeting, structures, physical-
presence semantics, lifecycle/result behavior, persistent retry rules, parser
bounds, and golden vectors. Its frozen top-level assignments are:

```text
OperationCategory::PROVISIONING       = 0x06
GET_PROVISIONING_STATUS               = 0x2C
APPLY_PROVISIONING                    = 0x2D
FULL_FACTORY_RESET                    = 0x2E
CANCEL_PROVISIONING_WINDOW            = 0x2F
FEATURE_PROVISIONING                  = feature bitmap bit 3 (0x0008)
ResultClass::PROVISIONING_RESULT      = 0x06
```

`FEATURE_PROVISIONING` is exactly feature bitmap bit 3 (`0x0008`). The local
provisioning target is the minor-3-only Host sentinel device `0x00`, target ID
`0x0000`; it is not a Wire address. The status STRUCTURE is schema 1 and exactly
72 bytes, APPLY is schema 1 and exactly 40 bytes, and FULL_FACTORY_RESET is
schema 1 and exactly 16 bytes. Implementations MUST use the validation order,
result values, authorization consumption rules, generation compare-and-swap
semantics, and legacy Event-erasure acknowledgement defined by that protocol
document rather than inferring them from this summary.

No new message type, framing, CRC, request-ID rule, payload maximum, outstanding
operation count, or unsolicited frame is needed.

### 15.2 Operation semantics

`GET_PROVISIONING_STATUS` is local, read-only, repeatable, and available in
every lifecycle state. Its bounded STRUCTURE reports runtime/durable state,
record validity/schema, role, IDs, network ID, provisioning generation,
hardware/capability profiles, label, hardware identity, window remaining,
Event-domain presence/count summary where safely recoverable, last volatile
result, and diagnostic counters. Canonical zero represents unavailable fields.

`APPLY_PROVISIONING` carries one complete target record, the expected hardware
identity, and `ACK_EVENT_ERASURE`. It is accepted only in
PROVISIONING_ALLOWED. The device assigns generations. Success means final
PROVISIONED bytes were committed/read back and the response reports
`REBOOT_REQUIRED`; it does not mean the role changed live.

`FULL_FACTORY_RESET` contains expected hardware identity and the explicit
erasure acknowledgement. It requires the separately selected physical full-
reset mode. `CANCEL_PROVISIONING_WINDOW` mutates volatile state only and is
rejected after durable PENDING begins.

Minor-3 provisioning responses use the exact `PROVISIONING_RESULT = 0x06`
codes frozen in `HOST_PROTOCOL_0.3.md`. Syntax/framing failures continue to use
the existing minor-3-valid protocol/request rejection vocabulary; lifecycle,
identity, generation, authorization, Event-erasure acknowledgement, storage,
durable success/retry, and reset outcomes use the new class only where the
frozen registry assigns it.

Malformed framing/payload uses existing protocol rejection. Unsupported
minor/category/operation remains explicit. Requests never echo secrets because
v0.8 stores none. The Python Host reference gains explicit status, apply,
reset, and cancel commands; it remains a bounded development/qualification
utility, not an interactive shell.

## 16. Wire Protocol impact

Wire Protocol remains **1**. No new packet type, opcode, header field, payload
field, RF provisioning operation, or network-ID field is required.

After boot resolution, existing COMMAND/ACK/RESPONSE/TEST/EVENT paths use the
provisioned local and peer IDs everywhere compile-time IDs were previously
used. Packet geometry, sequence correlation, exact command duplicate identity,
Event identity/content, admission ACK, retry, and receive restoration remain
unchanged.

Because network ID is not on Wire 1 and traffic is unauthenticated, two nearby
networks using the same public device IDs are not isolated by v0.8. The brief
does not conceal this limitation or reinterpret network ID as a security
boundary.

## 17. UI and device-state impact

Keep existing provisioned role screens, screen ordering, rendering, navigation,
Event producer gestures, settings values, and timeout behavior unchanged except
for the bounded protected-management entry.

Add startup/maintenance presentations:

| State | Minimum OLED content |
|---|---|
| UNPROVISIONED | `UNPROVISIONED`, abbreviated hardware ID, `HOLD TO PROVISION`, radio `OFF` |
| PROVISIONING_ALLOWED | `PROVISIONING`, USB/local indicator, seconds remaining, no RF |
| PROVISIONED HUB | existing Hub UI; Device screen uses persistent role/local/peer data |
| PROVISIONED NODE | existing Node UI; Device screen uses persistent role/local/peer data |
| INVALID_PROVISIONING | `IDENTITY INVALID`, bounded reason code, `RADIO OFF`, recovery prompt |
| COMMITTING/RESET | operation and erasure scope; input cannot start another mutation |
| REBOOT_REQUIRED | committed role/ID summary and explicit reboot instruction; radio remains off |

Do not put editable identity fields into the ordinary settings editor. A
protected Device Management action may be reached from that modal UI, but uses
separate state, storage, confirmation, and rendering. Existing Reset Settings
continues to mean settings-only reset.

## 18. Diagnostics

Add bounded volatile counters and last-result state for:

- virgin/unprovisioned boot;
- valid record recovery and fallback-copy recovery;
- invalid, unsupported, conflict, and storage-unavailable recovery;
- provisioning windows opened, expired, and cancelled;
- apply/reset requests accepted and rejected by reason;
- pending transactions recovered;
- successful provisioning/reprovisioning/full reset;
- commit, readback, verification, settings-reset, and Event-clear failures; and
- radio starts blocked by provisioning state.

Diagnostics must saturate, must not cause writes, and must not expose future
credential material. The authoritative current identity comes directly from
the selected protected record, not a diagnostic shadow. The last provisioning
result is volatile and clearly labeled as such.

Host minor 3 exposes the detailed read-only snapshot. Existing GET_DEVICE_INFO,
HELLO, GET_STATUS, GET_DIAGNOSTICS, and Event diagnostics remain compatible for
provisioned minor-1/2 clients. Device/OLED presentation may abbreviate fields
but must not claim validity unavailable from the storage manager.

## 19. Storage and recovery behavior

Storage ownership remains separated:

```text
redline  -> ordinary Configuration Schema 1 settings
red_id   -> protected Identity Schema 1 and provisioning transaction
red_evt  -> Node custody + Hub ledger Event schemas
future red_sec -> credentials/security state, not created in v0.8
```

Pure codecs own persistent bytes. A pure `IdentityStore` owns dual-copy
selection, invariants, transaction transitions, and recovery. An ESP32 adapter
owns Preferences/NVS. Runtime integration schedules writes only at explicit
foreground safe points. ISR, renderer, Host parser, Wire codec, and capability
handlers never access NVS.

Write frequency is limited to provisioning, recovery repair, reprovisioning,
and reset. Read-only status and every ordinary boot do not rewrite a healthy
record. Optional fallback repair writes at most one copy per detected recovery
event and only after the selected authority is unambiguous.

Unknown schemas are preserved and never downgraded or overwritten by ordinary
boot. Only a physically confirmed full reset may replace them. Storage
unavailability never defaults to a radio-capable identity.

## 20. Migration from v0.7.0

The v0.8 common image intentionally boots **UNPROVISIONED** when `red_id` has
no Identity Schema 1 record. It MUST NOT silently infer protected identity from
the historical `tx`/`rx` image, `ARGUS_LOCAL_DEVICE_ID` flags, current Event
metadata, USB port number, or hardware MAC.

The controlled Host tool MAY offer an operator convenience command that
constructs a proposal from explicitly supplied values matching the former
pair (`Hub 0x01`, `Node 0x10`, for example). The device receives an ordinary
fully explicit APPLY request and applies all normal validation/physical gates.
There is no automatic firmware migration/import path.

If legacy `red_evt` keys exist, provisioning status reports their presence and
APPLY requires `ACK_EVENT_ERASURE`. Successful first provisioning clears them
transactionally. This prevents v0.7 queued/ACTIVE/CONSUMED records from being
adopted under an identity whose provenance was not explicitly established.
Ordinary Configuration Schema 1 settings remain and are used after the new
identity boots, unless the operator chooses full factory reset.

## 23. Native and deterministic test plan

At minimum, deterministic tests cover:

### 23.1 Codec and validation

- exact virgin/unprovisioned, pending, Hub, Node, and reset vectors;
- valid Hub and Node provisioning;
- equal local/peer IDs, `0x00`, and `0xFF` rejected;
- zero network ID, unknown role/profile, malformed label/tail/reserved bytes;
- wrong size/magic/CRC, unknown schema, unknown state/transaction;
- record generation and provisioning generation ordering, ambiguity, and
  exhaustion.

### 23.2 Transaction and storage faults

- missing both copies gives virgin UNPROVISIONED;
- malformed/unknown copies give INVALID rather than defaults;
- torn/partial PENDING write leaves old authority and Event state;
- failed commit/readback/byte verification at every write;
- reboot after successful provisioning;
- reboot during every failed provisioning/reset phase;
- pending recovery is idempotent and bounded;
- factory reset completes settings, Event, and identity clearing in order;
- ordinary settings reset preserves identity and Event state;
- status reads cause no write.

### 23.3 Reprovisioning and Events

- role change, peer change, local-ID change, network change, profile change,
  and label change each clear Event domains before activation;
- stale queued Node records never transmit under a new Source_Device_ID;
- stale allocator epoch/high-water data is not inherited;
- stale Hub ACTIVE/CONSUMED records and ordinal metadata are not inherited;
- clear failure preserves PENDING and fails closed;
- unchanged APPLY preserves Event state and generations;
- new provisioning produces a fresh Event epoch/ID lifecycle;
- normal unchanged-identity reboot preserves v0.7 checkpoint/debit, FIFO,
  retry, ACK, ledger, and consume semantics.

### 23.4 Host and control boundary

- malformed provisioning request, invalid value lengths/types, unknown flags,
  and reserved bits;
- APPLY/reset outside allowed physical state rejected without mutation;
- expected hardware-identity mismatch rejected;
- window expiration/cancel/disconnect before PENDING causes no mutation;
- disconnect after PENDING does not cancel durable recovery;
- read-only status is repeatable/non-mutating;
- RF cannot invoke or mutate provisioning;
- minor-1 and minor-2 exact vectors, feature bitmaps, retained responses, and
  operations remain green;
- unprovisioned legacy HELLO receives the documented response and no false role.

### 23.5 Runtime/UI/common image

- virgin, valid Hub, valid Node, invalid, PENDING, and reset startup;
- no radio initialization/TEST/Event producer when not provisioned;
- identity immutable during ordinary runtime;
- physical entry requires the exact confirmed gesture and safe point;
- wake/startup-held input cannot provision or reset;
- UI entry/exit creates no Event and mutates no Event state;
- ordinary settings interaction unchanged;
- the common build has no operational identity macros and both role paths use
  the recovered snapshot;
- all existing v0.7 native suites remain green.

Native fault injection is authoritative for precise torn writes, individual
commit/readback failures, generation conflicts, and interruptions too fast or
selective to induce legitimately on hardware.

## 27. Failure and characterization-break policy

Stop on the first unexplained deviation involving:

- common artifact identity or wrong physical board;
- radio activity before valid provisioning;
- false/fabricated role or ID;
- a mutation accepted outside the physical window;
- torn/mixed authority, generation ambiguity, unexpected defaults, or write
  loop;
- old Event/ledger identity surviving reprovisioning;
- identity change without reboot or Event-erasure acknowledgement;
- Host minor-1/2 incompatibility or malformed minor-3 behavior;
- reset, radio ownership, structured operation, Event, settings, UI, or legacy
  TEST regression; or
- any evidence contradicting the expected state model.

Preserve logs and persistent state. Invoke a characterization break: identify
the smallest observable boundary, add diagnostics only if existing surfaces
cannot distinguish it, reproduce deterministically where possible, repair only
the proven owning defect, rerun every invalidated software/bench gate, then
resume from a documented physical baseline. Never retry a stimulus merely to
obtain a pass or rewrite the failed attempt.

## 30. Open questions

No scope-blocking design question remains in this brief. Host Protocol 0.3
request/response byte layouts, feature/category bits, operation and result-code
assignments, lifecycle semantics, parser bounds, and golden vectors are frozen
by `HOST_PROTOCOL_0.3.md`. Stage 5 implements that contract; it is not an
invitation to redesign the provisioning boundary.

If implementation evidence shows that the selected 64-byte record cannot
represent the frozen fields or that statically composing both role runtimes
exceeds reviewed HELTEC_V4 resource bounds, stop and amend this design with an
explicit compatibility/resource analysis. Do not silently restore separate
operational images, remove transactional fields, or borrow v0.9 security scope.
