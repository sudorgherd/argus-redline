## 1. Status and scope

This record documents the production dependency authority, framework-migration provenance, source boundary, validation evidence, and a bounded primary-source advisory check for ARGUS REDLINE v0.6.0.

It is not represented as an exhaustive SBOM vulnerability scan or independent security audit. The August 14 security review remains the authoritative project finding record. v0.6.0 preserves the v0.5.1 F-01 duplicate-cache remediation; F-02, F-03, and F-04 remain deferred authenticated-transport requirements.

## 3. Framework migration provenance

The previous production authority was PlatformIO Espressif32 `7.0.1` with Arduino-ESP32 `2.0.17` / framework package `3.20017.241212+sha.dcc1105b`.

During v0.6.0 Step 15, intermittent remote structured operations could complete the full REDLINE radio transaction and Host response handoff while Windows received no correlated Host frame. Qualification-only tracing subsequently proved full acceptance by `Serial.write()` for an affected response.

The project rejected reliability masking through arbitrary delays, automatic retries, duplicate Host responses, repeated writes, USB reset cycles, control-line toggling, unbounded queues, or semantic Host/Wire changes.

A narrow repository-controlled HWCDC backport was also rejected after reproducing the failure.

The complete Arduino-ESP32 3.3.9 / ESP-IDF 5.5.4 generation was then isolated and qualified without changing REDLINE Host Protocol, Wire Protocol, capability, authorization, settings, or application semantics. It passed M3, M4, M5, and the complete restarted M6 / Step 15 qualification.

The accepted production configuration therefore promotes the fully qualified framework generation rather than maintaining a local fork of old HWCDC behavior.

## 4. Characterization compatibility boundary

The Arduino-ESP32 3.x migration exposed one API difference in the validation-only ADC characterization path: `adcAttachPin()` is not available in the 3.x core.

`lib/capability_characterization/src/capability_characterization_arduino.h` uses a version-conditional characterization adapter:

- Arduino 2.x retains the established `adcAttachPin()` path.
- Arduino 3.x uses the supported ADC initialization path.
- The behavior remains guarded by `ARGUS_CAPABILITY_CHARACTERIZATION`.
- Ordinary production analog capability remains fail-closed as `HARDWARE_UNAVAILABLE`.

Both framework generations passed TX and RX characterization builds after this compatibility correction.

## 5. Bounded primary-source advisory check

A release-time primary-source check was performed against the major selected upstream projects. This is deliberately narrower than the complete v0.5.1 dependency/SBOM audit.

Observed release/security evidence:

- PlatformIO Core `6.1.19` is the current 6.1.x release used by the project, and the PlatformIO Core security page lists 6.1.x as supported with no published project security advisories.
- Arduino-ESP32 `3.3.9` is based on ESP-IDF `5.5.4`.
- The 2026 Arduino-ESP32 WebServer digest-authentication advisory GHSA-28hv-fwm3-rpcq affects versions through `3.3.7` and is patched in `3.3.8+`; the selected `3.3.9` release is outside that affected range.
- RadioLib `7.7.1` is a patch release whose published change fixes an out-of-bounds read and memory leak in LoRaWAN `parseDownlink`. The REDLINE radio role uses SX1262 transport rather than LoRaWAN, and the selected release includes that fix.
- RadioLib's security page lists no published project advisories and explicitly states that the library is not intended for security-critical applications.

Primary-source references:

- PlatformIO Core 6.1.19 release: https://github.com/platformio/platformio-core/releases/tag/v6.1.19
- PlatformIO Core security policy: https://github.com/platformio/platformio-core/security
- Arduino-ESP32 releases: https://github.com/espressif/arduino-esp32/releases
- Arduino-ESP32 GHSA-28hv-fwm3-rpcq: https://github.com/espressif/arduino-esp32/security/advisories/GHSA-28hv-fwm3-rpcq
- RadioLib 7.7.1 release: https://github.com/jgromes/RadioLib/releases/tag/7.7.1
- RadioLib security policy: https://github.com/jgromes/RadioLib/security

No new release-blocking dependency advisory was established by this bounded check. This statement is not equivalent to "no known vulnerabilities": components without complete product-specific advisory coverage, transitive build-tool packages, and advisories outside the reviewed primary-source set remain evidence limitations.

## 6. Security disposition preserved

v0.6.0 does not claim to close the deferred authenticated-network findings.

The release still lacks:

- cryptographic RF peer authentication;
- RF confidentiality;
- authenticated persistent replay/freshness protection;
- authentication-first RF resource rejection/governance;
- cryptographic USB user identity;
- protection against deliberate RF jamming.

The v0.5.1 duplicate-cache remediation remains preserved: complete structural admission precedes duplicate-cache lookup or mutation, and canonical duplicate identity remains source + sequence + opcode + payload length + meaningful payload bytes.

Production unauthenticated remote side-effect authority remains restricted.

## 9. Source and architecture boundary

v0.6.0 adds bounded source components for:

- Host Protocol vocabulary, codec, framing, streaming parser, and diagnostics;
- Host transport abstraction and role integration;
- structured operation request/response model;
- device/capability/procedure/diagnostic operation service;
- structured Wire operation and RESPONSE encoding;
- Hub radio-operation bridging;
- bounded retained-result lifecycle;
- qualification-only structured/TX-edge tracing;
- Python Host reference tooling;
- Arduino 3.x characterization compatibility.

The release does not introduce:

- a generic shell;
- arbitrary memory or GPIO access;
- runtime plugin installation;
- arbitrary remote code execution;
- application-specific ARGUS/BLACKSHEEP/NIGHTWATCH business logic;
- general opaque application transport;
- Node-originated EVENT queues;
- persistent identity/provisioning;
- authenticated RF transport;
- multi-Node orchestration;
- repeaters, routing, or mesh.

## 10. Audit conclusion

The v0.6.0 production dependency and source authority is explicit, pinned where appropriate, and consistent with the framework generation exercised during physical qualification.

The release retains the known security boundary rather than presenting framework migration or structured Host operations as cryptographic security work.

No new release-blocking dependency issue was established by the bounded primary-source advisory check, subject to the evidence limitations above.
