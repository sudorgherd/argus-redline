# ARGUS REDLINE v0.5.0 Capability Model

**Status:** Proposed architecture; implementation review has not approved these structs or enum values.

## Purpose

Define a bounded, inspectable registry of approved local hardware capabilities. Firmware exposes logical capability contracts and dispatches only to compiled handlers. It does not expose arbitrary pins, application names, uploaded code, or a remotely mutable registry.

## Architectural boundary

Firmware owns device identity, radio timing, transport reliability, the local registry, local validation, authorization hooks, safety/interlocks, and bounded hardware handlers. A future connected host owns human-facing names, databases, workflows, application permissions, orchestration, interpretation, command construction, and high-level procedure selection.

v0.5.0 proves local APIs and a low-risk hardware slice. v0.6.0 owns structured REQUEST/RESPONSE radio semantics, Host Protocol 0.1, the serial console, and the complete PC-to-capability path. Wire Protocol remains `1` in v0.5.0.

## Terminology

- **Capability:** an approved local function identified within one device.
- **Descriptor:** immutable metadata declaring class, operations, value contract, and policy IDs.
- **Registry:** a bounded ordered view of validated descriptors.
- **Operation:** a local request such as READ or SET; not a Wire Protocol opcode.
- **Binding:** profile-private mapping from logical ID to an approved handler and physical resources.
- **Authorization:** whether the supplied local caller context may request an operation.
- **Safety/interlock:** whether local conditions allow an otherwise authorized operation now.
- **Application semantics:** human meaning such as “evacuation light”; host-owned and absent from descriptors.

## Proposed identity

```cpp
using CapabilityId = uint16_t;
constexpr CapabilityId INVALID_CAPABILITY_ID = 0x0000;
```

IDs are opaque, nonzero, unique within one device, and stable within a hardware profile. v0.5.0 profile IDs are assigned at compile time, but compile-time assignment and permanent presence are not properties callers may infer from the higher-level ID contract. IDs are neither GPIO numbers nor globally unique device identities. A future host addresses a capability only in the context of a device ID.

Profile authors may group IDs by convention (for example `0x01xx` outputs, `0x02xx` digital inputs, and `0x03xx` analog inputs), but callers, dispatch, and compatibility must not derive class, permanence, hardware origin, provider, or policy from those ranges. The descriptor remains authoritative, and callers must tolerate lookup failure.

## Proposed capability classes

All values are proposals with `uint8_t` representation:

| Value | Class | v0.5.0 treatment |
|---:|---|---|
| `0x00` | `INVALID` | Rejected |
| `0x01` | `DIGITAL_INPUT` | Defined; simulated then low-risk implementation |
| `0x02` | `ANALOG_INPUT` | Defined; simulated then bounded external-input implementation |
| `0x03` | `SENSOR` | Defined; reserved for a later physical sensor |
| `0x04` | `INDICATOR_OUTPUT` | Defined; simulated then arbitration-safe implementation |
| `0x05` | `SIGNAL_OUTPUT` | Defined; reserved |
| `0x06` | `RELAY_OUTPUT` | Defined; reserved; no external-power relay in v0.5.0 |
| `0x07` | `POWER_MONITOR` | Defined; reserved |
| `0x08` | `LOCATION_PROVIDER` | Defined; reserved |
| `0x09` | `LOCAL_STORAGE` | Defined; reserved and not a raw storage interface |
| `0x0A` | `LOCAL_PROCEDURE` | Descriptor vocabulary only; no transferred or remotely installed code |

Unknown values are invalid. Defining a class does not imply that a profile registers one.

## Proposed operations and flags

`Operation` is a `uint8_t` local enum: `ENUMERATE=0x00`, `DESCRIBE=0x01`, `READ=0x02`, `SET=0x03`, `TRIGGER=0x04`, and `RUN_LOCAL_PROCEDURE=0x05`.

`ENUMERATE` acts on the registry rather than one descriptor and invokes no capability handler. `DESCRIBE` copies the selected descriptor snapshot and also invokes no hardware handler. `READ`, `SET`, `TRIGGER`, and `RUN_LOCAL_PROCEDURE` are dispatchable capability operations. The descriptor advertises all per-capability operations using one byte:

| Flag | Meaning |
|---:|---|
| `0x01` | `DESCRIBE` |
| `0x02` | `READ` |
| `0x04` | `SET` |
| `0x08` | `TRIGGER` |
| `0x10` | `RUN_LOCAL_PROCEDURE` |
| `0xE0` | Reserved; must be zero in v0.5.0 |

Every valid descriptor advertises `DESCRIBE`. Class/operation validation rejects combinations outside this initial matrix:

- `DIGITAL_INPUT`, `ANALOG_INPUT`, `SENSOR`, `POWER_MONITOR`, and `LOCATION_PROVIDER`: `DESCRIBE | READ`.
- `INDICATOR_OUTPUT`: `DESCRIBE | READ | SET` when state can be read, otherwise `DESCRIBE | SET`.
- `SIGNAL_OUTPUT` and `RELAY_OUTPUT`: `DESCRIBE | SET` and optionally `TRIGGER` only after a later safety review.
- `LOCAL_STORAGE`: no operational registration in v0.5.0.
- `LOCAL_PROCEDURE`: `DESCRIBE | RUN_LOCAL_PROCEDURE` only if later approved; descriptor-only is the default.

Unsupported combinations fail before profile code runs.

`ENUMERATE` and `DESCRIBE` do not use the descriptor's hardware `valueType` as an input or output contract. A future exposure layer may apply discovery policy before returning enumeration or description data, but the v0.5.0 hardware authorization and safety/interlock hooks apply before hardware-reading or hardware-affecting handler execution. `READ` therefore still passes authorization and safety/interlock gates whenever its profile policy requires them.

## Proposed value model

`ValueType` is a `uint8_t` enum: `NONE=0x00`, `BOOLEAN=0x01`, `UNSIGNED_32=0x02`, `SIGNED_32=0x03`, `NORMALIZED_U16=0x04`, `FIXED_Q16_16=0x05`, and `ENUM_U16=0x06`. Floating point and strings are excluded.

```cpp
struct CapabilityValue {       // proposed exact size: 8 bytes
    ValueType type;             // 1 byte
    uint8_t reserved[3];        // must be zero
    uint32_t bits;              // tagged payload
};
static_assert(sizeof(CapabilityValue) == 8);
```

- `BOOLEAN`: `bits` is exactly 0 or 1.
- `UNSIGNED_32`: full unsigned range, further bounded by the descriptor.
- `SIGNED_32`: two's-complement value interpreted as `int32_t`.
- `NORMALIZED_U16`: low 16 bits in `0..65535`; upper bits zero.
- `FIXED_Q16_16`: signed Q16.16 only where a concrete sensor justifies it.
- `ENUM_U16`: low 16 bits; upper bits zero and descriptor/profile validates members.
- `NONE`: `bits` is zero and is used for operations without an input or returned value.

Local representation is deterministic and pointer-free. Any future wire encoding must be separately specified by v0.6.0; it must not serialize compiler padding.

## Proposed descriptor

```cpp
struct CapabilityDescriptor {  // proposed exact size: 20 bytes
    CapabilityId id;            // 2
    CapabilityClass capabilityClass; // 1
    uint8_t operationFlags;     // 1
    ValueType valueType;        // 1
    uint8_t authorizationPolicyId; // 1
    uint8_t safetyPolicyId;     // 1
    uint8_t unitCode;           // 1
    uint16_t metadataFlags;     // 2
    uint16_t reserved;          // 2, must be zero
    uint32_t minimumBits;       // 4
    uint32_t maximumBits;       // 4
};
static_assert(sizeof(CapabilityDescriptor) == 20);
```

The descriptor is bounded, pointer-free, origin-neutral, and provider-neutral. It contains no raw pin, driver pointer, handler binding, or lifetime ownership. Handler/provider lifetime remains outside the descriptor; registry APIs own discovery and lookup semantics.

| Field | Meaning and allowed values | Owner / compatibility rule |
|---|---|---|
| `id` | Nonzero opaque logical ID | Hardware profile; stable within profile |
| `capabilityClass` | Known class enum | Capability model; unknown rejected |
| `operationFlags` | Valid flags and class combination | Capability model; reserved bits zero |
| `valueType` | One known fixed type | Capability model; must match class/operations |
| `authorizationPolicyId` | `0` default local policy; other compiled policy IDs | Profile/security policy; unknown rejected |
| `safetyPolicyId` | `0` no additional interlock; other compiled policy IDs | Profile safety policy; unknown rejected |
| `unitCode` | `0` none, `1` boolean, `2` count, `3` raw ADC, `4` normalized, `5` millivolts | Vocabulary; no strings, unknown rejected |
| `metadataFlags` | Initially `0x0001` simulated/test fixture; all other bits zero | Model; must not duplicate operation support; `READ` is authoritative for readability |
| `reserved` | Must be zero | Preserves deterministic extension space |
| `minimumBits` / `maximumBits` | Inclusive bit-pattern bounds interpreted deterministically by `valueType` | Profile supplies; dispatcher performs type-specific validation/comparison |

Descriptors contain no pin numbers, pointers, labels, application names, handler state, or mutable runtime values. Enumeration returns bounded descriptor copies/snapshots, not mutable references.

Bounds use the same tagged-bit interpretation as `CapabilityValue`:

- `NONE`: both bounds must be zero.
- `BOOLEAN`: bounds are unsigned, each is within `0..1`, and minimum is no greater than maximum.
- `UNSIGNED_32`: bounds and values use full-width `uint32_t` comparison.
- `SIGNED_32`: each bound and value bit pattern is reinterpreted as `int32_t`, then compared using signed arithmetic.
- `NORMALIZED_U16`: upper 16 bits of each bound and value are zero; unsigned comparison is limited to `0..65535`.
- `FIXED_Q16_16`: each bound and value bit pattern is reinterpreted as signed `int32_t` Q16.16, then compared using signed arithmetic.
- `ENUM_U16`: upper 16 bits are zero; unsigned bounds may constrain the numeric domain, while profile validation determines actual allowed enum members.

The dispatcher must select comparison semantics explicitly from `valueType`. It must never rely on implicit conversion or mix signed and unsigned arithmetic during bounds validation.

## Proposed results and denial statuses

`OperationStatus` is a `uint8_t` enum:

| Value | Status |
|---:|---|
| `0x00` | `OK` |
| `0x01` | `CAPABILITY_NOT_FOUND` |
| `0x02` | `UNSUPPORTED_OPERATION` |
| `0x03` | `INVALID_VALUE_TYPE` |
| `0x04` | `VALUE_OUT_OF_RANGE` |
| `0x05` | `UNAUTHORIZED` |
| `0x06` | `INTERLOCK_ACTIVE` |
| `0x07` | `HARDWARE_UNAVAILABLE` |
| `0x08` | `OPERATION_FAILED` |
| `0x09` | `BUSY` |
| `0x0A` | `INVALID_DESCRIPTOR` |

```cpp
struct OperationResult {       // proposed exact size: 12 bytes
    OperationStatus status;     // 1
    uint8_t reserved[3];        // zero
    CapabilityValue value;      // valid only when status == OK
};
static_assert(sizeof(OperationResult) == 12);
```

This is a local operation result, not a transport ACK. `status` explains validation, denial, or hardware execution; `value` carries a successful hardware value. Future transport delivery/error semantics remain separate in v0.6.0.

## Registry invariants

- Recommended capacity: 16 descriptors per profile for v0.5.0.
- Representation: immutable static array plus `uint8_t` count/view; no template registry and no heap ownership. Dynamic RMP/module registration is not part of v0.5.0.
- Count never exceeds capacity; null data is allowed only with count zero.
- IDs are nonzero and unique.
- Every descriptor passes field, class/flag, type, bounds, policy-ID, metadata, and reserved-byte validation.
- Registry order is the profile table order and is deterministic across boots/builds of that profile.
- Validation occurs once during setup and remains callable in native tests. An invalid registry disables capability dispatch and reports degraded diagnostics; it must not prevent radio startup.
- Registry tables cannot be modified by radio, serial, UI, or settings input.
- Descriptor consumers use lookup/enumeration snapshots rather than direct backing-array access and do not retain descriptor pointers across operations.

## Enumeration and lookup

Enumeration accepts an index and caller-owned output descriptor. It returns the exact count and either copies one complete descriptor or reports out-of-range; it exposes no table pointer. Lookup performs bounded linear search by opaque logical ID and copies a snapshot. Callers tolerate lookup failure and do not retain descriptor pointers or assume permanent capability lifetime. With capacity 16 this is clearer than sorting, hashing, allocation, or template machinery and has deterministic worst-case cost.

The v0.5.0 backing store remains static. These API and lifetime rules are only an architectural constraint: a future composite/dynamic RMP provider should be able to expose capabilities through the same `CapabilityId`, descriptor, validation, authorization, value, result, and dispatch model without replacing higher-level consumers. No RMP provider, dynamic registration, attach/detach lifecycle, or module discovery is implemented in v0.5.0.

```text
profile table
→ registry validation
→ bounded enumeration
→ descriptor snapshot
```

## Authorization, safety, and dispatch

Caller context is a small local enum/flags record such as `FIRMWARE_LOCAL`, `UI_LOCAL`, or `FUTURE_REMOTE`. It is not proof of cryptographic identity. In v0.5.0 production integration uses locally supplied contexts only.

Authorization and safety are separate compiled policy tables/switches. Authorization answers whether the caller/context may perform the operation. Safety answers whether current local state permits it. Both return explicit status and run before dispatchable handler execution according to profile policy, including for `READ` where required. Registry-level `ENUMERATE` and snapshot-only `DESCRIBE` do not execute hardware handlers; any future policy limiting their external visibility belongs to the exposure layer.

```text
logical capability ID
→ lookup
→ operation support check
→ value/type validation
→ authorization
→ safety/interlock
→ approved handler
→ structured result
→ diagnostics update
```

Not-found, unsupported operation, type/range failure, authorization denial, or interlock denial never calls the handler. `BUSY`, hardware unavailable, and operation failure propagate deterministically. Diagnostics count the final outcome without changing radio counters.

## Handler-binding recommendation

Three options were considered:

1. **Tagged profile switch:** smallest physical surface, but direct use can couple pure dispatch to board details.
2. **Fixed function table:** compact, but function pointers broaden the callback surface and can bind incompatible handlers.
3. **Narrow abstract interface:** one interface with a single virtual execute method; test fakes and the Heltec adapter implement it without heap allocation.

Recommend option 3. It uses virtual dispatch through a borrowed `LocalCapabilityHandler&`, but requires no RTTI, type inspection, or dynamic cast. Concrete handler objects are static- or stack-owned, remain alive for the full borrowed use, and are never allocated or transferred by the dispatcher. No descriptor contains a handler pointer. The Heltec implementation switches on logical ID privately, then uses profile-owned pins/polarity/ADC constraints. A simulated implementation supports native and pre-hardware tests. This is one narrow interface, not an inheritance framework or event bus.

Simulated handlers are development/test fixtures used before approved hardware integration. They must not remain registered as production release capabilities unless an explicitly test-only build documents them; production registration represents actual approved hardware/profile behavior.

No raw pin number crosses the hardware-profile boundary.

## Hardware-profile ownership

`heltec_v4_capabilities` privately owns logical-ID constants, pin assignments, polarity, ADC limits, initialization, policy selection, LED arbitration requests, and the concrete handler. The general model owns validation and dispatch order. DeviceInput remains the GPIO0 classifier; any button capability reads a snapshot supplied by that owner rather than polling GPIO0 again. The built-in LED capability requests an application-indicator state through existing LED arbitration rather than writing the pin directly.

## Diagnostics and presentation ownership

Capability diagnostics are separate capability-owned counters/state: lookups, accepted operations, denials, unsupported operations, validation failures, interlock denials, busy results, and hardware failures. RuntimeState may receive a bounded copied summary for approved diagnostics/presentation; it is not the registry or authoritative capability owner. DeviceUi receives bounded presentation snapshots only and owns no descriptors, handlers, registry state, or dispatch. The settings request queue is not generalized into a capability event system. The default v0.5.0 presentation is one summary on DEVICE or ABOUT (registered count and last capability status), not a new browser screen.

## Local invocation and scheduling ownership

Capability dispatch is synchronous in the pure model. Role firmware owns when an operation may execute. Handlers are never called from ISR context, renderer/UI callbacks, raw button callbacks, protocol decode logic, or transaction-engine internals. Hub execution must use an existing transaction/radio-safe state; Node execution remains subordinate to receive/validation/ACK/duplicate obligations and checked receive restoration. Handlers are bounded, introduce no new blocking capability delay to required radio/UI scheduling, and return failure without destabilizing radio operation. One approved local invocation produces at most one dispatch.

v0.5.0 defines no production transport or generic event mechanism for invocation. Physical characterization may use a separately approved temporary local validation path or validation build. That scaffolding is not a radio opcode, Host Protocol feature, serial maintenance console, permanent UI command, or production API commitment and is absent from the production release configuration.

## Persistence exclusion

Descriptors, IDs, raw pins, bindings, policy code, and capability runtime state are compiled into the profile and are not stored in the v0.4.0 ordinary-settings namespace. Future per-capability configuration requires a separate schema and authority review.

## Wire and host exclusion

No capability operation becomes a LoRa opcode in v0.5.0. Wire Protocol `1`, packet sizes, TEST/ACK behavior, device IDs, retries, and duplicate behavior remain unchanged. `GET_CAPABILITIES`, `READ_INPUT`, `READ_SENSOR`, `SET_INDICATOR`, and `TRIGGER_OUTPUT` are local semantic contracts only. Host framing, application labels, REQUEST/RESPONSE schemas, and PC orchestration begin in v0.6.0.

## First vertical slice mapping

| Capability | Proposed ID | Initial handler | Physical rule |
|---|---:|---|---|
| Application indicator | `0x0101` | Simulated, then arbitration request | Never bypass radio/button LED ownership |
| Digital user input | `0x0201` | DeviceInput-owned state adapter | Never poll GPIO0 independently |
| Analog input 0 | `0x0301` | Simulated, then Heltec ADC adapter | Pin and voltage remain unresolved until board verification |

The numeric grouping is a profile convention only. A dedicated external digital input may replace GPIO0 if ownership cannot remain singular. No relay or external-power load is part of the slice.

## Rejected alternatives

- Raw GPIO IDs or pin numbers: bypass profile safety and are not stable capabilities.
- Runtime registration from radio/serial: creates an untrusted mutable hardware surface.
- Heap-owned vectors/maps/strings: unnecessary and nondeterministic for a small registry.
- Descriptor-held callbacks/pointers: leak implementation and broaden execution surfaces.
- Generic event bus or plugin framework: obscures ownership and exceeds the milestone.
- Application names in firmware: move host semantics into constrained devices.
- New v0.5.0 LoRa opcodes: collapse the deliberate v0.5.0/v0.6.0 boundary.
- Transferred LOCAL_PROCEDURE code: remote code installation is explicitly excluded.

## Open decisions and recommended defaults

- **ID width:** approve `uint16_t`; enough profile-local space without 32-bit overhead.
- **Descriptor layout:** approve the proposed 20-byte record, `uint32_t` bound bit patterns with explicit type-directed comparison, and exact static assertion.
- **Units:** retain the small numeric `unitCode`; no string labels or conversion engine.
- **Binding:** approve one borrowed narrow handler interface with profile-private ID switch.
- **GPIO0:** consume DeviceInput state only; choose another verified input if a clean snapshot is unavailable.
- **Built-in LED:** represent an application-indicator request through existing OR arbitration; otherwise remain simulated.
- **ADC:** keep pin and maximum safe input unresolved until board definition and schematic are verified; use an externally bounded source.
- **OLED:** add only a bounded DEVICE/ABOUT summary unless hardware review proves a dedicated screen necessary.
- **LOCAL_PROCEDURE:** descriptor vocabulary only in v0.5.0; no registered production procedure by default.
- **Operation numbers:** use the local enum above only; reserve no Wire Protocol opcode before v0.6.0.
