# ARGUS REDLINE v0.5.1 Qualification Results

## 1. Scope and disposition

This record covers the physical two-board qualification performed on 2026-08-15
(America/Chicago) for the committed F-01 duplicate-cache remediation. The tested
source was branch `v0.5.1-duplicate-cache-remediation` at
`d8c92fc9e88c833113102c6b1060c43bf2a3edad`, with the procedure in
`docs/V0.5.1_IMPLEMENTATION_AND_QUALIFICATION_BRIEF.md`.

The ordinary two-board TEST/ACK regression, formal isolated 30/30 exchange run,
retry/terminal-timeout behavior, and receive restoration all passed. Physical
duplicate-ACK regeneration was **NOT EXECUTED** because the repository and
available production setup provide no documented method to suppress only the
first ACK deterministically. Payload-distinct/malformed hardware injection was
**NOT APPLICABLE TO CURRENT PRODUCTION COMMAND SURFACE** because Wire Protocol 1
has no valid payload-bearing command and no approved hardware injection harness.
The native direct-tracker and transaction-engine tests remain the authoritative
proof for those F-01 cases. These limitations are permitted by the brief and are
not represented as physical passes.

No physical GPIO4/ADC1_CH3 characterization, startup-held-button reproduction,
or extended endurance/fault run was performed in this F-01 session.

## 5. Retry, timeout, and receive restoration

### 5.1 Node unavailable

**Retry result: PASS. Timeout result: PASS.** After a normal successful exchange,
the Node alone was disconnected from USB power with its antenna left attached.
For sequence 138, the Hub logged the initial TEST, a 2,500 ms ACK timeout, retry
1/2 with the same source/destination/sequence/opcode, a second timeout, retry 2/2
with the same identity, a final timeout, and `COMMAND FAILED | SEQ 138`. The
production periodic scheduler subsequently continued with the next sequence;
multiple cycles were observed, but sequence 138 is the bounded evidence case.

### 5.2 Restoration

**Result: PASS.** Only the Node was repowered; the Hub remained continuously
powered. Before the serial monitor caused a Node reset, buffered Node output
showed fresh Hub sequences 173 and 174 received and acknowledged successfully.
Before the later serial monitor caused a Hub reset, buffered Hub output showed
fresh sequences 202 and 203 transmitted and accepted as `ACK MATCHED`. Thus the
prior terminal timeout did not leave the continuously powered Hub outside normal
operation, and the restored Node resumed receive/ACK operation.

## 7. Diagnostic observations

The formal 30/30 serial interval showed 30 commands, 30 matching ACKs, zero
retries, zero timeouts, zero duplicates, zero resets, and zero radio errors.
Only exact duplicates should increment Node `DUP`; the post-run physical display
showed `DUP 0`, consistent with ordinary distinct sequences.

Live display snapshots were read while periodic production traffic continued:

- Hub: `TX 228`, `SUCCESS 209`, `RETRY/TO 15/22`, `BAD/IGN 0`. TX and SUCCESS
  continued advancing. The cumulative retry/timeout values include the deliberate
  Node-unavailable interval and setup activity, so they are not the isolated
  formal-run delta.
- Node: `RX 56` was read first; by the time the next row was read, `CMD/ACK` had
  advanced to `59/59`; `DUP 0`; `BAD/IGN 0`. This is a time-skewed live snapshot,
  not one atomic counter sample.

No malformed, ignored, duplicate, or radio-error event was observed during the
formal run. Serial behavior and display counters remained consistent with the
expected accepted, successful, retransmission, timeout, and completed-transaction
meanings.
