## 2. Repository-derived baseline

### 2.1 Wire and packet model

`lib/redline_protocol/src/redline_protocol.h` defines:

- `Protocol::VERSION = 1`;
- `HEADER_SIZE = 6`, `MAX_PACKET_SIZE = 32`, and `MAX_PAYLOAD_SIZE = 26`;
- `Protocol::Packet` fields `type`, `source`, `destination`, `sequence`, `opcode`, `payloadLength`, and fixed `payload[26]`;
- `COMMAND=0x01`, `ACK=0x02`, and codec-recognized-only `ERROR=0x03`;
- `TEST=0x64`, whose valid command payload length is exactly zero;
- ACK statuses `SUCCESS`, `UNSUPPORTED_OPCODE`, and `MALFORMED_PACKET`.

`Protocol::decode()` rejects a null/short input, the wrong protocol version, payload lengths above 26, encoded-length/payload-length mismatch, and unknown packet types before populating a packet. `src-rx/main.cpp::handleReceivedPacket()` additionally rejects radio packet lengths outside 6..32 and radio read failures before decode. These framing, bounds, version, and packet-type gates remain authoritative.

### 2.2 Current Node transaction behavior and F-01

`lib/transaction_engine/src/transaction_engine.h::NodeDuplicateTracker` is a single-entry, in-memory tracker. Its `isDuplicate()` compares only:

```text
source + sequence + opcode
```

Its `remember()` stores that tuple and an `AckStatus`; it stores neither payload length nor payload content. `evaluateNodeCommand()` currently checks destination, packet type, and sender, then performs duplicate lookup, and only afterward calls `Protocol::isSupportedCommandOpcode()` and `Protocol::isValidCommandPayload()`.

New supported, unsupported, and malformed addressed commands currently replace the one cache entry. A duplicate regenerates an ACK with `makeAcknowledgment()` from the incoming command metadata and the remembered status; encoded ACK bytes are not cached.

Consequently:

- a malformed command can be remembered under an identity later reused by a valid command;
- the later valid command can be classified as a duplicate before its own payload is validated;
- payload-distinct requests collide when source, sequence, and opcode match;
- a cached error can therefore determine a later valid request's returned result.

For the only current production command, TEST, the practical result is a false remote error or liveness/diagnostic failure. TEST has no actuator or application side effect, and current production RF does not enter capability dispatch. The issue is nevertheless a transaction-integrity and availability defect that must be corrected before payload-bearing commands are introduced. It is Medium severity; this brief does not characterize it as memory corruption, privilege escalation, or cryptographic compromise.

The exact acceptance criterion is:

> A malformed or payload-distinct request cannot determine the cached result returned for a later valid request, while legitimate retransmission idempotency is preserved.

### 2.3 Current orchestration and diagnostics

`src-rx/main.cpp::handleReceivedPacket()` increments decoded-packet history after decode, then maps `NodeCommandOutcome` to counters and radio behavior:

- wrong destination, sender, or packet type increments `ignoredPackets` and restores receive;
- `DUPLICATE` increments `duplicates` and regenerates an ACK;
- `ACK_SUCCESS` increments `acceptedCommands`, updates health and peer-seen state, and sends an ACK;
- unsupported opcode sends an error ACK without incrementing accepted or malformed;
- malformed payload increments `malformedPackets` and sends an error ACK.

`startAcknowledgment()` preserves the deliberate approximately 100 ms pre-ACK delay. ACK completion records `transmissionsCompleted` and restores receive. `RuntimeState::Counters` in `lib/runtime_state/src/runtime_state.h` uses saturating counters, including decoded packets, successful transactions, accepted commands, retransmissions, acknowledgment timeouts, duplicates, malformed packets, ignored packets, and radio errors.

The correction must not silently redefine these counters. In particular, malformed or unsupported traffic must not become a duplicate merely because it collides with valid cache state, and a payload-distinct invalid TEST must retain its malformed disposition rather than incrementing duplicates.

## 3. Required transaction design

### 3.1 Processing order

The v0.5.1 Node path must preserve this security order, split across the existing radio handler, codec, and transaction engine:

1. `handleReceivedPacket()` obtains the radio length and rejects lengths outside `HEADER_SIZE..MAX_PACKET_SIZE`.
2. Read the frame; reject radio/CRC failure under existing radio-error behavior.
3. `Protocol::decode()` validates the encoded bounds, exact payload length, Wire Protocol version 1, and recognized packet type.
4. Reject a destination not addressed to the local Node.
5. Reject an ignored packet type; only `COMMAND` is semantically admissible to the Node transaction evaluator.
6. Reject a source other than the configured Hub. Source remains routing metadata, not authenticated identity.
7. Validate whether the opcode is supported.
8. For a supported opcode, validate payload length and every opcode-specific structural rule. TEST requires exactly zero bytes. Future validators must inspect content where an opcode defines content constraints.
9. Without consulting or modifying semantic duplicate state, discard ignored/wrongly addressed requests and decode failures. Generate the currently contracted `UNSUPPORTED_OPCODE` or `MALFORMED_PACKET` ACK for addressed commands when applicable, but do not allow those invalid commands to consult or mutate semantic duplicate state.
10. Treat the fully validated command as the canonical admissible request.
11. Compare that request exactly against the valid single cache entry.
12. For an exact legitimate retransmission, regenerate an ACK from the retransmitted command metadata and the cached result. Do not execute again and do not replace the entry.
13. Otherwise execute the new request once, select its result, and cache its canonical identity and result only under the cache-mutation rules below.

This sequencing deliberately separates an error response from permission to affect duplicate state. It changes no packet byte, timing constant, retry owner, or ACK format.

### 3.2 Canonical duplicate identity

The canonical identity must include and exactly compare, at minimum:

```text
source
sequence
opcode
payload length
payload content for exactly payload length bytes
```

Recommended representation inside `NodeDuplicateTracker`:

```cpp
bool hasRememberedCommand;
uint8_t source;
uint8_t sequence;
uint8_t opcode;
uint8_t payloadLength;
uint8_t payload[Protocol::MAX_PAYLOAD_SIZE];
Protocol::AckStatus status;
```

An equivalent fixed representation or a stored canonical `Protocol::Packet` is acceptable only if padding and unused payload bytes cannot participate nondeterministically in equality. Prefer explicit field comparison: scalar fields first, then exactly `payloadLength` bytes. Zeroing unused bytes is useful for deterministic state inspection but does not replace length-bounded equality.

The following packet properties need not be stored in the v0.5.1 cache because they are invariants established before lookup:

| Property | Decision |
|---|---|
| Wire version | Not stored: `Protocol::decode()` admits only `Protocol::VERSION == 1`. |
| Packet type | Not stored: only `PacketType::COMMAND` reaches semantic lookup. |
| Destination | Not stored: only the configured local Node destination reaches lookup. |
| Source | Stored even though configured-sender validation precedes lookup; it is part of the required transaction identity and keeps tracker semantics explicit. |

If later architecture allows multiple peers, destinations, packet versions, or command classes within one tracker, the identity must be revisited rather than assuming these invariants still hold.

A hash or checksum may be used only as a fast prefilter. It must never be the sole equality test; hash collisions must fall through to exact length-and-byte comparison and cannot share cached results.

The representation is bounded by the existing 26-byte maximum payload, uses no heap allocation, has one entry, and performs at most a fixed scalar comparison plus 26 byte comparisons. Sequence rollover remains ordinary `uint8_t` behavior: an exact request may match the one current entry after rollover; a different canonical payload does not. No persistence, timestamps, replay window, or second cache entry is introduced.

RAM use is expected to increase by the fixed storage needed for payload length and up to 26 payload bytes, subject to compiler padding. Flash may change slightly due to reordered validation and bounded comparison code. The later implementation session must record actual map/build deltas; this brief does not invent byte measurements.

### 3.3 Cache-mutation and response rules

“Consult” means semantic duplicate lookup. “Modify” means replace or clear the valid single entry. Decode and ignored traffic leave the existing entry intact.

| Input/outcome | Consult cache? | Modify cache? | Response/disposition | Required counter/state effect |
|---|---:|---:|---|---|
| Exact valid retransmission | Yes | No | Regenerate ACK with original cached result | Increment duplicate; do not execute or increment accepted |
| New valid request | Yes | Yes, after execution/result selection | Execute once and ACK result | Preserve accepted/success semantics for TEST |
| Valid request with same source/sequence/opcode but different valid payload | Yes | Yes, after execution | Treat as a new request, never reuse old result | Not a duplicate; execute once under normal counters |
| Malformed opcode representation | No | No | If rejected by framing/codec, silent reject; otherwise use the applicable existing malformed disposition | Preserve malformed classification; existing valid entry unchanged |
| Bad payload length for supported opcode | No | No | ACK `MALFORMED_PACKET` | Increment malformed; existing valid entry unchanged |
| Structurally invalid opcode-specific payload | No | No | ACK `MALFORMED_PACKET` | Increment malformed; existing valid entry unchanged |
| Unsupported opcode | No | No | Preserve ACK `UNSUPPORTED_OPCODE` | Do not increment duplicate/accepted/malformed unless current counter contract is deliberately documented otherwise; entry unchanged |
| Wrong destination | No | No | Ignore and restore receive | Increment ignored; entry unchanged |
| Ignored packet type | No | No | Ignore and restore receive | Increment ignored; entry unchanged |
| Wrong configured sender | No | No | Ignore and restore receive | Increment ignored; entry unchanged |
| Wrong protocol version | No | No | Decode failure; no ACK; restore receive | Preserve decode-malformed accounting; entry unchanged |
| Decode failure, including bounds/length/type failure | No | No | No ACK; restore receive | Preserve malformed/radio classification; entry unchanged |
| Execution success | Already consulted as a new valid request | Yes | ACK `SUCCESS` | Cache canonical request plus success; accepted once |
| Execution error for a fully valid request | Already consulted as a new valid request | Yes, when current/future command contract permits result caching | ACK defined execution result | Cache only a deterministic result whose retransmission must be idempotent |
| Error generated during pre-execution semantic validation | No | No | Preserve defined error ACK | Error response does not authorize cache mutation |
| Retransmission after sequence rollover | Yes, only after full validity | No only if complete canonical request exactly matches current entry; otherwise yes after new execution | Exact match reuses result; distinct request executes | Deterministic single-entry behavior; no claim of replay protection |

Wire Protocol 1 currently has no payload-bearing supported opcode and no separate execution-error status beyond the validator-selected ACK statuses. The “different valid payload” and execution-error rows are forward-safety contracts for the transaction engine. The permanent TEST regression must still exercise a payload-distinct same-tuple frame: because TEST admits only zero bytes, that second frame is malformed and must receive `MALFORMED_PACKET` without consulting or changing the valid cache entry.

## 4. Native regression requirements

Add tests in `test/test_transaction_engine/test_main.cpp`; extend `test/test_protocol/test_main.cpp` only if a reusable validator contract changes. Tests should expose tracker state through behavior or a narrow deterministic query rather than raw private storage.

| Case | Setup and input sequence | Expected ACK/disposition | Expected duplicate state |
|---|---|---|---|
| 1. Malformed then valid TEST | Empty tracker; addressed COMMAND TEST with one payload byte at source/sequence/opcode tuple T; then canonical zero-payload TEST at T | First: `ACK_MALFORMED_PACKET`; second: `ACK_SUCCESS`, not `DUPLICATE` | First does not populate; second becomes the valid entry |
| 2. Valid then payload-distinct same tuple | Canonical zero-payload TEST at T; then TEST at T with length 1 and a chosen byte | First: `ACK_SUCCESS`; second: `ACK_MALFORMED_PACKET`, never cached SUCCESS | Original valid entry remains unchanged; malformed frame is not duplicate |
| 3. Malformed overwrite attempt | Cache valid TEST A; send malformed TEST B using A's tuple (and, separately, a different tuple); retransmit exact A | Malformed requests receive malformed ACK; final A receives cached SUCCESS as `DUPLICATE` | Neither malformed request replaces or influences A |
| 4. Exact retransmission | Send valid TEST A, then byte-for-byte canonical A | SUCCESS then duplicate SUCCESS generated from remembered status | One entry; no second execution or replacement |
| 5. Ignored/wrongly addressed | Cache valid A; send wrong destination, wrong sender, and ACK/ERROR packet variants; retransmit A | Each invalid variant ignored; A remains duplicate SUCCESS | Entry unchanged throughout |
| 6. Sequence rollover | Seed/cache a valid request at `0xFF`; exercise Hub `HubTransactionState` wrap to `0x00`; compare exact and payload-distinct Node requests at repeated sequence values | Exact current canonical match reuses result; any distinct canonical request does not | Behavior depends only on current single entry and exact identity, never stale partial tuple |

Where TEST cannot represent two distinct valid payloads, add a test-only supported-payload validator seam only if it does not alter production protocol behavior; otherwise state explicitly that the malformed payload-distinct TEST is the Wire Protocol 1 regression and test the tracker's exact byte comparison directly with constructed canonical packets. Do not add a production opcode merely to test the cache.

Existing transaction tests that must remain passing or be deliberately updated include duplicate state initialization, field mismatch, remembered-status reuse, ACK endpoint reversal and encoding, ignored packets not mutating state, duplicate packets not replacing state, Hub ACK matching, inclusive timeout, retry count/exhaustion, sequence advancement/wrap, and deadline wrap. Existing protocol malformed-input tests must remain passing.

Native coverage must also verify:

- unsupported opcode produces its current ACK but does not populate or replace duplicate state;
- payload comparison uses exactly the declared length and is deterministic at lengths 0 and 26;
- unused payload bytes cannot create false inequality for equal canonical requests;
- a hash/checksum, if added, cannot make unequal packets equal;
- exact duplicate ACK regeneration preserves source/destination reversal, sequence, opcode, one-byte status, and original result;
- receive-restoration outcome ownership in `src-rx/main.cpp` remains unchanged for ignored, malformed, new, and duplicate paths;
- retry and timeout behavior in `HubTransactionState` is unchanged.

The tests must prove both sides of F-01: semantic collisions are eliminated and legitimate retransmission idempotency remains intact.

### 7.3 Retry, timeout, duplicate, and restoration

- **Retry:** Temporarily prevent one ACK without changing firmware; verify the Hub retains the sequence/opcode, increments retransmission once per retry, and succeeds when the Node can answer.
- **Timeout:** Keep the Node unavailable through initial attempt plus two retries; verify 2,500 ms ACK windows, two retransmissions, terminal failure, one sequence advancement, degraded presentation, and continued scheduling.
- **Duplicate ACK regeneration:** Suppress the first ACK at the Hub side while allowing the Node to process the command, then allow the identical Hub retransmission. Verify the Node increments duplicates, does not increment accepted again, regenerates the original status ACK, and the Hub completes normally.
- **Receive restoration:** Temporarily remove Node power or interrupt the radio path, restore it without restarting the Hub, and verify a later scheduled transaction restores reachability. Also verify Node receive resumes after normal, duplicate, malformed, and ignored injection cases where the available injection fixture supports them.
- **Exact-result retention:** Using a controlled packet-injection harness or approved test firmware that does not become production behavior, cause a valid request result to be cached, retransmit the exact request, and verify the original result is returned without re-execution.
- **Payload distinction:** Using the same controlled harness, send valid TEST and a same-source/sequence/opcode TEST with a nonzero payload. Verify the second receives MALFORMED, never an unrelated cached SUCCESS, does not alter the valid cache, and exact retransmission of the original still returns SUCCESS.

The last two cases require packet control beyond the ordinary periodic Hub firmware. If no approved hardware injection mechanism exists, the native regression is the authoritative F-01 logic proof and the hardware limitation must be recorded; do not claim those physical cases passed.

## 9. Explicitly deferred authenticated-transport findings

The following findings remain documented requirements for the future authenticated-transport milestone, currently roadmap v0.9.0:

- **F-02 — Forgeable radio metadata treated as peer identity:** requires authenticated packet integrity and cryptographic peer identity.
- **F-03 — Repeated RF commands force ACK work:** primarily requires authentication-first silent discard, followed by response budgets and rate governance.
- **F-04 — Captured ACKs become valid after sequence reuse:** requires persistent authenticated freshness, replay windows, and defined reboot/storage-loss behavior.

These findings must not be patched piecemeal into Wire Protocol 1 during v0.5.1. The F-01 correction does not solve spoofing, authentication, RF denial of service, persistent replay, reboot freshness, sequence-wrap replay, or ACK capture. Source and device IDs remain unauthenticated routing identifiers.

## 10. Compatibility requirements and non-goals

Unless a discovered contradiction is separately reviewed, v0.5.1 must preserve:

- Wire Protocol version 1 and exact TEST/ACK encoding;
- six-byte header, 32-byte packet bound, and 26-byte payload bound;
- Hub/Node addressing and configured sender behavior;
- cached ACK regeneration for exact legitimate retransmissions;
- Hub retry, timeout, sequence, and scheduling semantics;
- Node 100 ms pre-ACK ordering and receive restoration;
- bounded, allocation-free operation and single-entry in-memory duplicate state;
- current public API and capability behavior;
- v0.5.0 capability registry, authorization, interlock, and fail-closed analog behavior;
- Configuration Schema 1 and existing configuration fixtures;
- current packet types and ACK statuses;
- no RF path into capability execution.

Explicit non-goals are:

- authenticated transport;
- encryption;
- persistent replay windows or freshness state;
- rate limiting;
- response budgets;
- protocol-version increment;
- unrelated capability work;
- broad transaction-engine refactoring;
- dependency upgrades merely because versions are being recorded or audited;
- new opcodes, packet types, Host Protocol behavior, or application commands;
- multi-Node, routing, repeater, store-and-forward, or mesh behavior.
