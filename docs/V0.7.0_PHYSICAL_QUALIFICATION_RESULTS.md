#### Step B — Hub boot and Host readiness inspection

Production Hub source calls `Serial.begin(115200)` first in `setup()`, followed
by `Serial.setTxTimeoutMs(0)` and disabled debug output. Host RX is not serviced
until `setup()` completes and `runtimeState.isReady()` is true. Before that
point, initialization performs 140 ms of explicit delay, OLED initialization,
settings/NVS loading, persistent Hub Event-ledger recovery, SPI initialization,
and `radio.begin(915.0)`. These OLED, NVS, and radio operations can extend the
readiness interval. A radio initialization failure leaves runtime not ready and
therefore leaves Host RX gated.

The production machine-stream build intentionally emits no unsolicited Host
bytes; version/radio prints are limited to text-stream or characterization
builds. An immediately issued HELLO can therefore arrive before foreground
Host service begins. However, source contains no intentional multi-second boot
delay, and the fixed 140 ms delay alone does not explain the original 10-second
timeout. Normal buffering would also be expected to preserve already received
Host bytes until the loop services them. Immediate post-flash readiness was a
plausible variable but was not sufficient by source inspection alone to assign
the failure.

#### Step C — passive safe-open check

The first local passive-check command had a Python quoting syntax error. It
exited before importing or opening the serial device, transmitted no bytes,
and produced no hardware evidence. This procedural failure was corrected
without changing the intended diagnostic.

The corrected check directly reused
`tools.host_reference.redline_host.open_serial_transport()`. It constructed the
serial object closed, disabled software/hardware flow control, set DTR and RTS
inactive before opening, transmitted no Host bytes, observed for approximately
three seconds, and closed the stream. Open succeeded and pyserial reported DTR
and RTS false both immediately after open and immediately before close.

Contrary to the intended passive behavior, the read returned 265 bytes of an
ESP-ROM boot banner. The decisive decoded banner fields were:


#### Diagnostic disposition

**STOPPED — unexpected MCU reset during the passive safe-open check.** The
smallest proven boundary is below REDLINE Host request parsing: no application
bytes were transmitted, yet opening Linux `cdc_acm` produced an ESP-ROM
`USB_UART_CHIP_RESET`. This makes the USB CDC/host-driver/open boundary the
leading owner and provides a concrete mechanism capable of explaining the
initial HELLO loss: the first request may have been written while the MCU was
resetting or before USB/firmware Host service recovered. That causal sequence
has not been directly proven because the mandated stop prevented the controlled
retry.

Historical v0.6 qualification investigated a different symptom in the older
Arduino framework: application TX was accepted by HWCDC but not delivered to
the PC. The current evidence instead shows an open-associated chip reset before
any Host request, despite the current Arduino-ESP32 3.3.9 framework and the
safe-open control-line state. The earlier framework migration therefore does
not dispose this Linux open/reset observation.

The next smallest experiment should be a separately authorized, read-only
host/USB control-path capture around exactly one passive safe open (kernel USB
and `cdc_acm` events plus USB control requests), with no Host payload. Its goal
would be to determine which open-time control request causes
`USB_UART_CHIP_RESET` and whether Linux driver behavior differs from the
pyserial-visible DTR/RTS state. A controlled HELLO retry should not occur until
that reset behavior is understood or an approved reset-aware readiness
procedure is defined.

#### Exact open ordering and competing mechanism

`redline_host.py:393` constructs `serial.Serial()` closed, sets baud/read/write
timeouts, disables `xonxoff`, `rtscts`, and `dsrdtr`, sets `dtr=False` and
`rts=False`, assigns the port, and calls `.open()` exactly once. These property
assignments do not issue hardware requests while the object is closed.

The installed POSIX `.open()` implementation then performs this sequence:

1. `os.open(port, O_RDWR | O_NOCTTY | O_NONBLOCK)`;
2. `tcgetattr` and `tcsetattr(TCSANOW)` to configure raw serial operation;
3. a separate `TIOCMBIC` clearing `TIOCM_DTR`;
4. a separate `TIOCMBIC` clearing `TIOCM_RTS`;
5. `tcflush(TCIFLUSH)` and pipe setup, then marks the Python object open.

The `dtr` and `rts` getters return stored Python state, not a measurement of all
previous USB transfers. Also, the POSIX backend tolerates EINVAL/ENOTTY from
control updates; neither failure is known to have occurred here. It does not
explicitly modify HUPCL, so its actual inherited value needs trace evidence.
The previous statement that DTR/RTS remained false establishes logical API
state at sampled times, not absence of intermediate bus-level assertions.

External upstream Linux source shows nonblocking tty opening can raise both
lines when the existing baud is nonzero; the ACM driver translates raising
both to a CDC `SET_CONTROL_LINE_STATE` request. This is source comparison, not
an observed execution trace of Kali's exact patched 7.1.5 binary.
[TTY source](https://github.com/torvalds/linux/blob/master/drivers/tty/tty_port.c),
[ACM source, v7.1](https://raw.githubusercontent.com/torvalds/linux/v7.1/drivers/usb/class/cdc-acm.c).

The strongest predicted USB sequence is therefore:

| Predicted point | CDC bitmap | DTR | RTS | Consequence to test |
|---|---:|---:|---:|---|
| Kernel tty open asserts both | `0x0003` | 1 | 1 | Not visible in the cached false properties |
| pyserial clears DTR first | `0x0002` | 0 | 1 | Candidate USB Serial/JTAG reset-triggering intermediate state |
| pyserial clears RTS second | `0x0000` | 0 | 0 | Both logical and bus state finally inactive |

**These three transfers have NOT been captured.** The installed kernel header
`include/uapi/linux/usb/cdc.h` confirms `SET_CONTROL_LINE_STATE=0x22`,
`SET_LINE_CODING=0x20`, DTR bit 0 and RTS bit 1. pyserial explicitly documents
that OS/driver activation during open can produce a control-line glitch even
with inactive requested states.
[pyserial open documentation](https://pyserial.readthedocs.io/en/latest/pyserial_api.html#serial.Serial.open).

#### ESP32-S3 meaning and historical comparison

The repository board definition `boards/heltec_wifi_lora_32_V4.json` sets
`ARDUINO_USB_MODE=1` and `ARDUINO_USB_CDC_ON_BOOT=1`. Together with the installed
`HardwareSerial.h`, these select `HWCDC` over the built-in USB Serial/JTAG
peripheral. The repository variant supplies VID/PID and GPIO assignments; it
does not implement the USB reset handshake. This is distinct from a
programmable TinyUSB CDC stack or an external USB-UART adapter.

The actual bundled ESP32-S3 ROM and SoC headers define reason 21 (`0x15`) as
`USB_UART_CHIP_RESET` / `RESET_REASON_CORE_USB_UART`: the USB UART path reset the
digital core. Despite the ROM label's word CHIP, the header describes a core
reset. Separate reasons exist for USB JTAG (`0x16`), software, watchdog, power,
and brownout resets. A USB-UART core reset is not itself proof of a USB bus
reset, an external EN pulse, or a tty re-enumeration. Inspected `HWCDC.cpp`
handles a USB BUS_RESET interrupt by updating transport state; that handler
does not call a software MCU restart.

Espressif's ESP32-S3 TRM, section 33.4.2 and tables 33.4-3/33.4-4, documents the
virtual RTS/DTR reset mechanism, including the RTS=1/DTR=0 reset state. It also
describes Windows drivers that defer propagating DTR until RTS is set. That
provides a plausible reason separate POSIX clears could behave differently
from the previously successful Windows safe-open sequence; it does not prove
which transfers the historical Windows machine sent.
[Espressif TRM](https://documentation.espressif.com/esp32-s3_technical_reference_manual_en.pdf).

Historical Section 21 records genuine Windows open/reset remediation; Section
26 records the separate HWCDC accepted-write-but-no-delivery issue. Both are
relevant precedents, but neither supplies this Linux trace. No claim is made
that all three failures share one mechanism.

The earlier 265-byte ROM banner reports the reset reason of the boot producing
those bytes. Its observation alone did not timestamp the triggering reset or
exclude previously buffered boot output. The proposed trace must correlate a
fresh USB control sequence with the first received ROM bytes before asserting
open-time causality. This qualification of the earlier interpretation does not
erase its observation or the original FAIL.

Source establishes the expiry condition. Every durable QUEUED Event receives

or less is committed EXPIRED. Expiry can therefore preempt TX, admission wait,
or backoff and does not require five attempts.

remaining-seconds field is zero.
