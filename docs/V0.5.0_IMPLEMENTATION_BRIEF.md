# ARGUS REDLINE v0.5.0 Implementation Brief

**Status:** Implementation plan; v0.5.0 production implementation has not started.

**Planned release:** `v0.5.0` — Capability Registry and Safe Hardware Abstraction

**Baseline:** Firmware `v0.4.0`; Wire Protocol `1` remains unchanged unless a later explicit compatibility decision approves otherwise.

## 1. Release objective

Give each device a bounded, inspectable registry of approved local hardware capabilities, stable logical IDs, typed local operations, validation, authorization hooks, safety/interlocks, and profile-owned handlers. The firmware describes what approved hardware can do without embedding application meaning or exposing unrestricted GPIO.

v0.5.0 proves local capability semantics and one low-risk input/output/analog slice. It does not add operational LoRa capability commands, Host Protocol, or application workflows.

## 2. Baseline invariants

The implementation must preserve:

- Existing `TEST` command and sequence-matched ACK bytes and behavior.
- Hub transmit, retry-delay, ACK-wait, timeout, and sequence timing ownership.
- Node receive readiness, validation ordering, single-entry in-memory duplicate suppression, ACK regeneration from cached transaction metadata and status, and receive restoration.
- v0.4.0 settings validation, dual-slot persistence, repair/reset behavior, editor, and role-safe write points.
- Six-screen navigation, input timing, display timeout/wake suppression, and radio/UI independence.
- Hub `0x01` and Node `0x10` role identities unless separately configured through existing build authority.
- Wire Protocol `1`, existing packet types, six-byte header, maximum packet size, opcode `TEST=0x64`, and ACK statuses.
- Fixed-size embedded data, bounded synchronous handlers, no uncontrolled heap allocation, and no background task.
- No new blocking capability delay that interferes with radio ownership, ACK handling, UI responsiveness, or role scheduling; existing deliberate role timing, including the Node's approximately 100 ms pre-ACK delay, remains unchanged.

Capability failure must not prevent radio-capable startup. No capability code may write settings, own transport state, or execute from ISR context.

## 3. Scope

v0.5.0 includes:

- Capability class vocabulary and compatibility validation.
- Opaque stable logical capability IDs.
- Exact fixed-size descriptor and typed value/result proposals.
- Immutable profile registry, deterministic enumeration, and bounded lookup.
- Local operation/class/type/range validation.
- Separate authorization and safety/interlock policy contracts.
- Bounded handler dispatch through profile-owned bindings.
- Simulated-first DIGITAL_INPUT, ANALOG_INPUT, and INDICATOR_OUTPUT slice.
- Heltec V4 profile integration without exposing raw pins.
- Capability-specific diagnostics and a bounded UI summary only if approved.
- Native model/dispatch tests, two production builds, physical low-risk validation, and full v0.4.0 regression.

The roadmap behaviors `GET_CAPABILITIES`, `READ_INPUT`, `READ_SENSOR`, `SET_INDICATOR`, and `TRIGGER_OUTPUT` are names for local semantic enumeration/describe/read/set/trigger contracts and validation behavior only. They do not become LoRa opcodes, packet schemas, or Host Protocol commands in this milestone. v0.6.0 owns formal operation registration and radio-visible structured commands/responses.

## 4. Exact non-goals

- Arbitrary GPIO access, arbitrary pin-number commands, or a generic pin API.
- General remote code execution, uploaded/transferred procedures, or dynamic plugin loading.
- Runtime registration from radio, serial, UI, settings, or other untrusted input.
- Heap-owned registry entries, strings as descriptor state, unrestricted callbacks, or a generic event bus.
- Hazardous actuators, real relay-controlled external power, motors, servos, or PWM control.
- Mesh, routing, repeaters, store-and-forward, or multi-Node implementation.
- Host Protocol, a serial command console, structured REQUEST/RESPONSE radio operations, or any silent Wire change.
- Security/provisioning redesign or a claim of cryptographic authorization.
- Settings transfer over LoRa, persistent capability descriptors, user-created capabilities, or per-capability settings.
- Firmware-owned human meanings, workflows, databases, orchestration, sensor interpretation, or high-level application policy.
- v0.6.0 implementation.

## 5. Capability classes

The proposed `uint8_t` class vocabulary is defined precisely in [V0.5.0_CAPABILITY_MODEL.md](V0.5.0_CAPABILITY_MODEL.md).

| Class | Defined now | Physically implemented in v0.5.0 | Disposition |
|---|---|---|---|
| `DIGITAL_INPUT` | Yes | Preferred | Owner-safe input snapshot |
| `ANALOG_INPUT` | Yes | Preferred | Safe verified external source |
| `SENSOR` | Yes | No | Reserved for a concrete sensor |
| `INDICATOR_OUTPUT` | Yes | Preferred | Existing arbitration or simulated |
| `SIGNAL_OUTPUT` | Yes | No | Reserved |
| `RELAY_OUTPUT` | Yes | No | Reserved; no external power |
| `POWER_MONITOR` | Yes | No | Reserved |
| `LOCATION_PROVIDER` | Yes | No | Reserved |
| `LOCAL_STORAGE` | Yes | No | Reserved; never raw storage access |
| `LOCAL_PROCEDURE` | Vocabulary only | No | Descriptor shape only by default; never transferred code |

Defining an enum member does not register, authorize, or implement it.

## 6. Capability identity model

Recommend `using CapabilityId = uint16_t`, with `0x0000` invalid. Sixteen bits are enough for small profile-local registries while keeping descriptors compact. IDs are deterministic compile-time assignments, nonzero, unique within one device/profile, and stable for that hardware profile. They are never GPIO numbers and are not globally unique identities; the addressing context is `(device ID, capability ID)`.

Class-like ranges such as `0x01xx`, `0x02xx`, and `0x03xx` may improve human review, but code must treat IDs as opaque and read class from the descriptor. No runtime allocator or remote registrar exists.

## 7. Capability descriptor

The proposed pointer-free descriptor is exactly 20 bytes:

```cpp
struct CapabilityDescriptor {       // proposed exact size: 20 bytes
    CapabilityId id;                 // 2
    CapabilityClass capabilityClass; // 1
    uint8_t operationFlags;          // 1
    ValueType valueType;             // 1
    uint8_t authorizationPolicyId;   // 1
    uint8_t safetyPolicyId;          // 1
    uint8_t unitCode;                // 1
    uint16_t metadataFlags;          // 2
    uint16_t reserved;               // 2, must be zero
    uint32_t minimumBits;            // 4
    uint32_t maximumBits;            // 4
};
static_assert(sizeof(CapabilityDescriptor) == 20);
```

| Field | Type / bytes | Meaning | Allowed values and ownership |
|---|---:|---|---|
| Logical ID | `uint16_t` / 2 | Profile-local identity | Nonzero, profile-owned, stable |
| Class | enum `uint8_t` / 1 | Capability category | Known class only; model-owned vocabulary |
| Operation flags | `uint8_t` / 1 | Advertised local operations | `DESCRIBE`, `READ`, `SET`, `TRIGGER`, `RUN`; reserved bits zero |
| Value type | enum `uint8_t` / 1 | Input/output representation | Known fixed type and compatible with class |
| Authorization policy | `uint8_t` / 1 | Compiled policy selector | Known local policy ID |
| Safety policy | `uint8_t` / 1 | Compiled interlock selector | Known local policy ID |
| Unit code | `uint8_t` / 1 | Machine-readable unit category | Bounded enum; no label/string |
| Metadata flags | `uint16_t` / 2 | `0x0001` means simulated/test fixture; all other bits initially zero | Must not duplicate operation support; `READ` is authoritative for readability |
| Reserved | `uint16_t` / 2 | Extension space | Zero in v0.5.0 |
| Minimum bits | `uint32_t` / 4 | Inclusive lower-bound bit pattern interpreted by value type | Profile supplies; dispatcher performs type-specific comparison |
| Maximum bits | `uint32_t` / 4 | Inclusive upper-bound bit pattern interpreted by value type | Profile supplies; dispatcher performs type-specific comparison |

Implementation must use `static_assert(sizeof(CapabilityDescriptor) == 20)` and explicit field validation. Descriptors contain no raw pins, pointers, labels, application names, callbacks, or mutable state. Any later serialized representation must be independently encoded rather than copying compiler memory.

Compatibility rule: an unknown class, type, policy ID, unit, metadata bit, operation bit, nonzero reserved field, or invalid range rejects that descriptor/registry before dispatch.

Bounds use deterministic `valueType` interpretation:

- `NONE`: both bounds are zero.
- `BOOLEAN`: unsigned bounds are within `0..1`.
- `UNSIGNED_32`: bounds and value use full unsigned comparison.
- `SIGNED_32`: bounds and value are reinterpreted as `int32_t` and compared signed.
- `NORMALIZED_U16`: upper 16 bits are zero and the unsigned range is within `0..65535`.
- `FIXED_Q16_16`: bounds and value are reinterpreted as signed `int32_t` Q16.16.
- `ENUM_U16`: upper 16 bits are zero; numeric bounds apply and the profile validates actual enum members.

The dispatcher selects comparison semantics explicitly from `valueType` and never relies on implicit mixed signed/unsigned arithmetic.

## 8. Operation model

Local operation categories are `ENUMERATE`, `DESCRIBE`, `READ`, `SET`, `TRIGGER`, and `RUN_LOCAL_PROCEDURE`. `ENUMERATE` is registry-level and invokes no handler. `DESCRIBE` returns a bounded descriptor snapshot and invokes no handler. Every descriptor must advertise `DESCRIBE`. `READ`, `SET`, `TRIGGER`, and `RUN_LOCAL_PROCEDURE` are dispatchable capability operations and require the descriptor to advertise the corresponding flag.

`ENUMERATE` and `DESCRIBE` do not use the descriptor hardware `valueType` as an input/output contract. A future exposure layer may independently restrict discovery, but that is not v0.5.0 hardware dispatch policy.

- Inputs/sensors/monitors/providers support `READ`.
- Indicator outputs support `SET`, and may support `READ` only if state is meaningful.
- Signal/relay outputs remain unregistered; later review may permit `SET`/`TRIGGER`.
- LOCAL_PROCEDURE remains descriptor-only by default; `RUN_LOCAL_PROCEDURE` is not exposed remotely.

For dispatchable operations, lookup, operation support, type, range, authorization, and interlock validation occur in that order before handler execution. `READ` passes applicable profile authorization and safety/interlock policy before reading hardware. Unsupported class/operation combinations never reach board code.

## 9. Typed value and result model

Recommend an 8-byte `CapabilityValue`: one `ValueType`, three zero reserved bytes, and one tagged `uint32_t` payload. Proposed types are `NONE`, `BOOLEAN`, `UNSIGNED_32`, `SIGNED_32`, `NORMALIZED_U16`, `FIXED_Q16_16`, and `ENUM_U16`. Floats, strings, buffers, pointers, and ownership transfer are excluded.

Boolean is exactly 0/1. Normalized and enum values use the low 16 bits with upper bits zero. Fixed Q16.16 is used only when a real sensor justifies it. Descriptor bounds validate set/request values before dispatch.

Recommend a 12-byte `OperationResult`: one `OperationStatus`, three zero reserved bytes, and one `CapabilityValue`. Statuses are `OK`, `CAPABILITY_NOT_FOUND`, `UNSUPPORTED_OPERATION`, `INVALID_VALUE_TYPE`, `VALUE_OUT_OF_RANGE`, `UNAUTHORIZED`, `INTERLOCK_ACTIVE`, `HARDWARE_UNAVAILABLE`, `OPERATION_FAILED`, `BUSY`, and `INVALID_DESCRIPTOR`.

The local operation result is distinct from transport success/ACK. A successful hardware value is valid only with `OK`; denial/failure status remains explicit. Encoding is deterministic and allocation-free. v0.6.0 must separately define any wire representation.

## 10. Registry model

Use a static immutable descriptor array plus a bounded count/view, with recommended maximum 16 entries per profile. This is simpler than a template registry and adequate for deterministic linear lookup. Dynamic provider or RMP registration is not part of v0.5.0.

All consumers use bounded enumeration and lookup APIs that copy descriptor snapshots; they do not access the backing table directly or retain descriptor pointers. Capability IDs are opaque logical IDs. Callers must not infer class, permanence, hardware origin, or provider from an ID or profile range, and must tolerate lookup failure on every independent operation. These rules keep v0.5.0 static while allowing a future composite or dynamic RMP provider to reuse the same ID, descriptor, validation, authorization, value, result, and dispatch abstractions without replacing the higher-level model. They do not implement RMP or dynamic registration in v0.5.0.

Registry validation checks capacity, null/count consistency, duplicate/nonzero IDs, descriptor fields, class/flag/type combinations, bounds, policies, and reserved values. Enumeration preserves profile table order and copies one descriptor into caller-owned storage. Lookup performs bounded linear search. No pointer to mutable table state escapes, and no radio/UI/settings input can mutate the table.

Invalid registry state disables capability operations, increments a capability validation diagnostic, and leaves radio initialization able to continue in a degraded state.

## 11. Handler binding

Compared approaches:

- Tagged profile switch: smallest surface but hard to fake if directly embedded in policy.
- Fixed function table: testable but broadens function-pointer/callback compatibility risk.
- Narrow interface: one borrowed handler object with one virtual execute method.

Recommend the narrow interface. Pure dispatch uses virtual dispatch through a borrowed `LocalCapabilityHandler&` with no RTTI requirement. Implementations are static- or stack-owned; there is no allocation, ownership transfer, or handler pointer in a descriptor. Simulated handlers are development/test fixtures for model, registry, policy, dispatch, and integration validation; they must not remain registered as production release capabilities unless an explicitly test-only build documents that behavior. Production registration corresponds only to approved hardware/profile behavior. The Heltec profile implementation switches privately on logical ID and owns pins, polarity, ADC configuration, initialization, and physical calls.

### Local invocation and scheduling boundary

Dispatch is synchronous at the pure capability-model layer, but role firmware exclusively owns when a production-local operation may execute. A handler must never be invoked from ISR context, renderer/UI callbacks, raw button callbacks, protocol decode logic, or transaction-engine internals. Hub execution is admitted only at an existing transaction/radio-safe state. Node execution remains subordinate to receive, validation, ACK generation/transmission, duplicate handling, and receive-restoration ownership. Hardware work must be bounded, add no blocking capability delay to required radio/UI scheduling, and return failures without destabilizing radio operation. One approved local invocation produces at most one dispatch.

v0.5.0 does not invent a radio opcode, Host Protocol feature, generic serial maintenance console, permanent UI command, or generic event queue to create invocations. A separately approved temporary local validation path or validation build may invoke the physical slice during characterization; it is test scaffolding, not a production API commitment, and must be absent from the production release configuration.

This is one test seam, not an inheritance hierarchy, plugin API, or event bus. Unknown IDs and handler failures return statuses rather than falling through to arbitrary hardware.

## 12. Authorization and safety

Authorization and safety are independent local gates:

1. **Authorization:** may this locally supplied caller context perform this operation on this capability?
2. **Safety/interlock:** is execution safe now according to compiled local state/policy?

The initial caller context may distinguish firmware-local, UI-local, test, and future-remote contexts. It is not cryptographic authentication, and documentation must not imply otherwise.

Deterministic pre-handler denials include not found, unsupported operation, invalid type, out of range, unauthorized, and interlock active. Handler/runtime results include hardware unavailable, operation failed, and busy. Tests must prove a denied request never calls the handler.

## 13. First complete vertical slice

### DIGITAL_INPUT

Prefer the GPIO0 user button only through a stable snapshot/API owned by DeviceInput. Capability code must not poll, debounce, configure, or generate UI events. If a suitable snapshot cannot be exposed without coupling, use a simulated handler first and then a separately verified input pin/switch.

### INDICATOR_OUTPUT

Represent a dedicated logical application-indicator request. Feed it into existing nonblocking LED arbitration so radio/ACK indication, button feedback, master LED enable, and capability request remain separately owned. Never write the built-in LED pin directly from capability dispatch. If arbitration cannot remain clear, retain a simulated handler or validate a separate external LED.

### ANALOG_INPUT

Start simulated. Hardware preparation must verify a board-safe ADC pin from the current board definition/schematic and confirm no existing owner. Use a bounded external divider/potentiometer, enforce voltage limits, and return raw or `NORMALIZED_U16`. No caller selects a pin or ADC parameters.

No relay or external-power control is permitted.

## 14. Hardware profile boundary

General capability code contains no Heltec pin number. A likely `heltec_v4_capabilities` adapter privately owns:

- Profile-local ID constants and descriptor table.
- Pin/channel assignments and active-high/active-low polarity.
- ADC attenuation, bounds, normalization, and initialization.
- DeviceInput snapshot access and LED arbitration requests.
- Handler implementation and profile policy selection.

The profile must expose only descriptor/handler contracts to capability policy. GPIO ownership conflicts are review blockers.

## 15. Runtime diagnostics and UI

Add separate bounded capability-owned counters/state only after ownership review: lookups, accepted operations, denials, unsupported operations, validation failures, interlock denials, busy outcomes, and hardware failures. RuntimeState may receive a bounded copied summary for approved diagnostics/presentation, but it does not own the registry or authoritative capability state. DeviceUi receives presentation snapshots only and owns no descriptors, handlers, registry state, or dispatch. Do not inflate radio counters, let diagnostics change dispatch results, or generalize the settings request queue into a capability event system.

Default UI recommendation: extend DEVICE or ABOUT with a bounded registered-count and last capability status snapshot. Do not add a full browser or another screen unless Step 11 review demonstrates a clear need. Capability operations must not wake the display through radio-generated dirty state, block rendering, or change navigation.

## 16. Persistence boundary

The registry, descriptors, raw pins, bindings, policies, and capability runtime state are compiled into the hardware profile. They never enter namespace `redline`, `cfg_a`, `cfg_b`, or `rst_pend`. Ordinary settings remain the sole v0.4.0 persistence model. Future per-capability settings require a separately versioned schema and authority design.

## 17. Wire and host boundary

No arbitrary GPIO value enters Wire Protocol `1`. Local APIs may enumerate, describe, read, set, trigger, and dispatch in tests and explicitly scheduled production-local code, but no new packet behavior is implied.

v0.5.0 may document local semantic operation IDs only. `GET_CAPABILITIES`, `READ_INPUT`, `READ_SENSOR`, `SET_INDICATOR`, and `TRIGGER_OUTPUT` remain internal contracts. v0.6.0 owns the formal opcode/payload registry, REQUEST/RESPONSE distinction, Host Protocol 0.1, USB/serial development console, and PC → Hub → Node → capability → response → PC slice. Any Wire change requires explicit compatibility review and deliberate approval.

## 19. Test strategy

Native tests must cover:

- Every descriptor field, valid descriptor, reserved values, and exact-size assertions.
- Invalid class/type/flag combinations and invalid bounds/policies/metadata, including every type-specific bound rule and full-range `UNSIGNED_32`.
- Empty, full, and over-capacity registries; zero, duplicate, and missing IDs.
- Deterministic enumeration and lookup without mutable table exposure.
- Registry-only ENUMERATE, snapshot-only DESCRIBE, dispatchable operations, type mismatch, range failure, and malformed tagged values.
- Authorization and interlock denial ordering; handler never called after denial.
- Hardware unavailable, operation failure, busy, exact handler count, and structured result propagation.
- Every value/status representation and deterministic local encoding helper, if one exists.
- Hub/Node/profile composition, simulated flags, and absence of arbitrary pin fields/arguments.
- Diagnostics saturation and isolation from radio counters.

Integration regression must prove settings and editor behavior unchanged; input/UI remain nonblocking; Hub TEST/ACK/retry timing remains unchanged; Node validation, single-entry in-memory duplicate suppression, ACK regeneration from cached transaction metadata and status, ACK ordering, and receive restoration remain unchanged; Wire Protocol remains `1`; and both builds remain bounded. No exact-output fixture may be weakened.

## 20. Physical validation summary

Follow [V0.5.0_HARDWARE_VALIDATION_PLAN.md](V0.5.0_HARDWARE_VALIDATION_PLAN.md). Start with simulated handlers, then prove singular-owner digital input, arbitration-safe indicator, and a verified bounded analog source. Exercise capability actions during normal TEST/ACK and observe at least 30 clean post-action exchanges. Record failures and deferred items; do not call this endurance testing.

## 21. Risks and unresolved decisions

| Decision | Recommended default before implementation |
|---|---|
| Capability ID width | `uint16_t`, opaque and profile-local |
| Descriptor layout | Proposed 20-byte pointer-free layout with `uint32_t` bound bit patterns, explicit type-directed comparison, and static assertion |
| Units | Small numeric `unitCode`; no strings/conversion framework |
| Binding | One borrowed narrow handler interface; profile-private ID switch |
| GPIO0 ownership | Read DeviceInput-owned snapshot only; otherwise use another verified input/simulation |
| Built-in LED ownership | Application request through current OR arbitration; otherwise simulate/separate LED |
| ADC pin/range | Unresolved until repository board definition and schematic review; never infer from memory |
| OLED | One DEVICE/ABOUT summary only if approved; no browser by default |
| LOCAL_PROCEDURE | Vocabulary/descriptor shape only; no production registration by default |
| Internal operation numbers | Local enum only; no Wire opcode reservation before v0.6.0 |
| Production invocation | Role-scheduled only at existing safe ownership points; temporary validation path is test scaffolding, not a production API |

Implementation must pause for review if any recommended default changes descriptor compatibility, physical ownership, transport behavior, or milestone scope.

## 22. Release gate

```text
[ ] Node/profile reports registered capabilities through a bounded local tested API
[ ] Unsupported or missing capabilities are rejected before handler execution
[ ] Logical capability IDs are used instead of arbitrary GPIO numbers
[ ] Input/sensor values are returned through the structured typed result model
[ ] One approved low-risk indicator output is controlled through established ownership
[ ] Local authorization can deny an operation before handler execution
[ ] Local safety/interlock policy can deny an operation before handler execution
[ ] Radio and UI remain responsive during bounded hardware operations
[ ] No arbitrary GPIO, runtime registration, dynamic plugin, or transferred-code path exists
[ ] Wire Protocol 1, TEST/ACK bytes, timing, retries, and duplicate behavior remain unchanged
[ ] Physical DIGITAL_INPUT/INDICATOR_OUTPUT/ANALOG_INPUT slice passes where bindings are approved
[ ] No relay, hazardous actuator, or external-power control is connected
[ ] Software and physical evidence clearly identify deferred characterization
```

Unperformed fault injection, exact collision testing, or extended endurance remains deferred characterization rather than an implicit release failure unless a later approved gate explicitly requires it.

## 24. Definition of done

v0.5.0 is done when an immutable validated registry describes approved profile-local capabilities by logical ID, local operations are type/range/authorization/interlock checked before a bounded handler, and a low-risk physical slice passes without regressing v0.4.0 radio, UI, or settings behavior.

It does not prove Host Protocol, radio capability operations, cryptographic authorization, persistent capability configuration, transferred procedures, hazardous outputs, multiple Nodes, routing, mesh, or application workflows. Those boundaries remain explicit, with structured operations and the PC-to-capability path assigned to v0.6.0.
