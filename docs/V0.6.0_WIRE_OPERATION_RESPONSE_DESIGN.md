# ARGUS REDLINE v0.6.0 Wire Operation and Response Design

**Status:** Normative v0.6.0 design; implementation NOT STARTED

**Wire decision:** Wire Protocol 1 — v0.6 additive extension

## 1. Decision and compatibility

v0.6 retains Wire Protocol 1. It does not change the six-byte header, field
ordering, packet-type values already assigned, maximum packet size of 32 bytes,
`TEST=0x64`, or existing ACK encodings. It assigns previously unused packet
type and opcode values. This is additive under the roadmap compatibility rule:
old Nodes reject new opcodes with the existing unsupported result, and old Hubs
ignore an unknown RESPONSE type. No existing encoded byte gains a new meaning.

`RESPONSE=0x04` is added to existing `COMMAND=0x01`, `ACK=0x02`, and
`ERROR=0x03`. The encoded Wire version remains integer `VERSION=1`; there is
no on-wire Wire minor-version field and this extension is not named Wire
Protocol 1.1.

`PING=0x20` is the bounded compatibility probe. A Hub MAY emit v0.6 PING before
extension support is known. A legacy Wire Protocol 1 Node returns the existing
one-byte ACK status `UNSUPPORTED_OPCODE=0x01`; that result establishes that
v0.6 structured operations are unavailable from that peer. A v0.6-capable
Node admits PING, returns ACK `SUCCESS=0x00`, and then returns RESPONSE. After
that successful discovery, the Hub may use other v0.6 operations according to
policy. Explicit configuration MAY instead establish extension support. v0.6
adds no feature bitmap, discovery packet type, or negotiation subsystem.

Mixed-version tests MUST prove this bootstrap and safe rejection/ignore
behavior. Any future change to the header, existing values, or incompatible
payload interpretation requires a Wire version decision.

Wire Protocol 1 remains unauthenticated. This extension is not cryptographic
identity, authorization, freshness, or replay protection.

## 2. Bounds and common encoding

The existing packet geometry remains:

```text
type/version, source, destination, sequence, opcode, payload length, payload
```

Maximum packet size is 32 bytes, so payload is 0..26 bytes. Multi-byte values
are little-endian. Every reserved byte/value MUST be zero. Wire/command
admission and exact structural validation—including length, schema, known enum
encoding, and target-field geometry—MUST complete before duplicate lookup or
mutation. Capability lookup, authorization, operation-specific value/range and
policy validation, interlock evaluation, hardware availability, and handler
execution occur only after an admitted request is reserved and acknowledged.

Structured request payload:

```text
target ID      uint16_t
value type     uint8_t
value length   uint8_t
value          0..22 bytes
```

Structured response payload:

```text
result code    uint8_t
target ID      uint16_t
value type     uint8_t
value length   uint8_t
value          0..21 bytes
```

`NONE=0x00`, `BOOLEAN=0x01`, `UNSIGNED_32=0x02`, `SIGNED_32=0x03`,
`NORMALIZED_U16=0x04`, `FIXED_Q16_16=0x05`, and `ENUM_U16=0x06`, with the
same exact lengths and field-wise encoding as Host Protocol 0.1.
`STRUCTURE=0x7F` is response-only and may carry only a fixed record defined
below; it is not an arbitrary byte-buffer capability type. Capability
results and device-operation results use the existing v0.5 `OperationStatus`
numeric authority:

| Value | `OperationStatus` |
|---:|---|
| `0x00` | `OK` |
| `0x01` | `CAPABILITY_NOT_FOUND` |
| `0x02` | `UNSUPPORTED_OPERATION` |
| `0x03` | `INVALID_VALUE_TYPE` |
| `0x04` | `VALUE_OUT_OF_RANGE` |
| `0x05` | `UNAUTHORIZED` |
| `0x06` | `INTERLOCK_ACTIVE` |
| `0x07` | `HARDWARE_UNAVAILABLE` |
| `0x08` | `OPERATION_FAILED` |
| `0x09` | `BUSY` |
| `0x0A` | `INVALID_DESCRIPTOR` |

Each operation MAY constrain which of these statuses it can validly return.
Undefined result-code values, or a defined status prohibited by the operation
schema, are malformed. No second response-status registry is created.

## 3. Operation registry

| Opcode | Operation | Request | Successful response | Remote v0.6 baseline |
|---:|---|---|---|---|
| `0x20` | `PING` | target 0; NONE | `UNSIGNED_32` uptime snapshot | allowed |
| `0x21` | `GET_DEVICE_INFO` | target 0; NONE | bounded fixed device-info record | allowed |
| `0x22` | `GET_STATUS` | target 0; NONE | bounded fixed status record | allowed |
| `0x23` | `GET_CAPABILITIES` | target 0; optional `UNSIGNED_32` cursor | bounded page | allowed |
| `0x24` | `DESCRIBE_CAPABILITY` | capability ID; NONE | bounded descriptor summary | allowed |
| `0x25` | `READ_CAPABILITY` | capability ID; NONE | typed value | policy-permitted read |
| `0x26` | `SET_INDICATOR` | capability ID; BOOLEAN | status, no value | production REMOTE disabled |
| `0x27` | `RUN_PROCEDURE` | registered procedure ID; bounded typed argument or NONE | status/typed result | production REMOTE disabled |
| `0x28` | `GET_DIAGNOSTICS` | target 0; optional cursor | bounded page | allowed |
| `0x64` | `TEST` | existing zero-byte schema | existing ACK only | unchanged |

Fixed `STRUCTURE` records are:

```text
DEVICE_INFO (8 bytes)
firmware major:u8, minor:u8, patch:u8, Wire:u8, Schema:u8,
hardware profile:u8, role:u8, device ID:u8

STATUS (10 bytes)
status flags:u16, uptime seconds:u32, retry count:u16,
timeout count:u16

CAPABILITY_PAGE (3 + 2*N bytes, N=0..9)
next cursor:u16 (0xFFFF=end), count:u8, capability IDs[N]:u16

CAPABILITY_DESCRIPTION (6 bytes)
class:u8, value type:u8, operation flags:u8, unit:u8,
availability:u8 (0=unavailable, 1=available), reserved:u8=0

DIAGNOSTIC_PAGE (2 + 5*N bytes, N=0..3)
next cursor:u8 (0xFF=end), count:u8,
entries[N] { metric ID:u8, saturating value:u32 }
```

Status flag bits are `READY=0x0001`, `RADIO_OPERATIONAL=0x0002`,
`TRANSACTION_ACTIVE=0x0004`, `DEGRADED=0x0008`, and `ERROR=0x0010`; bits
`0xFFE0` are zero. Counters saturate at `0xFFFF` in this record.

Descriptor class values reuse the exact v0.5 assignments: `INVALID=0x00`,
`DIGITAL_INPUT=0x01`, `ANALOG_INPUT=0x02`, `SENSOR=0x03`,
`INDICATOR_OUTPUT=0x04`, `SIGNAL_OUTPUT=0x05`, `RELAY_OUTPUT=0x06`,
`POWER_MONITOR=0x07`, `LOCATION_PROVIDER=0x08`, `LOCAL_STORAGE=0x09`, and
`LOCAL_PROCEDURE=0x0A`. Operation-flag bits are `DESCRIBE=0x01`,
`READ=0x02`, `SET=0x04`, `TRIGGER=0x08`, and
`RUN_LOCAL_PROCEDURE=0x10`; bits `0xE0` are zero. Unit values are `NONE=0x00`,
`BOOLEAN=0x01`, `COUNT=0x02`, `RAW_ADC=0x03`, `NORMALIZED=0x04`, and
`MILLIVOLTS=0x05`. All fields are copied snapshots. No record serializes a
C/C++ struct or exposes a string.
Enumeration/diagnostics use bounded pages and never fragment in v0.6.

Unknown opcodes retain the existing unsupported-opcode behavior and never
reach duplicate state. Unsupported capability operations use the structured
result vocabulary only after a structurally valid v0.6 request is admitted.

## 4. COMMAND, ACK, and RESPONSE

A structured operation begins with COMMAND. After full admission, the Node:

1. validates destination, configured source, packet type, and opcode;
2. validates the exact payload length, schema, enum encodings, and structural
   field relationships;
3. checks the canonical duplicate identity;
4. for a new admitted request, reserves the single cache entry and returns ACK
   `SUCCESS`;
5. performs device/capability processing at its approved safe point: capability
   lookup, authorization, operation-specific value/range and policy validation,
   interlock, hardware availability, then handler execution; and
6. caches and sends RESPONSE with the `OperationStatus` result.

ACK is transport-level receipt/admission. It never means the capability or
procedure completed. RESPONSE is operation completion. The Hub transaction
therefore progresses `awaiting ACK → awaiting RESPONSE → terminal`. A valid
RESPONSE received before its ACK MAY prove both acceptance and completion,
allowing completion without waiting for the reordered ACK. An ACK alone cannot
produce an operation-success result.

The existing one-byte ACK status registry remains `SUCCESS=0x00`,
`UNSUPPORTED_OPCODE=0x01`, and `MALFORMED_PACKET=0x02`. Structured requests use
`SUCCESS` only to mean admitted and accepted for operation processing. Unknown
opcodes and structurally malformed requests terminate with the applicable
existing ACK rejection and produce no RESPONSE. Capability absence,
unsupported capability operation, invalid operation value/range or policy,
authorization denial, active interlock, unavailable hardware, BUSY, and
operation failure are post-admission operation outcomes: they MUST be returned
in RESPONSE using `OperationStatus` and MUST NOT create new ACK statuses.

A matching ACK with an undefined status is malformed: it is counted/ignored,
does not transition the transaction, and does not reset or extend its deadline.
This explicitly corrects the previously observed ambiguous behavior.

## 5. Correlation and matching

The Wire tuple is source, destination, sequence, and opcode; Host request ID is
not transmitted over radio. ACK and RESPONSE reverse endpoints and copy the
sequence and opcode. The Hub accepts them only for the configured peer and the
one active transaction after exact type/length/status validation.

Wrong source/destination, sequence, or opcode is ignored and cannot change the
active transaction. A RESPONSE for no active matching transaction is late and
ignored. A malformed matching RESPONSE is counted and ignored; it does not
complete the transaction or extend its deadline. A byte-identical duplicate
valid RESPONSE may be counted but cannot complete twice.

## 6. Duplicate request and result behavior

The v0.5.1 canonical request identity remains exactly:

```text
source + sequence + opcode + payload length + meaningful payload bytes
```

The cache remains fixed-size, single-entry, volatile, and allocation-free.
Complete Wire/command admission and structural request validation MUST precede
lookup or mutation. Malformed, unknown/unsupported Wire-opcode, ignored,
wrongly addressed, or otherwise structurally inadmissible requests MUST NOT
consult or poison duplicate state. Capability lookup and all operation-layer decisions,
including authorization, occur after lookup and reservation so retransmission
can reproduce the accepted request's result without repeating processing.

For a duplicate of an admitted structured request, the Node MUST NOT execute
again. It regenerates the cached ACK. If execution completed, it also
regenerates the cached RESPONSE from the bounded cached result. If work is
still active, it sends only the cached acceptance ACK; the original execution
owns the eventual RESPONSE. Result retention is part of the same one cache
entry. Accepting a different canonical request replaces that entry only at the
defined safe point and never while its result is required for active retry.

Reset loses the cache. Thus this design provides retransmission idempotency
only within volatile retention and does not solve F-04 or authorize blind
retry of side effects after reset.

## 7. Timeout and retry

The Hub uses the existing bounded attempt policy. Until a valid ACK or RESPONSE
is observed, retry retransmits the exact original COMMAND bytes with the same
sequence. After valid acceptance ACK, the Hub does not create a new operation;
it waits for RESPONSE and MAY retransmit the identical COMMAND at the defined
retry point to solicit cached state. Every retry shares one overall bounded
deadline; ACK, malformed, mismatch, or duplicate traffic does not extend it.

At deadline, the Hub reports transport timeout and restores receive state.
A late RESPONSE is ignored. The host learns timeout, not proof that a remote
side effect did or did not occur. No automatic retry with a new sequence is
permitted for a side-effecting operation.

## 8. Capability validation and authorization

Structural request validation precedes duplicate lookup. For a new admitted
request, duplicate reservation and ACK `SUCCESS` precede operation processing.
Processing order is capability lookup, authorization, operation-specific
value/range and policy validation, interlock, hardware availability, then
handler execution. Every failure in this processing phase is cached as the
operation result and returned through RESPONSE using `OperationStatus`; none
is represented as transport rejection in ACK.

`HOST_LOCAL` identifies the physical/local host path, not a cryptographic user.
It may exercise only the locally permitted operation/capability policy.
`REMOTE` identifies unauthenticated Wire Protocol 1 input, not a verified peer.
The default remote allowlist is PING, device/status/capability discovery,
diagnostic snapshots, and bounded reads where descriptor policy permits.

`SET_INDICATOR` remains in the vocabulary to make its schema testable and to
support local Host operation. General REMOTE authorization MUST remain
disabled. `RUN_PROCEDURE` addresses only a compiled, registered procedure; it
cannot upload code, select a function, or invoke an arbitrary handler, and
general REMOTE authorization MUST remain disabled. Normal capability policy
MUST NOT convert unauthenticated REMOTE input into production side-effect
authority.

A separately reviewed compile-time laboratory build MAY enable one explicitly
bounded RF side-effect test path for physical qualification. The build and
test evidence MUST identify that path as unauthenticated, and it MUST NOT be
represented as production authenticated authority.

v0.8 retains identity/provisioning ownership and v0.9 retains authenticated
encryption, peer identity, persistent freshness, replay rejection, credential
rotation, and revocation. This design does not partially redesign them.

## 9. Compatibility and required validation

Native tests MUST cover:

- exact numeric encodings and 0/26-byte payload boundaries;
- legacy TEST/ACK byte-for-byte behavior;
- PING bootstrap: legacy ACK `UNSUPPORTED_OPCODE`, v0.6 ACK `SUCCESS` followed
  by RESPONSE, explicit-configuration support, and suppression of other v0.6
  operations until support is discovered or configured;
- old-peer rejection/ignore behavior for every other new type/opcode;
- every operation length, enum, value type/range, target, cursor, and result;
- ACK versus RESPONSE state transitions, including RESPONSE-before-ACK;
- invalid ACK status not terminating or extending a transaction;
- malformed, invalid-status, late, duplicate, wrong-source, wrong-sequence,
  wrong-opcode, and wrong-destination ACK/RESPONSE;
- timeout and exact-byte retry at each state;
- canonical duplicate identity, including payload-length and payload-byte
  distinctions, and proof that structurally inadmissible traffic never
  reads/mutates cache while authorization and other operation outcomes occur
  after reservation and are returned/cached as RESPONSE results;
- one handler execution with duplicate ACK/RESPONSE regeneration;
- cache replacement and volatile-reset ambiguity;
- authorization, interlock, unavailable hardware, and remote read allowlist;
- mandatory production REMOTE denial of SET_INDICATOR and RUN_PROCEDURE,
  including proof that normal capability policy cannot enable them; and
- bounded storage, saturation, and receive restoration.

After the implementation entry gate and native/build gates pass, physical
qualification MUST cover two-board legacy coexistence; PING, device/status and
capability discovery; permitted reads; denial of remote side effects; an
explicitly approved laboratory indicator path if used; ACK loss/retry and
cached RESPONSE regeneration where controllable; timeout, late/mismatch
handling, receive restoration, reset ambiguity, host disconnect/reconnect,
radio/host coexistence, and OLED/input/settings regression.

No physical result is claimed by this design. Remaining pre-entry hardware
qualification still gates implementation, and v0.6 physical qualification
still gates eventual release.
