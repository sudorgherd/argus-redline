# ARGUS REDLINE — v0.2.0 Implementation Brief

**Milestone:** `v0.2.0`
**Title:** Firmware Architecture and Test Foundation
**Status:** Release preparation complete
**Baseline:** Clean, synchronized `main` at or after commit `1d665b1`
**Development branch:** `v0.2.0-architecture-foundation`
**Released firmware baseline:** `v0.1.03`
**Final firmware identifier:** `v0.2.0`
**Wire compatibility:** Protocol v0.1 / Wire Protocol version 1

This brief implements the authoritative v0.2.0 milestone defined in the [Versioned Development Roadmap](ARGUS_REDLINE_VERSIONED_DEVELOPMENT_ROADMAP.md#L96-L173). The roadmap controls milestone scope and release gates. Current source code remains authoritative for behavior that must be preserved.

## 1. Objective

Restructure the working single-Hub/single-Node firmware into small, reusable, testable components without changing observable radio behavior.

v0.2.0 establishes:

- separate firmware and wire-protocol version reporting;
- centralized build and version metadata;
- authoritative runtime and transaction-state types;
- reusable hardware-independent protocol and transaction logic;
- native tests for that logic;
- a documented two-board regression procedure.

The milestone must preserve Wire Protocol version 1 and the existing `TEST` command/ACK transaction. These requirements come directly from the roadmap’s v0.2.0 scope and release gate: [roadmap:96–173](ARGUS_REDLINE_VERSIONED_DEVELOPMENT_ROADMAP.md#L96-L173).

This is an incremental extraction, not a rewrite. Hub and Node firmware must remain buildable and behaviorally usable after every implementation step.

Unfinished development builds must not claim to be the final v0.2.0 release. During implementation they should report `0.2.0-dev`, or continue reporting the prior released firmware identifier until centralized version metadata is introduced. Final `v0.2.0` reporting is permitted only after every release-gate condition passes.

## 2. Current baseline

### Repository and branch prerequisite

Implementation begins only when:

- `main` has a clean working tree;
- local `main` is synchronized with `origin/main`;
- the intended baseline commit is recorded;
- a dedicated development branch is created from that baseline.

Recommended branch:

```text
v0.2.0-architecture-foundation
```

Do not implement v0.2.0 directly on `main`.

### Firmware targets

The repository has two PlatformIO environments:

- `tx`: Hub firmware from `src-tx/**`, local ID `0x01`, peer ID `0x10`.
- `rx`: Node firmware from `src-rx/**`, local ID `0x10`, peer ID `0x01`.

See [platformio.ini:20–38](../platformio.ini#L20-L38).

Both environments target the Heltec WiFi LoRa 32 V4 using Arduino, RadioLib, and the ThingPulse SSD1306 library: [platformio.ini:4–18](../platformio.ini#L4-L18).

### Wire protocol

Protocol v0.1 uses Wire Protocol version 1. It currently defines:

- a six-byte header;
- a maximum packet size of 32 bytes;
- a maximum payload size of 26 bytes;
- packet types `COMMAND`, `ACK`, and `ERROR`;
- ACK statuses `SUCCESS`, `UNSUPPORTED_OPCODE`, and `MALFORMED_PACKET`;
- one supported application opcode, `TEST=0x64`, with a zero-byte payload.

See [protocol.h:8–40](../include/protocol.h#L8-L40) and [protocol.h:42–79](../include/protocol.h#L42-L79).

The codec recognizes all three packet types, but current firmware actively uses only `COMMAND` and `ACK`: [protocol.h:144–189](../include/protocol.h#L144-L189), [src-tx/main.cpp:134–149](../src-tx/main.cpp#L134-L149), and [src-rx/main.cpp:133–157](../src-rx/main.cpp#L133-L157).

### Hub transaction behavior

The Hub currently:

1. waits for the next scheduled transaction;
2. creates a zero-payload `TEST` command;
3. transmits it;
4. enters receive mode;
5. waits up to 2.5 seconds for an ACK;
6. accepts only a matching source, destination, sequence, opcode, and one-byte status;
7. retries after 500 ms;
8. permits two retries after the initial attempt;
9. advances the eight-bit sequence after success, a valid error ACK, or retry exhaustion;
10. schedules the next transaction after three seconds.

See [src-tx/main.cpp:13–39](../src-tx/main.cpp#L13-L39), [src-tx/main.cpp:101–248](../src-tx/main.cpp#L101-L248), and [src-tx/main.cpp:250–357](../src-tx/main.cpp#L250-L357).

### Node transaction behavior

The Node currently:

1. listens asynchronously;
2. validates packet length and Wire Protocol version;
3. checks destination, packet type, and configured sender;
4. detects a duplicate using one in-memory entry containing the most recent source, sequence, and opcode;
5. validates opcode and payload length for a new command;
6. records the resulting ACK status;
7. regenerates and encodes an ACK from transaction metadata and status;
8. resumes listening after ACK transmission.

See [src-rx/main.cpp:13–34](../src-rx/main.cpp#L13-L34), [src-rx/main.cpp:96–204](../src-rx/main.cpp#L96-L204), and [src-rx/main.cpp:206–302](../src-rx/main.cpp#L206-L302).

Duplicate state is single-entry, in-memory, and volatile across restart. The encoded ACK packet is not cached.

### Version identity

The firmware source identifies itself as v0.1.03, but both runtime messages currently label that value as `Protocol v0.1.03`: [src-tx/main.cpp:393–396](../src-tx/main.cpp#L393-L396) and [src-rx/main.cpp:337–340](../src-rx/main.cpp#L337-L340).

Tag `v0.1.03` points to merge commit `27bcb39`, which moved device identities into build configuration. Wire Protocol version remains `1`.

## 3. Compatibility constraints

v0.2.0 must preserve all of the following unless a separately approved compatibility change explicitly supersedes this brief.

### Wire format

- `Protocol::VERSION == 1`.
- Six-byte header layout and field order.
- Maximum packet and payload sizes.
- Control-byte version/type encoding.
- Packet-type numeric values.
- Opcode numeric values.
- ACK-status numeric values.
- Exact codec acceptance and rejection rules.

The current definitions are at [protocol.h:8–40](../include/protocol.h#L8-L40), [protocol.h:81–104](../include/protocol.h#L81-L104), and [protocol.h:106–189](../include/protocol.h#L106-L189).

### Application behavior

- Hub emits `COMMAND`.
- Hub command opcode remains `TEST=0x64`.
- `TEST` payload length remains zero.
- Node emits `ACK`.
- ACK payload remains exactly one status byte.
- ACK source and destination remain reversed from the command.
- ACK sequence and opcode continue to match the command.
- Unsupported opcodes yield `UNSUPPORTED_OPCODE`.
- Invalid supported-opcode payloads yield `MALFORMED_PACKET`.
- Successful `TEST` commands yield `SUCCESS`.

See [src-tx/main.cpp:134–149](../src-tx/main.cpp#L134-L149) and [src-rx/main.cpp:133–157](../src-rx/main.cpp#L133-L157).

### Addressing and transaction behavior

- Hub and Node continue using the configured local and peer IDs.
- Packets for other destinations remain ignored.
- Packets from an unexpected sender remain ignored.
- ACK matching continues to require type, endpoints, sequence, opcode, and one-byte payload.
- The sequence remains eight-bit and begins at `1`.
- Sequence advancement behavior remains unchanged, including wrap from `255` to `0`.
- Existing retry count, timeout, retry delay, and transaction interval remain unchanged.
- Unrelated or malformed received packets do not silently become matching ACKs.

See [device_config.h:5–24](../include/device_config.h#L5-L24), [src-tx/main.cpp:13–18](../src-tx/main.cpp#L13-L18), [src-tx/main.cpp:101–131](../src-tx/main.cpp#L101-L131), and [src-tx/main.cpp:237–335](../src-tx/main.cpp#L237-L335).

### Duplicate behavior

- Duplicate detection remains single-entry and in-memory.
- The duplicate key remains source, sequence, and opcode.
- Duplicate state remains volatile across restart.
- A duplicate uses the previously determined status.
- Its ACK is regenerated and encoded from transaction metadata and status.
- No encoded-packet cache is introduced.

See [src-rx/main.cpp:30–34](../src-rx/main.cpp#L30-L34), [src-rx/main.cpp:96–114](../src-rx/main.cpp#L96-L114), and [src-rx/main.cpp:133–163](../src-rx/main.cpp#L133-L163).

### Version reporting

- Development builds report `0.2.0-dev`, or retain the prior released firmware identifier until centralized version metadata exists.
- Development builds must not report final `v0.2.0`.
- Wire Protocol version remains separately reported as `1`.
- Final `v0.2.0` reporting occurs only during release preparation after every release-gate condition passes.

### Repository constraints

Packet layouts, field meanings, opcode/status values, addressing behavior, and transaction semantics must not change silently: [AGENTS.md:10–15](../AGENTS.md#L10-L15).

## 4. Explicit non-goals

v0.2.0 does not add:

- new application commands or behavior;
- menus or screen navigation;
- button handling;
- persistent settings;
- configuration schema 1;
- runtime provisioning;
- multiple Nodes;
- encryption or authentication;
- persistent replay protection;
- persistent transaction identity;
- Node-originated events;
- sensors, outputs, or capabilities;
- repeaters;
- routing;
- mesh behavior;
- ARGUS integration;
- a new wire format;
- a new host protocol.

These exclusions are authoritative at [roadmap:165–173](ARGUS_REDLINE_VERSIONED_DEVELOPMENT_ROADMAP.md#L165-L173). Repository rules independently require preservation of the single-Hub/single-Node architecture: [AGENTS.md:3–8](../AGENTS.md#L3-L8).

Creating an abstraction boundary for future work does not authorize implementing that future behavior.

## 5. Proposed component boundaries

The roadmap’s directory tree is suggested rather than mandatory: [roadmap:113–138](ARGUS_REDLINE_VERSIONED_DEVELOPMENT_ROADMAP.md#L113-L138). v0.2.0 should create only components needed to extract and test current behavior.

### `lib/redline_protocol/`

Own:

- the existing `Protocol::Packet` representation;
- wire constants;
- packet types, opcodes, and ACK statuses;
- codec functions;
- opcode and payload validation;
- address comparison.

This is hardware-independent logic currently located in [protocol.h:6–198](../include/protocol.h#L6-L198).

No wire constant or behavior changes during extraction.

### `lib/redline_version/`

Own centralized compile-time metadata:

- development firmware identifier: `0.2.0-dev`, or the prior release identifier until migration reaches this component;
- final firmware release identifier: `v0.2.0`, enabled only during final release preparation;
- Wire Protocol version: `1`;
- hardware profile identifier: `HELTEC_V4`;
- configuration schema state: explicitly undefined/not implemented;
- host protocol state: explicitly undefined/not implemented.

It should provide separate firmware and wire-version strings so runtime diagnostics cannot label the firmware release as a protocol version.

### `lib/transaction_engine/`

Own hardware-independent transaction decisions and state:

- Hub transaction phase;
- current sequence;
- retry count;
- retry/advance decisions;
- ACK matching;
- ACK-status interpretation;
- deadline outcome as an input event, not direct `millis()` access;
- Node command classification;
- duplicate tracking;
- ACK construction from command metadata and status.

The component must not call Arduino, RadioLib, OLED, SPI, GPIO, delay, or serial APIs.

### `lib/device_state/`

Own authoritative state types needed by current firmware:

- role (`HUB` or `NODE`);
- readiness;
- radio/transaction phase;
- current sequence;
- retry count;
- last transaction result;
- last packet metadata;
- diagnostic status suitable for presentation.

Only fields used by current behavior should be added. Menu, persistence, capability, and security state are out of scope.

### `lib/diagnostics/`

Optional within v0.2.0.

If introduced, it should define hardware-independent diagnostic events or values, not perform serial or OLED output directly. Arduino `String`, `Serial`, and display rendering should remain outside pure logic.

### Deferred component boundaries

Do not create empty or speculative `settings`, `capabilities`, `input`, or menu systems merely because they appear in the roadmap’s suggested future structure. Those components belong to later milestones unless a small interface is strictly necessary for compiling current behavior.

## 6. Logic to move out of `src-tx/main.cpp`

### Move into pure/shared components

- Hub transaction-state enum and state data currently at [src-tx/main.cpp:23–39](../src-tx/main.cpp#L23-L39).
- Sequence advancement and retry-decision logic from [src-tx/main.cpp:101–132](../src-tx/main.cpp#L101-L132).
- `TEST` command construction from [src-tx/main.cpp:134–150](../src-tx/main.cpp#L134-L150).
- ACK structural matching from [src-tx/main.cpp:237–248](../src-tx/main.cpp#L237-L248).
- ACK-status validation and resulting transaction decision from [src-tx/main.cpp:324–357](../src-tx/main.cpp#L324-L357).
- Timing constants should move to centralized transaction configuration while retaining their exact values: [src-tx/main.cpp:13–18](../src-tx/main.cpp#L13-L18).
- Packet-log data extraction may move to a diagnostic event type, but serial rendering should not.

### Split rather than move wholesale

`processAcknowledgment()` currently mixes:

- RadioLib packet-length lookup;
- radio reads;
- CRC/read errors;
- RSSI/SNR retrieval;
- protocol decoding;
- ACK matching;
- status validation;
- state transitions;
- serial output.

See [src-tx/main.cpp:250–357](../src-tx/main.cpp#L250-L357).

Split it into:

1. hardware adapter reads bytes and radio metrics;
2. codec decodes bytes;
3. transaction engine evaluates the packet;
4. firmware shell performs the returned radio/state action;
5. serial/OLED layer presents the result.

### Keep `src-tx/main.cpp` as composition root

The Hub entry point should continue to own:

- object construction;
- hardware initialization;
- interrupt registration;
- event-loop orchestration;
- calls into pure transaction logic;
- dispatch of returned radio actions;
- presentation of diagnostics.

The goal is a small coordinator, not an empty or framework-heavy entry point.

## 7. Logic to move out of `src-rx/main.cpp`

### Move into pure/shared components

- Node transaction-state types at [src-rx/main.cpp:16–34](../src-rx/main.cpp#L16-L34).
- Single-entry duplicate comparison and remembered metadata/status at [src-rx/main.cpp:96–114](../src-rx/main.cpp#L96-L114).

- Destination, sender, type, opcode, and payload classification decisions currently embedded in [src-rx/main.cpp:239–301](../src-rx/main.cpp#L239-L301).

A pure Node command evaluator should accept:

- a decoded packet;
- configured local and peer IDs;
- current duplicate state.

It should return a decision such as:

- ignore;
- ACK success;
- ACK unsupported opcode;
- ACK malformed packet;
- regenerate prior ACK for duplicate.

The result should include enough metadata to build the ACK without retaining encoded radio bytes.

### Split rather than move wholesale

`handleReceivedPacket()` mixes radio access, codec work, addressing, duplicate detection, validation, status selection, metrics, logging, and ACK transmission: [src-rx/main.cpp:206–302](../src-rx/main.cpp#L206-L302).

Split it into:

1. hardware adapter reads packet bytes and metrics;
2. codec decodes;
3. pure evaluator classifies;
4. pure ACK factory creates the response;
5. firmware shell invokes RadioLib;
6. presentation layer reports the result.

### Keep `src-rx/main.cpp` as composition root

The Node entry point should retain hardware initialization, interrupt dispatch, receive/transmit orchestration, and diagnostic presentation.

## 9. Native test strategy

Add a PlatformIO `native` test environment for hardware-independent C++ only.

Tests should:

- compile without Arduino headers;
- avoid RadioLib, OLED, SPI, GPIO, and serial dependencies;
- use deterministic input events rather than real time;
- construct packets and state explicitly;
- compare exact encoded bytes where wire compatibility matters;
- characterize current behavior before moving logic;
- run on every extraction step.

Preferred layout:

```text
test/
├── test_protocol/
├── test_hub_transactions/
├── test_node_commands/
├── test_duplicates/
├── test_sequence/
└── test_device_config/
```

Use PlatformIO’s supported native test framework unless repository constraints require another choice. Do not add an additional test dependency without demonstrating that PlatformIO’s available test support is insufficient.

### Test seams

- Clock: pass `now` or an explicit `TIMEOUT` event into pure logic.
- Radio: represent completion and received data as inputs; return requested radio actions.
- Diagnostics: return typed result codes/events.
- Configuration: pass IDs and timing values as immutable configuration.
- Version metadata: expose compile-time constants through hardware-independent headers.

### Device-configuration test strategy

Device-configuration validation remains part of the overall v0.2.0 release requirements, but it is not part of the first protocol-characterization task.

The current configuration relies on environment-specific preprocessor definitions and compile-time checks: [device_config.h:5–24](../include/device_config.h#L5-L24) and [platformio.ini:20–38](../platformio.ini#L20-L38).

Testing it may require one of these later approaches:

- separate native build environments with Hub and Node build flags;
- compile fixtures that deliberately test valid and invalid macro combinations;
- compile-failure tests for equal or missing IDs;
- a later hardware-independent runtime validation helper that complements the compile-time assertions.

The selected approach must not weaken the existing compile-time validation.

### Assumptions

- PlatformIO’s native environment and bundled test support are adequate for the required tests.
- Production and native tests can compile the same protocol/transaction sources without Arduino compatibility shims.
- Wire encoding remains byte-oriented and does not depend on target struct layout.

### Unresolved design choices

- Header-only versus `.h/.cpp` component organization.
- Exact transaction-engine result type: enum plus data, tagged union, or small action structure.
- Whether Hub and Node engines share one module or use sibling modules.
- Whether timing values remain compile-time constants or enter an immutable configuration struct.
- Whether diagnostic events belong in v0.2.0 or remain local until v0.3.0.
- Whether version metadata is generated from build flags or maintained in a single checked-in header.
- Which device-configuration test strategy provides useful coverage without overcomplicating the first native test environment.

Resolve these choices in the smallest way that supports current behavior and tests. Do not design later milestone APIs prematurely.

## 10. Minimum required tests

### Codec and wire compatibility

1. Encode the exact current zero-payload `TEST` command and verify all six bytes.
2. Decode the same command and verify every field.
3. Round-trip a one-byte ACK.
4. Reject input shorter than six bytes.
5. Reject payload length greater than 26.
6. Reject encoded-length/payload-length mismatch.
7. Reject the wrong Wire Protocol version.
8. Reject an unknown packet type.
9. Confirm codec recognition of `COMMAND`, `ACK`, and `ERROR`.
10. Confirm `TEST=0x64`.
11. Confirm the three ACK-status numeric values.
12. Confirm `TEST` accepts only a zero-byte payload.
13. Confirm unsupported opcodes fail command validation.

These cases derive from [protocol.h:8–79](../include/protocol.h#L8-L79) and [protocol.h:106–189](../include/protocol.h#L106-L189).

### Hub transactions

14. Initial sequence is `1`.
15. A matching success ACK completes the transaction.
16. A valid non-success ACK completes the transaction without retry.
17. Wrong source is ignored.
18. Wrong destination is ignored.
19. Wrong sequence is ignored.
20. Wrong opcode is ignored.
21. Wrong packet type is ignored.
22. ACK payload length other than one is ignored.
23. Invalid ACK status is treated exactly as current firmware treats it.
24. Timeout schedules a retry after 500 ms.
25. Two retries are permitted after the initial attempt.
26. Retry exhaustion advances the sequence and schedules the next transaction.
27. Successful completion resets retry count and advances the sequence.
28. Sequence `255` wraps to `0`.
29. Ignored packets do not reset the original ACK deadline.

These cases derive from [src-tx/main.cpp:13–18](../src-tx/main.cpp#L13-L18), [src-tx/main.cpp:101–132](../src-tx/main.cpp#L101-L132), and [src-tx/main.cpp:217–357](../src-tx/main.cpp#L217-L357).

### Node commands and duplicates

30. Packet for another destination is ignored.
31. Packet from an unexpected source is ignored.
32. Non-`COMMAND` packet is ignored.
33. Valid `TEST` produces `SUCCESS`.
34. Unsupported opcode produces `UNSUPPORTED_OPCODE`.
35. Invalid `TEST` payload produces `MALFORMED_PACKET`.
36. First command is remembered.
37. Same source, sequence, and opcode is detected as a duplicate.
38. Different source is not a duplicate.
39. Different sequence is not a duplicate.
40. Different opcode is not a duplicate.
41. Duplicate reuses the previously determined status.
42. Duplicate ACK is regenerated with reversed endpoints, matching sequence/opcode, and one status byte.
43. Duplicate state begins empty, characterizing its volatility across restart.
44. A sequence-wrap command is evaluated consistently with the single-entry comparison.

Native duplicate-detection and regenerated-ACK tests are mandatory for v0.2.0.

These cases derive from [src-rx/main.cpp:96–157](../src-rx/main.cpp#L96-L157) and [src-rx/main.cpp:259–301](../src-rx/main.cpp#L259-L301).

### Configuration and metadata

45. Local and peer IDs cannot be equal.
46. Hub configuration resolves to local `0x01`, peer `0x10`.
47. Node configuration resolves to local `0x10`, peer `0x01`.
48. Development firmware and wire versions are distinct constants.
49. Development builds do not report final `v0.2.0`.
50. Wire Protocol version remains `1`.
51. Hardware profile reports `HELTEC_V4`.
52. Final release preparation can select `v0.2.0` only after all gates pass.

Tests 45–47 are required before release but are explicitly deferred from the first protocol-characterization task. They may use separate native build environments, compile fixtures, or a later runtime-testable validation helper.

The roadmap’s minimum required categories are at [roadmap:140–152](ARGUS_REDLINE_VERSIONED_DEVELOPMENT_ROADMAP.md#L140-L152).

## 11. Migration sequence in small reviewable steps

Each step must leave Hub and Node firmware buildable. Prefer one focused commit per step.

### Step 0 — Establish the development branch

- Verify the working tree is clean.
- Verify local `main` is synchronized with `origin/main`.
- Record the baseline commit.
- Create `v0.2.0-architecture-foundation`.
- Perform all v0.2.0 implementation on that branch.
- Do not implement directly on `main`.

### Step 1 — Characterize the existing codec

- Add the native PlatformIO environment.
- Add tests directly against the existing protocol header.
- Lock down numeric constants and exact encoded bytes.
- Do not move production code yet.
- Do not add Hub/Node device-configuration tests in this step.

### Step 2 — Centralize version metadata

- Add firmware, wire, and hardware-profile metadata.
- Use `0.2.0-dev` during implementation, or retain `v0.1.03` until this step is complete.
- Change runtime reporting so firmware and wire versions are separate.
- Do not report final `v0.2.0`.
- Do not alter packet control-byte generation or decoding.

### Step 3 — Establish shared component packaging

- Move the protocol implementation into the selected reusable component layout.
- Preserve the existing `Protocol` namespace or provide a compatibility include.
- Build both firmware targets and run native codec tests.

### Step 4 — Extract Node duplicate tracking and ACK construction

- Move `isDuplicateCommand()`, remembered metadata/status, and ACK construction into pure code.
- Add mandatory native duplicate and ACK-regeneration tests first or in the same step.
- Keep radio transmit/listen orchestration in `src-rx/main.cpp`.

### Step 5 — Extract Node command evaluation

- Move address, sender/type, opcode, and payload decisions into a pure evaluator.
- Keep byte reads, metrics, logging, and radio calls in the Node shell.
- Verify exact status and ignore behavior.

### Step 6 — Extract Hub ACK matching

- Move structural ACK matching and status interpretation into pure code.
- Keep RadioLib receive/read operations and metrics in the Hub shell.
- Verify ignored packets preserve the existing deadline behavior.

### Step 7 — Extract Hub retry and sequence state

- Introduce authoritative Hub transaction state.
- Move retry/advance decisions into pure functions or a small engine.
- Pass timeout events into the engine rather than giving it `millis()` access.
- Test retry exhaustion and sequence wrap.

### Step 8 — Introduce authoritative runtime state

- Consolidate duplicated role/readiness/transaction/diagnostic fields needed by current behavior.
- Do not add menu, settings, capability, persistence, or security fields.
- Keep the display behavior visually unchanged.

### Step 9 — Add device-configuration validation coverage

- Select separate native environments, compile fixtures, or a runtime-testable helper.
- Verify Hub and Node configurations independently.
- Preserve the existing compile-time errors and unequal-ID assertion.
- Keep this separate from initial protocol characterization.

Run the compile fixtures from PowerShell with the workstation-local PlatformIO executable. The valid cases must return zero; each invalid case must return nonzero and contain its exact expected diagnostic:

```powershell
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
$platformio = 'C:\Users\admin\.platformio\penv\Scripts\platformio.exe'

& $platformio run -e config_hub_valid
if ($LASTEXITCODE -ne 0) { throw 'config_hub_valid failed' }

& $platformio run -e config_node_valid
if ($LASTEXITCODE -ne 0) { throw 'config_node_valid failed' }

$invalidConfigurations = @(
    @('config_missing_local', 'ARGUS_LOCAL_DEVICE_ID must be defined by the build environment'),
    @('config_missing_peer', 'ARGUS_PEER_DEVICE_ID must be defined by the build environment'),
    @('config_equal_ids', 'Local and peer device IDs must be different')
)

foreach ($configuration in $invalidConfigurations) {
    $output = (& $platformio run -e $configuration[0] 2>&1 | Out-String)
    if ($LASTEXITCODE -eq 0) { throw "$($configuration[0]) unexpectedly succeeded" }
    if (-not $output.Contains($configuration[1])) {
        throw "$($configuration[0]) did not emit: $($configuration[1])"
    }
}
```

### Step 10 — Reduce entry points to hardware orchestration

- Remove superseded local logic from `main.cpp`.
- Keep initialization, radio calls, event loops, and presentation.
- Run all native tests and build both targets.

### Step 11 — Run and document physical regression

- Execute the two-board procedure below.
- Record development firmware identifier, Wire Protocol version, board roles, radio frequency, test date, and results.
- Address regressions before declaring v0.2.0 complete.
- Treat selective physical ACK-loss testing as best-effort unless a repeatable method exists.

### Step 12 — Final release preparation

Only after every release-gate condition passes:

- change firmware reporting from `0.2.0-dev` or the preserved prior identifier to final `v0.2.0`;
- rerun native tests;
- rebuild both firmware targets;
- repeat the required physical regression checks;

### Equipment and assumptions

### Build and flash

```powershell
& 'C:\Users\admin\.platformio\penv\Scripts\platformio.exe' run -e tx -t upload
& 'C:\Users\admin\.platformio\penv\Scripts\platformio.exe' run -e rx -t upload
```

### Baseline transaction test

1. Start serial monitoring for both boards.
2. Reset both boards.
3. Confirm each reports the development firmware identifier and Wire Protocol version separately.
4. Confirm neither unfinished build reports final `v0.2.0`.
5. Confirm the Hub becomes ready.
6. Confirm the Node becomes ready and enters receive mode.
7. Observe at least ten consecutive `TEST` transactions.
8. For each transaction, confirm:
   - Hub source/destination are `0x01 → 0x10`;
   - Node receives the same sequence and opcode;
   - Node transmits ACK `0x10 → 0x01`;
   - ACK sequence and opcode match;
   - ACK status is `SUCCESS`;
   - Hub reports a matched ACK;
   - sequence advances once;
   - RSSI and SNR diagnostics remain present.
9. Record any malformed packet, timeout, retry, duplicate, or radio error.

### Node-unavailable retry and recovery test

1. After a successful transaction, disconnect or power down the Node.
2. Observe the next Hub transaction.
3. Confirm the initial attempt times out.
4. Confirm no more than two retries occur.
5. Confirm retry delay and ACK timeout remain behaviorally unchanged.
6. Confirm the Hub reports command failure after retry exhaustion.
7. Restore the Node without restarting the Hub.
8. Confirm a later scheduled transaction succeeds.
9. Confirm sequence behavior matches the pre-refactor firmware.

### Duplicate ACK regeneration

Native tests for duplicate detection and regenerated ACK behavior are mandatory and release-blocking.

Selective physical ACK-loss testing is best-effort unless a repeatable lab method is established. Inability to suppress only the ACK reproducibly does not by itself block v0.2.0 when:

- mandatory native duplicate tests pass;
- normal two-board regression passes;
- addressing and retry behavior remain intact;
- no other evidence indicates a hardware regression.

If a repeatable method is available:

1. Allow the Node to receive a command.
2. Suppress only the corresponding Node-to-Hub ACK without rebooting the Node.
3. Restore the link before the Hub retry.
4. Confirm the retransmitted source/sequence/opcode is detected as a duplicate.
5. Confirm the Node regenerates an ACK with the previously determined status.
6. Confirm the Hub accepts that ACK.
7. Document the equipment and timing used.

Do not add a production command or alter radio semantics solely to create this test condition.

### Addressing regression

With only the standard two-board configuration, confirm all logged packets use the configured endpoints. A negative physical wrong-destination test requires a controlled packet injector or temporary test-only build and is not mandatory unless an approved test method is added.

### Required physical pass criteria

The required two-board regression passes when:

- both firmware targets build and flash;
- both boards boot;
- development firmware and Wire Protocol versions are reported separately;
- normal `TEST` exchanges succeed;
- addressing remains correct;
- retry exhaustion and recovery remain correct;
- sequence behavior remains correct;
- no new blocking, reset, display, or radio failures appear.

Selective physical ACK-loss testing is recorded when reproducible, but is not independently release-blocking. Native duplicate and regenerated-ACK tests remain mandatory.

### Final release-version check

After all other release gates pass and final `v0.2.0` reporting is enabled:

- rebuild both targets;
- flash both boards;
- verify final firmware reports `v0.2.0`;
- verify Wire Protocol still reports version `1`;
- rerun the required baseline transaction test.

## 14. Risks and rollback strategy

### Compatibility risks

- Accidental change to encoded bytes during protocol relocation.
- Changed interpretation of malformed or unsupported packets.
- Changed ACK matching when receive and decision logic are separated.
- Resetting the ACK deadline after ignored packets.
- Off-by-one change in retry count.
- Sequence advancement at a different point.
- Loss of eight-bit wrap behavior.
- Expanding duplicate identity beyond or below source/sequence/opcode.
- Replacing regenerated ACK behavior with encoded-packet caching.
- Changed timing due to reordered RadioLib calls or removal of the Node’s 100 ms delay.
- Arduino/native type-width differences.
- Version metadata accidentally changing Wire Protocol `1`.
- Development builds prematurely reporting final `v0.2.0`.

### Architectural risks

- Creating abstractions for unimplemented future features.
- Introducing excessive interfaces around simple code.
- Allowing Arduino types such as `String` into pure logic.
- Moving hardware ownership into components that native tests cannot compile.
- Performing file movement and behavioral cleanup in the same review.
- Adding dependencies that are unnecessary for the milestone.
- Mixing device-configuration fixture work into the first protocol test slice.
- Implementing directly on `main`.

### Rollback strategy

- Begin from a clean, synchronized `main`.
- Record the exact baseline commit before branching.
- Perform implementation on `v0.2.0-architecture-foundation`.
- Use commit `1d665b1` as the documented roadmap baseline unless a later clean baseline is explicitly selected.
- Keep each extraction in a small independent commit.
- Require firmware builds and relevant native tests before proceeding to the next extraction.
- Preserve existing entry-point behavior until its replacement is tested.
- Do not delete old logic in the same step that first introduces an unverified abstraction when a temporary adapter can keep the firmware working.
- If a regression appears, revert the smallest extraction commit rather than resetting or rewriting unrelated work.
- Preserve captured baseline packet bytes and physical-test observations for comparison.
- Do not report final `v0.2.0` or tag the release until every release-gate item passes.

## 16. Recommended first implementation task

From a clean, synchronized `main`, create the dedicated `v0.2.0-architecture-foundation` branch. Then create the PlatformIO native test environment and add characterization tests for the existing `include/protocol.h` behavior without moving production code.

The first code change should cover:

- exact `TEST` command bytes;
- exact ACK bytes;
- encode/decode round trips;
- invalid length;
- invalid packet type;
- invalid Wire Protocol version;
- payload validation;
- packet-type, opcode, and ACK-status numeric values.

The first task explicitly excludes Hub/Node compile-time device-configuration tests. Those remain required for v0.2.0 but should be addressed later through separate native environments, compile fixtures, or a runtime-testable validation helper.

Why this comes first:

- the codec is already hardware-independent;
- it establishes a working native-test toolchain;
- it locks down Wire Protocol version 1 before extraction;
- it creates no firmware behavior change;
- it provides immediate evidence that later component movement preserves compatibility;
- it is small and independently reviewable.

Only after this characterization step passes should protocol packaging or transaction extraction begin.

### Assumptions

- The explicit local PlatformIO executable can run a native environment.
- PlatformIO native testing is supported by the installed toolchain.
- Existing `protocol.h` compiles without Arduino dependencies.
- No additional dependency is needed for the first test slice.

### Unresolved choices for the first task

- Exact native environment configuration.
- Test framework selection within PlatformIO’s available support.
- Whether the existing protocol header stays in `include/` for the first test or moves only in a later change.

These choices should be resolved during implementation planning without broadening the first change beyond protocol characterization.
