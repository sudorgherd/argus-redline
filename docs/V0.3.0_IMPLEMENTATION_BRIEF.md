# ARGUS REDLINE v0.3.0 Implementation Brief

**Status:** Proposed implementation plan; no v0.3.0 behavior is implemented by
this document.

**Planned release:** `v0.3.0` — Device Runtime, Screens, and Input

**Starting release:** `v0.2.0`

**Compatibility baseline:** Protocol v0.1 / Wire Protocol `1`

**Supported hardware profile:** `HELTEC_V4`

**Topology:** one Hub and one Node, directly connected over LoRa

This brief is subordinate to the release order and milestone scope in the
[versioned development roadmap](ARGUS_REDLINE_VERSIONED_DEVELOPMENT_ROADMAP.md).
Current source code is authoritative for implemented behavior. The labels
**Verified fact**, **External hardware fact**, **Approved design decision**, and
**Remaining implementation risk** distinguish evidence from approved planning
choices and risks that implementation must verify.

## 1. Release objective

`v0.3.0` should create a reusable, responsive local device-interface shell for
both the Hub and Node. It should provide a shared screen model, deterministic
one-button input, useful volatile diagnostics, and nonblocking OLED updates
without changing the established single-Hub/single-Node radio transaction.

The radio and transaction path must continue operating independently of the
visible screen, display power state, and button activity. A screen may present
transaction state, but it must never own or influence transaction decisions.

**Approved design decision:** Treat this release as a presentation and input milestone,
not as a menu or settings milestone. Retain Protocol v0.1 / Wire Protocol `1`
and the existing `TEST`/`ACK` exchange byte-for-byte.

### 2.2 Current runtime-state model

`RuntimeState::State` is hardware-independent and currently contains only:

| Field | Type/current behavior | Authority |
|---|---|---|
| role | `DeviceRole::{HUB,NODE}` | Immutable runtime presentation identity |
| local ID | `uint8_t` snapshot | `DeviceConfig` remains authoritative |
| peer ID | `uint8_t` snapshot | `DeviceConfig` remains authoritative |
| ready | `bool`, default false | Firmware radio initialization |
| phase | `RuntimePhase` | Firmware orchestration mirrors current radio-facing phase |
| latest RSSI | `float`, default `0.0F` | Last successful received-radio measurement |
| latest SNR | `float`, default `0.0F` | Last successful received-radio measurement |

The fields and methods are defined in
`lib/runtime_state/src/runtime_state.h:7-81`. Hub and Node construction and
mutations occur in `src-tx/main.cpp:22-26,103-126,199-223,293-295,413-423` and
`src-rx/main.cpp:18-22,100-116,148-168,229-231,312-325`.

**Verified fact:** Runtime state is not a transaction authority.
`HubTransactionState` owns sequence, retries, ACK wait, timeout deadline, and
terminal completion (`lib/transaction_engine/src/transaction_engine.h:134-232`).
`NodeDuplicateTracker` owns one volatile duplicate entry and its remembered ACK
status (`lib/transaction_engine/src/transaction_engine.h:7-39`).

### 2.3 Current OLED and input behavior

- **Verified fact:** Both roles instantiate `SSD1306Wire` at address `0x3C`
  with `SDA_OLED` and `SCL_OLED` (`src-tx/main.cpp:11`, `src-rx/main.cpp:11`).
- **Verified fact:** Both role files duplicate the same 26×16 RG XBM logo and
  nearly identical `showHomeScreen()` rendering. The 128×64 composition is a
  centered 32×32 white logo field, black RG mark, `RaveGoat Labs` title, and a
  role/status line (`src-tx/main.cpp:40-67`, `src-rx/main.cpp:37-64`).
- **Verified fact:** The Hub draws `TX | READY`; the Node draws `RX | READY`.
  Radio-init errors and Node receive-start errors can replace that initial
  screen (`src-tx/main.cpp:405-414`, `src-rx/main.cpp:304-325`).
- **Verified fact:** Ordinary transaction phases update `RuntimeState`, but do
  not redraw the OLED. The settled home screen therefore remains stable during
  transactions; Serial carries per-transaction details
  (`docs/V0.2.0_TWO_BOARD_REGRESSION.md:156-172`).
- **Verified fact:** There is no application-button symbol, `pinMode`, GPIO
  sample, interrupt, debounce logic, or semantic input event in either role.
  The repository V4 variant defines OLED, radio, LED, serial, I2C, and SPI pins
  but no button alias (`variants/heltec_V4/pins_arduino.h:9-68`).
- **Verified fact:** Current display operations are synchronous calls to
  `clear()`, drawing primitives, and `display()`. They occur only during setup
  and setup failure, not in the normal transaction loop
  (`src-tx/main.cpp:48-67,380-423`; `src-rx/main.cpp:45-64,279-325`).

### 2.4 Current orchestration boundaries

The Hub entry point retains packet construction and encoding, `millis()`-based
scheduling, RadioLib transmit/receive calls, interrupt completion, packet
decoding, RSSI/SNR acquisition, Serial/OLED presentation, and terminal ordering.
It delegates ACK classification and retry/sequence decisions to
`transaction_engine` (`src-tx/main.cpp:138-378,426-484`).

The Node entry point retains packet reads/decoding, RadioLib state changes,
RSSI/SNR acquisition, the existing 100 ms pre-ACK delay, ACK encoding and
transmission, interrupts, and presentation. It delegates command evaluation,
duplicate state, and ACK construction to `transaction_engine`
(`src-rx/main.cpp:100-276,328-348`).

These boundaries are v0.3.0 invariants. UI work must call into them or observe
their results; it must not absorb their policy.

## 3. Scope

The controlled v0.3.0 scope is:

1. Expand the existing authoritative runtime/presentation state with only the
   volatile diagnostics and packet snapshots needed by the initial screens.
2. Add explicit runtime health (`STARTING`, `READY`, `DEGRADED`, `ERROR`) and a
   typed last-error classification without changing radio decisions.
3. Add role-appropriate counters with one documented update point per counter.
4. Add one last-received-packet snapshot with validity markers for optional
   fields; do not use zero values as “unavailable.”
5. Add a shared screen identifier and one-level navigation model for Home,
   Radio, Device, Last Packet, Diagnostics, and About.
6. Add a hardware-independent debouncer and semantic button-event classifier.
7. Integrate the verified on-board V4 application/program button as a polled,
   active-low input after boot.
8. Add shared hardware-independent presentation snapshots and role-specific
   content decisions.
9. Add a Heltec/ThingPulse rendering adapter that contains OLED-driver calls
   and preserves the RG-branded Home screen.
10. Add dirty-state rendering, bounded live refresh, display timeout, and input
    wake behavior without adding delays to normal radio processing.
11. Add native tests for all pure state, input, navigation, and presentation
    policies; preserve all existing tests.
12. Build both board roles and repeat physical two-board transport, retry,
    recovery, OLED, and input regression.

**Approved design decision:** Implement `PRESS`, `RELEASE`, and `LONG_PRESS`
internally, with `SHORT_PRESS` emitted on release when no long press occurred.
Double press is deferred from v0.3.0. The roadmap's broader initial event list
includes it, but the approved v0.3.0 contract does not; the release gate requires
reliable short/long distinction (`docs/ARGUS_REDLINE_VERSIONED_DEVELOPMENT_ROADMAP.md:207-226`).
Deferral avoids delaying short-press navigation for an unused gesture.

## 4. Explicit non-goals

The following are outside v0.3.0:

- persistent settings or NVS persistence;
- configuration schema or migration behavior;
- runtime provisioning or identity changes;
- multiple Nodes or a device registry;
- packet layout, packet type, opcode, ACK-status, or Wire Protocol changes;
- new application commands or Node-originated events;
- security, authentication, or encryption;
- panic, duress, check-in, or emergency gesture semantics;
- arbitrary GPIO control or capability control;
- repeaters, routing, mesh, or store-and-forward behavior;
- host protocol or ARGUS integration;
- battery, sleep, or broader power-lifecycle policy beyond turning the OLED
  panel off after an inactivity timeout;
- a deep menu, settings editor, scrolling menu tree, or new screens beyond the
  six named by the roadmap;
- a broad scheduler, framework, dependency-injection system, generalized state
  machine, or event bus;
- changing the current radio frequency, retry count, ACK timeout, retry delay,
  transaction interval, Node pre-ACK delay, or sequence lifecycle.

Wire Protocol remains `1`. No wire-format change is expected or justified by
this release.

## 5. Repository findings and gap analysis

### 5.1 Reusable foundations already present

- `redline_protocol` is the sole codec/validation implementation; the legacy
  `include/protocol.h` is only a forwarding header.
- `transaction_engine` owns pure Node command classification, duplicate
  tracking, ACK construction, Hub ACK matching, and Hub retry/sequence state.
- `runtime_state` is already the correct hardware-independent home for
  presentation and diagnostic state, but lacks validity flags, counters,
  packet snapshots, health, and error classification.
- `redline_version` already separates firmware, wire, and hardware metadata.
- Native PlatformIO/Unity testing and compile-only DeviceConfig fixtures are
  established and should be extended rather than replaced.

### 5.2 Duplicated and coupled logic

- The RG logo bytes and `showHomeScreen()` layout are duplicated in both role
  files (`src-tx/main.cpp:40-67`; `src-rx/main.cpp:37-64`).
- `showStatus()`, `logVersionMetadata()`, and `logPacket()` are also duplicated,
  but Serial consolidation is not necessary to meet v0.3.0. Move only display
  duplication that blocks a shared screen shell.
- Both firmware loops mutate runtime phase directly at hardware-transition
  points. This is correct ownership; a screen controller must read a snapshot
  and never drive those transitions.
- Current `0.0F` metric defaults cannot distinguish “no packet yet” from a real
  measurement. v0.3.0 needs explicit availability.
- No counter or last-packet model exists. Serial log output is immediate and is
  not retained for later display.
- Display drawing accepts Arduino `String` and calls the OLED driver directly,
  preventing native testing of content selection and layout decisions.

### 5.3 Responsiveness hazards

- The normal Hub loop is nonblocking while it waits for radio interrupts and
  ACK deadlines, but uses scheduled transmit/retry timestamps
  (`src-tx/main.cpp:426-484`). Display work must fit around this polling.
- The Node intentionally blocks for 100 ms before ACK transmission
  (`src-rx/main.cpp:124-171`). v0.3.0 must preserve this established behavior
  and must not add display or button delays around it.
- Both roles use `delay(1000)` only when not ready
  (`src-tx/main.cpp:426-430`; `src-rx/main.cpp:328-332`). This means input and
  display cannot remain responsive in a fatal not-ready loop without changing
  that loop. **Recommendation:** replace only this error-loop delay with
  rollover-safe nonblocking polling during the display-integration step, while
  preserving the absence of radio work. This is a scheduling refactor, not new
  radio behavior, and needs a physical radio-init-failure check.
- OLED I2C transfer is synchronous. It cannot be made truly asynchronous with
  the current library, but limiting full-buffer flushes to dirty/periodic
  events avoids continuous traffic. The ThingPulse API separates buffer draws
  from the `display()` flush and provides `displayOn()`/`displayOff()`
  ([official ThingPulse API](https://github.com/ThingPulse/esp8266-oled-ssd1306#api)).

### 5.4 Ownership conflicts to avoid

- Do not copy active sequence, retry count, ACK deadline, or completion policy
  into `RuntimeState::State`. Expose them in a temporary presentation snapshot
  assembled by Hub firmware from `HubTransactionState`.
- Do not copy the Node duplicate key or remembered status into runtime state.
  A duplicate counter may be incremented after the evaluator returns
  `DUPLICATE`, but it is diagnostic only.
- Do not let display timeout change `ready`, runtime phase, radio mode, or
  transaction timing.
- Do not let a “degraded” presentation flag decide retries or acknowledgments.
- Do not duplicate `DeviceConfig`, protocol, or version constants in UI code.

### 5.5 Hardware-independent policy suitable for native tests

The following can be pure C++: saturating counter updates, packet snapshots,
health/error presentation state, raw-level/time-to-button-event classification,
screen cycling, home return, display timeout/wake state, dirty invalidation,
periodic refresh decisions, and role-specific presentation snapshots. GPIO
reads, `millis()`, Arduino strings, fonts, coordinates, and OLED calls remain
outside those components.

## 6. Proposed architecture

### 6.1 Component boundaries

**Recommendation:** Use three narrow reusable components and one
hardware-facing adapter:

```text
lib/runtime_state/src/runtime_state.h
    existing authoritative volatile presentation/diagnostic state

lib/device_input/src/device_input.h
    hardware-independent debouncer and semantic event classifier

lib/device_ui/src/device_ui.h
    screen/navigation state, display timeout, dirty scheduling,
    and fixed-size presentation snapshot types

lib/heltec_display/src/heltec_display.h
lib/heltec_display/src/heltec_display.cpp
    ThingPulse/Arduino adapter, RG asset, fonts, coordinates, drawing,
    displayOn/displayOff, and buffer flush
```

`heltec_display` is intentionally hardware-dependent and should be excluded
from native tests by PlatformIO dependency discovery or an explicit library
manifest/build filter only if discovery requires it. Do not add a new third-party
dependency; the existing ThingPulse library is sufficient.

Keep `src-tx/main.cpp` and `src-rx/main.cpp` as separate orchestration entry
points. Each samples GPIO and time, updates authoritative state after existing
radio outcomes, assembles a presentation snapshot, and asks the adapter to
render only when the UI policy requests it.

### 6.2 Explicit data flow

```text
hardware/radio activity
    -> existing transaction decision
    -> authoritative runtime-state update
    -> immutable presentation snapshot
    -> Heltec screen renderer
```

```text
raw GPIO level + uint32_t time
    -> DeviceInput::Button
    -> semantic button event
    -> DeviceUi::Controller navigation action
    -> display invalidation
    -> presentation snapshot
    -> Heltec screen renderer
```

The renderer must never read RadioLib, transaction-engine state, GPIO, or
`millis()` directly. Firmware creates the snapshot from the appropriate owners.

### 6.3 Proposed narrow APIs

Illustrative APIs, subject only to naming refinement during implementation:

```cpp
namespace DeviceInput {
enum class ButtonEvent : uint8_t {
    NONE, PRESS, RELEASE, SHORT_PRESS, LONG_PRESS
};

class Button {
public:
    Button(uint32_t debounceMs, uint32_t longPressMs);
    ButtonEvent update(bool pressed, uint32_t nowMs);
};
}
```

The implementation may queue at most the events produced by one sample (for
example `RELEASE` plus `SHORT_PRESS`) or expose a small result bitset. It must
not become a general event bus.

```cpp
namespace DeviceUi {
enum class Screen : uint8_t {
    HOME, RADIO, DEVICE, LAST_PACKET, DIAGNOSTICS, ABOUT
};

class Controller {
public:
    void handle(ButtonEvent event, uint32_t nowMs);
    RenderDecision update(uint32_t nowMs, bool liveDataChanged);
    void markDirty();
    Screen screen() const;
    bool displayAwake() const;
};
}
```

`RenderDecision` should distinguish no action, wake, render, and sleep. It
must not call hardware. Presentation data should use fixed-size fields and
availability flags so native tests do not depend on Arduino `String`.

## 7. Device-state model

### 7.1 Existing fields retained

Keep role, immutable identity snapshots, readiness, runtime phase, and radio
metrics. Add explicit metric validity rather than interpreting `0.0F` as
unavailable. `DeviceConfig::LOCAL_ID` and `DeviceConfig::PEER_ID` remain the
only configured identity authority (`include/device_config.h:15-23`).

### 7.2 Proposed diagnostic state

**Recommendation:** Add these volatile types to `runtime_state`:

```cpp
enum class Health : uint8_t { STARTING, READY, DEGRADED, ERROR };

enum class ErrorClass : uint8_t {
    NONE,
    RADIO_INITIALIZATION,
    RADIO_START_RECEIVE,
    RADIO_START_TRANSMIT,
    RADIO_READ,
    PACKET_LENGTH,
    PACKET_DECODE,
    PACKET_IGNORED,
    ACK_TIMEOUT,
    REMOTE_ACK,
    ACK_STATUS
};

struct LastPacket {
    bool available;
    Protocol::PacketType type;
    uint8_t source;
    uint8_t destination;
    uint8_t sequence;
    uint8_t opcode;
    uint8_t payloadLength;
    bool ackStatusAvailable;
    uint8_t rawAckStatus;
    uint32_t observedAtMs;
};

struct Counters {
    uint32_t transmissionsCompleted;
    uint32_t decodedPacketsReceived;
    uint32_t successfulTransactions;
    uint32_t acceptedCommands;
    uint32_t retransmissions;
    uint32_t acknowledgmentTimeouts;
    uint32_t duplicates;
    uint32_t malformedPackets;
    uint32_t ignoredPackets;
    uint32_t radioErrors;
};
```

Whether `runtime_state.h` should include `protocol.h` is an architectural
choice. **Recommendation:** Store packet type as a raw `uint8_t` in the state
snapshot to keep runtime state independent of the codec, and convert at the
firmware boundary. The UI can label recognized values without validating them.

### 7.3 Exact ownership and update points

All counters are presentation diagnostics, not transaction inputs. Use
saturating `uint32_t` increments so long-running displays do not wrap to a
misleading small value. Fresh construction resets all fields; persistence is
not part of v0.3.0.

| Field | Hub update point | Node update point | Meaning |
|---|---|---|---|
| `transmissionsCompleted` | TX-complete interrupt path, including retries | ACK TX-complete path | Radio operation completed; not delivery proof |
| `decodedPacketsReceived` | after successful ACK decode | after successful command decode | Decoded inbound packets, including later-ignored packets |
| `successfulTransactions` | matching `SUCCESS` ACK terminal path | not incremented / shown unavailable | End-to-end Hub result only |
| `acceptedCommands` | not incremented / shown unavailable | new `ACK_SUCCESS` outcome only | Valid new Node commands; duplicates excluded |
| `retransmissions` | when `attemptFailed()` returns `RETRANSMIT` | not applicable | Hub retry action, not initial TX |
| `acknowledgmentTimeouts` | each ACK deadline expiration before retry/failure decision | not applicable | Hub timeout events |
| `duplicates` | not applicable | evaluator returns `DUPLICATE` | Diagnostic mirror; tracker remains authoritative |
| `malformedPackets` | bad length/decode, malformed ACK payload/status | bad length/decode or malformed command payload | Packets rejected as malformed |
| `ignoredPackets` | decoded ACK evaluator returns an ignore outcome | decoded command evaluator returns an ignore outcome | Address/type/sender/sequence/opcode mismatch as applicable |
| `radioErrors` | start/read errors and CRC mismatch | start/read errors | Hardware/API failures; classification retained separately |

**Approved design decision:** Last Packet means the latest successfully decoded inbound
packet only: ACK on Hub, command on Node. This avoids a Node ACK immediately
overwriting the command an operator most needs to inspect. Record it immediately
after decode, before semantic evaluation, with the same RSSI/SNR sample and
`observedAtMs` supplied by firmware. Invalid encoded input updates error/counters
but does not fabricate packet fields. The snapshot has no direction field, no
TX history, and no separate TX/RX records. Presentation may label its content
`RX` because the contract is inbound-only.

`lastActivityAtMs` should update on completed TX or successfully read RX and is
presentation-only. It must not be used as an ACK deadline. Show age by
wrap-safe unsigned subtraction from a firmware-supplied current time.

### 7.4 Health and reachability

- `STARTING`: default before radio initialization completes.
- `READY`: radio initialized and normal role operation is available.
- `DEGRADED`: Hub exhausted retries or has a remote non-success result; Node
  may use this only for recoverable radio start/read failures. It must not infer
  Hub absence merely from silence because no Node polling cadence is defined.
- `ERROR`: unrecoverable startup/radio initialization failure.

**Approved design decision:** Do not add a stored `peerReachable` Boolean. For the Hub,
derive a presentation label from health/last terminal result. For the Node,
show peer state as `UNKNOWN` until a valid Hub command is received, then
`SEEN`; do not time it out in v0.3.0. A symmetric reachability flag would imply
policy the current Node cannot support.

## 8. Screen model

### 8.1 Common rules

Use exactly six top-level screens in a circular order:

```text
Home -> Radio -> Device -> Last Packet -> Diagnostics -> About -> Home
```

Short press advances one screen. Long press returns Home. No nesting, editable
values, or scrolling is required. Use the OLED's 128×64 bounds and existing
ThingPulse `ArialMT_Plain_10`/`ArialMT_Plain_16` fonts. Non-Home screens should
use a compact title plus no more than five small-font content rows. Truncate or
use fixed abbreviations; do not implement general scrolling.

### 8.2 Home

- **Purpose:** Stable role/readiness identity and RG branding.
- **Fields:** Existing RG mark, `RaveGoat Labs`, and `TX | READY` or
  `RX | READY`; degraded/error states replace only the bottom status text.
- **Role difference:** `TX` versus `RX` and role-specific health label.
- **Unavailable behavior:** Not applicable for core identity; startup uses
  `TX | START` / `RX | START` only if hardware validation approves the brief
  startup exposure.
- **Update:** health/readiness change, navigation to Home, display wake.
- **Static/live:** Stable in ordinary activity; no packet animation.
- **Layout:** Preserve the existing logo bytes, coordinates, title, fonts, and
  normal ready strings (`src-tx/main.cpp:40-67,413-414` and
  `src-rx/main.cpp:37-64,312-313`).

### 8.3 Radio

- **Purpose:** Current radio-facing phase and last valid link metrics.
- **Fields:** role, phase, RSSI, SNR, and Hub peer state (`REACHABLE`/
  `DEGRADED`) or Node peer observation (`UNKNOWN`/`SEEN`).
- **Role difference:** Hub phases are idle/transmitting/waiting; Node phases
  are listening/transmitting ACK.
- **Unavailable behavior:** RSSI and SNR render `--` until metric validity is
  true; never show default zero as a measurement.
- **Update:** phase, metric, health, or peer-observation change; periodic age
  refresh at most once per second while visible.
- **Static/live:** Live.

### 8.4 Device

- **Purpose:** Fixed identity and current role/readiness.
- **Fields:** role, local ID, peer ID, readiness/health, hardware profile.
- **Role difference:** values only; shared layout.
- **Unavailable behavior:** none; values come from DeviceConfig and
  `redline_version`.
- **Update:** navigation, wake, readiness/health change.
- **Static/live:** Mostly static.

### 8.5 Last Packet

- **Purpose:** Inspect the latest decoded inbound radio packet.
- **Fields:** packet type/direction, source→destination, sequence, opcode,
  payload length, and ACK status when the inbound packet is an ACK.
- **Role difference:** Hub normally shows ACK plus status; Node normally shows
  COMMAND and no ACK status.
- **Unavailable behavior:** `NO PACKET` until `LastPacket.available` is true;
  status displays `--` when unavailable.
- **Update:** each decoded inbound packet, navigation, wake.
- **Static/live:** Live on new packets.

### 8.6 Diagnostics

- **Purpose:** Show role-relevant counters and the latest error classification.
- **Hub fields:** TX completions, successful transactions, retries, timeouts,
  ignored/malformed total, last error.
- **Node fields:** RX decoded, accepted commands, ACK TX completions,
  duplicates, ignored/malformed total, last error.
- **Unavailable behavior:** Counter zero is meaningful; last error is `NONE`.
- **Update:** counter/error changes, navigation, wake.
- **Static/live:** Live. Use role-specific labels to avoid pretending unlike
  counters are equivalent.

### 8.7 About

- **Purpose:** Unambiguous build compatibility information.
- **Fields:** `ARGUS REDLINE`, firmware `v0.3.0` only after release metadata is
  finalized, Wire Protocol `1`, hardware `HELTEC_V4`, role.
- **Role difference:** role only.
- **Unavailable behavior:** none.
- **Update:** navigation or wake only.
- **Static/live:** Static.

**Approved design decision:** Development firmware uses `0.3.0-dev` after
implementation begins. Final `v0.3.0` metadata must not be applied until every
release-gate condition passes.

## 9. Input behavior

### 9.1 Verified V4 hardware facts

- **External hardware fact:** Heltec's official WiFi LoRa 32 V4.2 datasheet
  identifies header/control `0` as GPIO0 and the `PRG Button`
  ([official V4.2 datasheet](https://resource.heltec.cn/download/WiFi_LoRa_32_V4/datasheet/WiFi_LoRa_32_V4.2.0.pdf),
  pin-description table).
- **External hardware fact:** Heltec's official V4.3 schematic labels the user
  switch `S2` / `USER_Key`, connects that net to ESP32-S3 GPIO0, and switches
  it to ground
  ([official V4.3 schematic](https://resource.heltec.cn/download/WiFi_LoRa_32_V4/Schematic/HTIT-WB32LAF_V4.3.pdf)).
- **External hardware fact:** GPIO0 is an ESP32-S3 strapping pin. Espressif
  documents a default weak pull-up and low GPIO0 as part of download-boot
  entry; it recommends a pull-up and warns that strapping is sampled at reset
  ([official ESP32-S3 guidance](https://docs.espressif.com/projects/esp-techpedia/en/latest/esp-friends/get-started/try-firmware/try-firmware-hardware/esp32s3.html),
  [hardware design guidelines](https://docs.espressif.com/projects/esp-hardware-design-guidelines/en/latest/esp32s3/esp-hardware-design-guidelines-en-master-esp32s3.pdf)).
- **Repository assumption:** The project board profile is generic
  `heltec_wifi_lora_32_V4`; the custom variant does not define the button
  (`boards/heltec_wifi_lora_32_V4.json:24-48`,
  `variants/heltec_V4/pins_arduino.h:59-68`). The physical regression record
  must record whether each board is V4.2, V4.3, or another V4 revision.

### 9.2 Approved electrical and timing contract

```text
application button pin       GPIO0
released level               HIGH
pressed level                LOW
firmware pin mode            INPUT_PULLUP
debounce interval            30 ms
long-press threshold         800 ms after debounced press
double press                deferred from v0.3.0
sampling                     once per loop, never from an ISR
time type                    uint32_t milliseconds
```

Use wrap-safe unsigned elapsed-time subtraction. A debounced `PRESS` occurs
after the raw active-low state remains pressed for 30 ms. Emit `LONG_PRESS`
once at 800 ms. On debounced release, emit `RELEASE`; if no long press was
emitted, also classify a `SHORT_PRESS`. Navigation consumes `SHORT_PRESS` and
`LONG_PRESS`; `PRESS`/`RELEASE` remain observable/testable input events but do
not navigate directly.

If the button is already held when firmware input initialization begins, seed
the raw and stable state without emitting a synthetic press or long press.
Require a full debounced release before accepting the next press. Holding GPIO0
during reset may select the ESP32-S3 download boot path; this hardware behavior
cannot be hidden by runtime firmware and must be documented in the operator
test procedure.

**Approved design decision:** Double press is not implemented, emitted, consumed,
or assigned an action in v0.3.0. The input classifier therefore does not delay
`SHORT_PRESS` while waiting for a second press.

## 10. Display scheduling

### 10.1 Approved policy

- Poll input and service radio logic on every `loop()` iteration.
- Mark the display dirty on screen change, wake, health/readiness change,
  relevant state update, or newly decoded packet.
- Flush immediately when dirty only if at least 100 ms has elapsed since the
  previous flush: maximum 10 full OLED refreshes per second.
- While a live screen is visible, request a periodic refresh no more than once
  per second for activity age; Home, Device, and About need no periodic refresh.
- Use a 30-second inactivity timeout measured from semantic input. Timeout
  calls `displayOff()` once and sets presentation power state only.
- Any debounced press wakes the display and consumes that gesture for wake;
  the following gesture navigates. This prevents an invisible navigation jump.
- Ordinary radio activity updates state and dirty flags but does not wake the
  OLED. With Hub traffic every three seconds, radio wake would prevent timeout
  permanently and cause distracting activity.
- When awake, radio updates may refresh the currently visible live screen,
  subject to the 10 Hz cap. They must not change the selected screen.
- Display timeout never sleeps the ESP32-S3, gates `Vext`, resets OLED, changes
  radio state, or alters transaction state. Only use the OLED driver's
  `displayOff()`/`displayOn()` API.

### 10.2 Radio-path invariants

No display call may introduce `delay()`. During Hub transmit, ACK wait, retry,
or terminal processing and during Node receive, pre-ACK delay, ACK transmit, or
receive restart, radio orchestration retains priority. A pending render may be
performed only after the existing path returns to `loop()` and must remain
bounded by the refresh policy.

The display never calls `radio.getRSSI()`, `radio.getSNR()`, or any RadioLib
method. Firmware captures metrics at the existing points and updates runtime
state first (`src-tx/main.cpp:293-317`; `src-rx/main.cpp:227-237`).

**Remaining implementation risk:** The approved 10 Hz maximum dirty-render rate
and 1 Hz maximum live-data refresh rate are project policy, not verified hardware
limits. Physical tests must measure
whether a full 128×64 I2C flush causes a receive gap. Lower the refresh rate,
not the radio service rate, if interference is observed.

## 16. Risks and remaining implementation decisions

| Item | Evidence/risk | Approved decision or required control |
|---|---|---|
| Exact board revision | Repository says generic V4; official V4.2 and V4.3 both map the user/program key to GPIO0, but physical revisions are not recorded | Record silkscreen/revision for both boards before implementation hardware checks |
| GPIO0 boot strap | Active-low button is also download-boot strap | Approved: use only after boot with `INPUT_PULLUP`; document held-at-reset behavior; never attach a boot-time operational guarantee |
| Double press | No current action needs it; it would delay short-press resolution and complicate precedence | Approved: deferred from v0.3.0 |
| Display timeout | Roadmap requires behavior but gives no duration | Approved: 30 seconds as volatile compile-time policy; persistence belongs to v0.4.0 |
| Screen order | Roadmap lists screens but not navigation order | Approved: the six-screen circular order in Section 8 |
| Counter overflow | Long-running volatile counters can wrap | Approved: saturate `uint32_t`; show maximum without wrap |
| Counter semantics | “sent” can mean requested, accepted, or completed | Use completed radio operations and explicit role-specific labels as Section 7 defines |
| Peer reachability | Node has no keepalive expectation and cannot infer absence safely | Approved: Hub derives reachable/degraded from transaction result; Node shows UNKNOWN/SEEN only |
| Radio activity wake | Hub traffic every three seconds would keep OLED awake | Approved: do not wake on radio; update dirty state only |
| Refresh rate | OLED flush is synchronous and no timing measurement exists | Approved: max 10 Hz dirty render / 1 Hz live refresh; measure physically and reduce OLED rate if needed |
| Unavailable metrics | Current defaults are zero with no validity | Add explicit validity and show `--` |
| Navigation parity | Same screens are useful, but counter content differs | Use identical navigation/order with role-specific presentation content |
| Fatal not-ready delay | Current 1000 ms delay blocks local input/error refresh | Replace only with nonblocking error-loop scheduling during integration and test radio-init failure; do not change radio recovery policy |
| Last Packet meaning | Latest TX would overwrite useful Node RX immediately | Approved: latest successfully decoded inbound packet only; no direction field or TX history |
| OLED text fit | 128×64 and current fonts leave limited rows; native tests cannot prove pixels | Use fixed abbreviated rows, no scrolling, and photograph every screen on both boards |
| Final firmware version | Final metadata before validation would overstate completion | Approved: use `0.3.0-dev` after implementation begins; set final `v0.3.0` only after the release gate passes |

The GPIO0 mapping, active-low behavior, and strapping role are externally
verified. GPIO mode, thresholds, screen order, timeout, refresh cadence,
counter saturation, inbound-only Last Packet semantics, peer-state semantics,
gesture mapping, and development-version policy are approved project design
decisions. Physical timing, OLED fit, exact board revisions, and absence of
