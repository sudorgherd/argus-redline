# ARGUS REDLINE v0.2.0 Release Notes

**Status:** Release preparation; no tag or published release has been created.

ARGUS REDLINE v0.2.0 establishes the firmware architecture and native-test foundation for the existing single-Hub/single-Node system. It does not add new application behavior or expand the network topology.

## Highlights

- Packaged the Protocol v0.1 codec as the reusable `redline_protocol` component while preserving the compatibility header.
- Separated firmware-version reporting from Wire Protocol reporting and centralized the `HELTEC_V4` hardware profile.
- Added native characterization coverage for exact packet bytes, codec validation, protocol constants, and version metadata.
- Extracted Node single-entry duplicate tracking, regenerated ACK construction, and command evaluation into hardware-independent transaction logic.
- Extracted Hub ACK evaluation plus retry, timeout, and sequence state into the same reusable transaction component.
- Added authoritative hardware-independent runtime state for role, identity exposure, readiness, phase, RSSI, and SNR.
- Added compile fixtures for valid Hub/Node device identities and expected failures for missing or equal IDs.
- Consolidated the Hub and Node entry points around hardware orchestration without changing their radio behavior.
- Documented and completed the physical two-board desk regression.

## Compatibility

- Firmware identifier: `v0.2.0`.
- Protocol v0.1 continues to use Wire Protocol version `1`.
- Hardware profile remains `HELTEC_V4`.
- Wire Protocol version 1 remains byte-compatible: packet layouts, exact encoded bytes, packet-type values, `TEST=0x64`, ACK-status values, addressing, validation order, retry timing, sequence behavior, and duplicate semantics are unchanged.
- The codec recognizes `COMMAND`, `ACK`, and `ERROR`; current firmware actively uses only `COMMAND` and `ACK`.
- Duplicate detection remains single-entry, in-memory, keyed by source/sequence/opcode, and volatile across restart. Duplicate ACKs are regenerated from remembered transaction metadata and status rather than replayed from an encoded-packet cache.

## Physical regression

The two Heltec WiFi LoRa 32 V4 boards successfully completed repeated Protocol v0.1 `TEST`/ACK exchanges using the `0.2.0-dev` build before final version selection. The regression verified:

- correct Hub `0x01` and Node `0x10` addressing;
- matching TEST opcode and sequence values;
- successful one-byte ACK behavior;
- RSSI and SNR diagnostics on both devices;
- normal OLED behavior;
- exactly two retransmissions after an unavailable Node;
- terminal failure after retry exhaustion;
- automatic communication recovery after restoring the Node;
- continued operation without observed unexpected resets, hangs, crashes, or radio-state failures.

The boards were also physically reset while PlatformIO `log2file` monitors were active. Both native USB CDC sessions disconnected and re-enumerated, the Hub sequence restarted, and both boards resumed correct communication.

## Evidence limitations

- The early startup metadata lines were not retained because the PlatformIO monitors reattached after USB CDC re-enumeration. The literal lines are not claimed as observed. Firmware `0.2.0-dev`, Wire Protocol `1`, and `HELTEC_V4` were verified for the physically tested build through compilation and native tests.
- Physical duplicate-packet injection: **NOT TESTED**. Mandatory native tests cover the single-entry duplicate decision and regenerated-ACK semantics; production firmware was not modified to force this case.
- The physical regression used `0.2.0-dev`. Final `v0.2.0` selection changes only the firmware identifier; final binaries are rebuilt and retested in software during release preparation.
