# ARGUS REDLINE v0.7.0 Architecture Baseline

**Status:** Normative pre-implementation architecture baseline  
**Baseline release:** `v0.6.0` — Structured Operations, Responses, and Host Protocol  
**Target milestone:** `v0.7.0` — Node-Originated Events and Reliable Delivery  
**Wire Protocol:** `1` at entry; any change requires compatibility analysis  
**Configuration Schema:** `1`  
**Host Protocol:** developmental `0.1` at entry  
**Hardware profile:** `HELTEC_V4`

## 1. Purpose

This document fixes the architectural entry state and constraints for v0.7.0.
It defines what released v0.6.0 already does, what v0.7.0 may extend, and what
`V0.7.0_EVENT_RELIABILITY_DESIGN.md` must decide. It does not claim that any
v0.7.0 behavior is implemented or select final Event bytes, identifiers, queue
geometry, storage records, retry constants, expiry rules, arbitration policy,
or Host frames.

Normative `MUST`, `MUST NOT`, `SHOULD`, and `MAY` statements constrain the
future design and implementation.

## 2. Source-of-Truth Baseline

The entry authority is the released v0.6.0 source, normative design package,
release and qualification evidence, with current source taking precedence over
older handoffs. The authoritative roadmap owns milestone scope.

| Dimension | Entry value | Meaning |
|---|---:|---|
| Firmware release | `v0.6.0` | Released application milestone |
| Wire Protocol | `1` | LoRa packet encoding/namespace |
| Configuration Schema | `1` | Ordinary persistent settings |
| Host Protocol | `0.1` | Developmental computer-to-Hub interface |
| Hardware profile | `HELTEC_V4` | Qualified board/capability profile |

These versions are independent. A v0.7.0 firmware release does not
automatically increment any protocol or schema.

## 3. Released v0.6.0 Architecture

v0.6.0 is a qualified direct one-Hub/one-Node system. The Wire codec owns
packet bounds and validation; Hub transaction logic owns one bounded
Hub-originated operation; Node admission owns validation, exact duplicate
recognition, execution admission, and ACK/RESPONSE generation; capabilities
own logical IDs, authorization, validation, interlocks, and hardware dispatch;
Host Protocol 0.1 owns bounded machine framing and correlated operations;
runtime state owns observable state; UI observes that state; and Configuration
Schema 1 settings use bounded dual-slot storage and recovery.

Foreground orchestration explicitly services radio, Host, UI, input,
capabilities, and storage. The radio ISR only raises a flag. Hardware and
storage access remain outside interrupt context.

Released Wire bounds and packet types are:

```text
header                 6 bytes
maximum packet        32 bytes
maximum payload       26 bytes

COMMAND   = 0x01
ACK       = 0x02
ERROR     = 0x03
RESPONSE  = 0x04
```

v0.6.0 actively uses COMMAND, ACK, and RESPONSE for structured operations.
ERROR remains recognized but is not their completion mechanism. This baseline
does not assign an EVENT numeric value.

## 4. Existing Transaction Model

```text
Hub initiates structured operation
        |
        v
Node validates and admits COMMAND
        |
        v
Node sends ACK
        |
        v
Node executes one bounded operation
        |
        v
Node sends RESPONSE
        |
        v
Hub correlates and completes transaction
```

ACK means transport receipt/admission, never application completion. RESPONSE
is structured operation completion. Existing correlation, bounded retry,
timeout, and receive-restoration behavior remains authoritative.

Node duplicate matching uses the exact retained admitted command: source,
sequence, opcode, payload length, and meaningful payload bytes. Complete
admission/structural validation precedes duplicate lookup. A duplicate is not
executed again; retained ACK and completed RESPONSE are regenerated. This
single-entry state is bounded and volatile, so it is not durable Event
deduplication.

## 5. Architectural Change Introduced by v0.7.0

v0.7.0 adds the first normal Node-originated structured application traffic:

```text
local Node event source
        |
        v
bounded Event creation
        |
        v
persistent Event identity
        |
        v
bounded outbound queue
        |
        v
radio arbitration
        |
        v
EVENT transmission
        |
        v
Hub receipt / deduplication
        |
        v
delivery acknowledgment
        |
        v
queue lifecycle completion
```

This is architectural direction, not a packet/state-machine specification.
The design MUST support origination without a Hub command, retransmission after
a lost acknowledgment without duplicate Hub processing, reboot survival for
important queued Events, bounded queue behavior, predictable expiry, and
locally visible Hub unavailability.

The key change is initiative: either side may need the half-duplex radio.
Existing Hub operation ownership is preserved while independent Event
ownership and arbitration are added.

v0.7.0 MAY extend only the Wire/Event codec, Node Event runtime and separate
storage, Hub Event admission/deduplication, explicit radio orchestration,
runtime diagnostics/UI presentation, bounded input/capability source adapters,
and a versioned Host boundary. It may not broaden hardware authority or embed
application workflows in transport.

## 6. Radio Ownership and Arbitration Boundary

The design MUST define explicit, auditable radio ownership and reconcile Event
work with continuous Node receive, Hub COMMAND operations, Node ACK/RESPONSE
transmission, Hub ACK/RESPONSE waits and retries, UI, storage, Host service,
input service, and flag-only radio interrupts.

It MUST define Event-transmit eligibility, priority, busy/collision behavior,
receive restoration, pending-work preservation, and service safe points. It
MUST NOT hide timing-sensitive orchestration inside an oversized generic
scheduler/framework. This baseline does not choose the arbitration algorithm.

## 7. Event Identity and Reliability Boundary

Persistent Event identity is new. The eight-bit Wire sequence is a wrapping
transport correlation value and MUST NOT alone serve as durable Event identity.
Existing command duplicate mechanisms are insufficient because their state is
bounded, substantially volatile, and represents Hub-originated commands.

The detailed design MUST define durable Event identity, retransmission
identity, reboot recovery, the Hub deduplication key, ID allocation and
wrap/exhaustion/reuse behavior, corruption behavior, and persistence scope.
Identity must remain stable wherever an Event may be recovered and retried.

At least the roadmap lifecycle must be represented:

```text
queued -> transmitting -> acknowledged
   |            |
   +----------> failed
   +----------> expired
```

Exact states and terminal-record rules are deferred. Delivery acknowledgment
must also be distinguished from Host/application consumption.

## 8. Persistence and Storage Boundary

Configuration Schema 1 holds ordinary preferences. Event queue records are a
different transport/delivery persistence domain.

- Ordinary settings and Event storage MUST remain distinct.
- Queued Events MUST NOT be inserted into the settings record merely because
  storage infrastructure exists.
- Event persistence MUST have its own bounded record, capacity, lifecycle,
  version/recovery, and ownership design.
- Writes, erases, validation, and recovery MUST remain outside ISR context and
  coordinated with radio service.
- The design MUST account for flash endurance, unnecessary writes, torn writes,
  power loss, corruption, partial recovery, and deterministic post-reboot state.

Important queued Events must survive Node reboot. That does not imply every
Event is persistent. Exact format, commit scheme, and importance/retention
policy belong to the detailed design.

## 9. Hub Duplicate-Processing Boundary

The Hub MUST process a retransmitted Event only once within the defined
reliability contract. Validation MUST precede deduplication-state mutation or
application-visible delivery.

The design MUST define exact admission, canonical identity/content comparison,
identity/content mismatch behavior, truthful acknowledgment conditions,
bounded duplicate retention, Hub reboot/state-loss behavior, and reclamation.
It must distinguish radio receipt, Hub acceptance/retention, Host exposure, and
application consumption.

Duplicate suppression MUST NOT silently discard a new Event after ambiguous
identity collision or acknowledge custody the Hub did not assume.

## 10. Queue and Resource-Governance Boundary

The design MUST specify maximum queue depth, persistent storage use, Event
payload, overflow and retention policies, retry bounds, expiry, priority (if
any), flash-write behavior, and failure visibility.

Queue-full behavior MUST be deterministic, locally visible, diagnosable, and
explicit about which Event is retained/rejected. Numeric limits must be
justified against the 26-byte payload, RAM, flash/endurance, timing, and
qualification evidence.

v0.7.0 MUST NOT introduce unbounded queues/allocation, indefinite retries,
implicit bulk storage, or a general workflow runtime.

## 11. Event Expiry and Time Authority

A persisted Event may survive reboot while volatile monotonic `millis()` cannot
measure powered-off time. The current baseline provides no RTC, GNSS time
guarantee, or synchronized wall clock.

The detailed design MUST define expiry meaning, lifetime start, which waits
consume lifetime, powered-on time authority, reboot/reset/wrap behavior,
powered-off-time limitations, and deterministic cleanup/diagnostics. It MUST
NOT claim knowledge of powered-off elapsed time without a real authority.
Expired Events MUST NOT remain in retry loops.

## 12. Host Protocol Boundary

Host Protocol 0.1 supports synchronous v0.6.0 structured operations; it does
not define unsolicited Node Event delivery.

The design MUST decide whether to add a compatible/versioned asynchronous
Event message, add bounded polling/retrieval, or deliberately defer host-visible
delivery. It MUST preserve bounded framing, recovery, negotiation, independent
Host versioning, and distinguish:

```text
radio receipt -> Hub acceptance -> Host delivery -> application consumption
```

Transport receipt is not application consumption. No Host Event frame,
operation, version, or ownership-transfer rule is defined here.

## 13. Runtime, UI, and Diagnostics Boundary

Runtime state remains the observable authority. The design MUST define bounded,
unambiguously owned state/counters for queue use/rejection, Event attempts,
acknowledgment, failure, expiry, duplicates, persistence recovery, and Hub
unavailability as applicable.

Hub-unavailable state MUST be shown locally, with explicit evidence for setting
and clearing it. UI remains observational: screen/input behavior MUST NOT own
delivery, arbitration, persistence, or retries and must remain nonblocking.
Unclassifiable radio corruption must not be mislabeled as an Event failure.

## 14. Capability and Event-Source Boundary

Event transport is separate from Event-source semantics:

```text
bounded source observation -> validated creation request -> Event transport
```

Button presses, sensor thresholds, status changes, device errors, manual
check-ins, and bounded compiled policies may create Events. Each source must
define bounded data, emission conditions, and queue-rejection handling, and
must not bypass identity, admission, persistence, or arbitration.

Existing logical-ID, authorization, validation, interlock, and hardware-profile
boundaries remain intact. Compiled policies are bounded firmware behavior, not
downloaded code, scripts, bytecode, transferred procedures, or a workflow
engine. This milestone does not define ARGUS, BLACKSHEEP, surveillance,
incident, panic, or duress product semantics.

## 15. Security Boundary

Wire Protocol 1 remains unauthenticated and unencrypted. Open requirements are
F-02 peer authentication, F-03 authentication-first discard/response
governance, and F-04 authenticated persistent freshness/replay protection.
v0.7.0 MUST NOT silently solve, redefine, or claim closure of them.

- Reliable Event identity is not cryptographic replay protection.
- Hub duplicate suppression is not peer authentication.
- Persisted Event IDs are not credentials or authenticators.
- Routing/device IDs remain unauthenticated identifiers.
- Event ACK/retry does not prove an authentic peer.
- Unauthenticated traffic MUST NOT gain dangerous side-effect authority merely
  because it is represented as an Event.

The design must assess abuse of queue, persistence, response, deduplication,
and radio resources without designing cryptography. Roadmap ownership of
identity/provisioning remains v0.8.0 and authenticated transport/security
remains v0.9.0 unless the roadmap is explicitly revised.

## 16. Compatibility and Versioning Constraints

Wire Protocol 1 is the entry baseline, not a predetermined exit decision. An
additive Event type may remain compatible, or analysis may require a version
change. The detailed design MUST record that analysis before assigning EVENT a
numeric value.

Existing packet values and meanings MUST NOT be reassigned. Existing
COMMAND/ACK/RESPONSE operations, ACK-versus-RESPONSE semantics, Wire bounds,
Host Protocol independence, Configuration Schema 1 ordinary settings, and
separate reporting of all version dimensions MUST remain valid unless an
explicit versioned change deliberately replaces them.

No Event packet value, opcode, layout, Host version, or Configuration Schema
change is established here.

## 17. Explicit v0.7.0 Non-Goals

- Production panic or duress workflows.
- Product-specific ARGUS/BLACKSHEEP or surveillance semantics.
- General workflow transfer, scripts, bytecode, or downloaded procedures.
- Multi-hop forwarding, relays, routing, or mesh.
- Bulk/opaque application storage or a general workflow runtime.
- Unrestricted GPIO/hardware authority.
- Cryptography, credentials, authenticated transport, or security replay
  protection.
- v0.8.0 identity/provisioning behavior.
- A general Host service or application business-meaning engine.
- Life-safety or guaranteed-delivery claims.

## 18. Decisions Deferred to V0.7.0_EVENT_RELIABILITY_DESIGN.md

`docs/V0.7.0_EVENT_RELIABILITY_DESIGN.md` MUST settle:

1. EVENT semantics/value and the compatibility/Wire-version decision.
2. Exact envelope, payload, type registry, validation, and error behavior.
3. Persistent Event-ID format/lifecycle, reboot, wrap, and corruption behavior.
4. Node queue record/state model, capacity, ordering, retention, and deletion.
5. Persistent format, bounded use, endurance, torn-write and recovery design.
6. Overflow policy and source-visible admission results.
7. Retry schedule/bounds, timeouts, backoff, failure, and unavailability rules.
8. ACK/Event matching and lost/late/duplicate/malformed acknowledgment behavior.
9. Hub admission, duplicate retention, capacity, mismatch, and processing scope.
10. Hub reboot and the boundary between acceptance and application consumption.
11. Expiry semantics and time authority, including powered-off time.
12. Radio arbitration, priority, busy behavior, and receive restoration.
13. Runtime counters, local presentation, and Hub-unavailable evidence.
14. Initial Event-source interfaces and release slice.
15. Host exposure/deferral, framing, negotiation, ownership, and Host version.
16. Exact native, integration, fault/reboot/power-loss, compatibility, build,
    and two-board physical qualification requirements.

## 19. Required Regression Invariants

Existing native and physical qualification become v0.7.0 regression
requirements. The later design/brief MUST preserve and retest:

- Wire bounds, malformed rejection, and existing encodings;
- TEST/ACK and structured COMMAND/ACK/RESPONSE behavior;
- Hub correlation, bounded retry/timeout, and receive restoration;
- validation-before-duplicate handling and no duplicate re-execution;
- Host Protocol 0.1 framing, negotiation, recovery, bounded lifecycle, and
  retained results unless negotiated versioning deliberately extends them;
- capability registry, logical IDs, authorization/validation ordering,
  interlocks, and production denial of unauthenticated remote side effects;
- Configuration Schema 1 validation, defaults, dual-slot recovery/reset, and
  bounded writes;
- nonblocking observational UI/input behavior;
- flag-only ISR and foreground-only radio/hardware/storage service;
- bounded/static resources and saturating diagnostics; and
- the qualified HELTEC_V4 direct one-Hub/one-Node physical baseline.

Any incompatibility must be deliberate, isolated, versioned, documented, and
qualified rather than introduced as an incidental Event detail.

## 20. Baseline Conclusion

v0.7.0 adds a second, Node-originated structured traffic direction to released
v0.6.0. It must provide bounded reliable Event delivery, persistent identity,
reboot survival for important queued Events, duplicate-safe Hub processing,
predictable failure/expiry, and visible unavailability while preserving
existing operations and explicit radio orchestration.

Exact Wire, identity, queue, storage, retry, expiry, arbitration, Host,
diagnostic, and qualification decisions belong to
`docs/V0.7.0_EVENT_RELIABILITY_DESIGN.md` and must be accepted before firmware
implementation begins.
