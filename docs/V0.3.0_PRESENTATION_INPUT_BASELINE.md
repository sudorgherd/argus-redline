# ARGUS REDLINE v0.3.0 Presentation and Input Baseline

## 1. Purpose

This document records the interface baseline that exists before any v0.3.0 UI
or input implementation. It characterizes the released v0.2.0 firmware source
as inherited by the `v0.3.0-device-runtime-ui` branch. It does not implement or
claim any planned v0.3.0 screen, input, counter, timeout, or presentation
behavior.

The repository source is authoritative for implemented behavior. The approved
[v0.3.0 implementation brief](V0.3.0_IMPLEMENTATION_BRIEF.md) is authoritative
for future work after this characterization step.

## 3. Current OLED hardware configuration

### 3.1 Construction and pins

Both roles construct the same global display object:

```cpp
SSD1306Wire display(0x3C, SDA_OLED, SCL_OLED);
```

The constructor appears at `src-tx/main.cpp:11` and `src-rx/main.cpp:11`.
The custom Heltec V4 variant defines the relevant pins as
`SDA_OLED = 17`, `SCL_OLED = 18`, and `RST_OLED = 21`
(`variants/heltec_V4/pins_arduino.h:59-63`). The configured I2C address is
`0x3C`.

### 3.2 Power, reset, and initialization order

Hub and Node perform the same setup sequence
(`src-tx/main.cpp:380-400`; `src-rx/main.cpp:279-299`):

1. Start Serial at 115200 baud.
2. Configure `LED_BUILTIN`, `Vext`, and `RST_OLED` as outputs.
3. Drive the LED LOW.
4. Drive `Vext` LOW.
5. Delay 100 ms.
6. Drive `RST_OLED` LOW.
7. Delay 20 ms.
8. Drive `RST_OLED` HIGH.
9. Delay 20 ms.
10. Call `display.init()`.
11. Initialize the radio SPI bus.
12. Call `radio.begin(915.0)`.

**Verified repository fact:** The firmware drives `Vext` LOW before resetting
and initializing the OLED. This document records the source-level level and
ordering; it does not independently prove the board's electrical Vext polarity.

The board manifest selects the ESP32-S3 Heltec V4 variant and 16 MB flash
(`boards/heltec_wifi_lora_32_V4.json:2-25,39-48`). The production configuration
uses the ThingPulse SSD1306 library and RadioLib
(`platformio.ini:4-16`).

## 4. Current Home-screen composition

### 4.1 Bitmap and ownership

Each role owns a separate, byte-for-byte identical definition of
`rgLogo26x16` in its own `main.cpp` (`src-tx/main.cpp:40-46` and
`src-rx/main.cpp:37-43`). The array contains 64 bytes and is stored with
`PROGMEM`. It is drawn as a 26×16 XBM.

The bitmap remains duplicated; Step 1 does not move it or reproduce its full
byte array in tests or documentation.

### 4.2 Exact drawing sequence

Both `showHomeScreen(const String& status)` implementations perform the same
operations and one final buffer flush (`src-tx/main.cpp:48-67` and
`src-rx/main.cpp:45-64`):

| Order | Operation | Exact value or coordinates |
|---:|---|---|
| 1 | Clear local display buffer | `display.clear()` |
| 2 | Select white | `setColor(WHITE)` |
| 3 | Draw logo background | `fillRect(48, 0, 32, 32)` |
| 4 | Select black | `setColor(BLACK)` |
| 5 | Draw RG XBM | `drawXbm(51, 8, 26, 16, rgLogo26x16)` |
| 6 | Select white | `setColor(WHITE)` |
| 7 | Center text | `setTextAlignment(TEXT_ALIGN_CENTER)` |
| 8 | Select title font | `ArialMT_Plain_16` |
| 9 | Draw title | `(64, 34)`, `RaveGoat Labs` |
| 10 | Select status font | `ArialMT_Plain_10` |
| 11 | Draw supplied status | `(64, 53)`, caller-provided string |
| 12 | Flush buffer to OLED | `display.display()` |

The Home implementations are identical except for the caller-provided status
text. The function name, drawing primitives, colors, alignment, fonts,
coordinates, title, and bitmap are otherwise the same.

### 4.3 Normal role appearance

- Hub calls `showHomeScreen("TX | READY")` after successful radio
  initialization (`src-tx/main.cpp:411-421`).
- Node calls `showHomeScreen("RX | READY")` after successful radio
  initialization and before its initial `startListening()` call
  (`src-rx/main.cpp:310-324`).

The settled normal screen therefore uses the same RG-branded composition with
only `TX | READY` versus `RX | READY` distinguishing the role.

## 5. Current OLED call locations

Every current OLED method call is either inside `showHomeScreen()` or inside
`setup()`. Neither interrupt callback contains an OLED call, and neither normal
`loop()` path directly or indirectly calls `showHomeScreen()`.

| Role | Function/path | Trigger | Buffer drawing | `display()` flush | Ordinary transaction processing |
|---|---|---|---|---|---|
| Hub | `setup()` → `display.init()` | Every boot after Vext/reset sequence | No Home content | No explicit `display()` call | No |
| Hub | `setup()` → `showHomeScreen("RADIO ERR " + state)` | `radio.begin(915.0)` fails | Yes, complete Home composition | Yes, exactly once | No; setup returns |
| Hub | `setup()` → `showHomeScreen("TX | READY")` | Radio initialization succeeds | Yes, complete Home composition | Yes, exactly once | No; startup only |
| Node | `setup()` → `display.init()` | Every boot after Vext/reset sequence | No Home content | No explicit `display()` call | No |
| Node | `setup()` → `showHomeScreen("RADIO ERR " + state)` | `radio.begin(915.0)` fails | Yes, complete Home composition | Yes, exactly once | No; setup returns |
| Node | `setup()` → `showHomeScreen("RX | READY")` | Radio initialization succeeds | Yes, complete Home composition | Yes, exactly once | No; startup only |
| Node | `setup()` → `showHomeScreen("RX START ERR")` | Initial `startListening()` fails | Yes, complete Home composition | Yes, exactly once | No; setup failure handling |

Within each `showHomeScreen()` invocation, all buffer drawing calls listed in
Section 4 execute before the single `display.display()` flush. There are no
other calls to `display.clear()`, `setColor()`, `fillRect()`, `drawXbm()`,
`setTextAlignment()`, `setFont()`, `drawString()`, or `display.display()` in
production source.

## 6. Current error presentation

Only these conditions alter the OLED:

| Role | Condition | OLED status text | Resulting control flow |
|---|---|---|---|
| Hub | `radio.begin(915.0)` returns an error | `RADIO ERR <state>` | `setup()` returns; readiness remains false |
| Node | `radio.begin(915.0)` returns an error | `RADIO ERR <state>` | `setup()` returns; readiness remains false |
| Node | First `startListening()` after ready screen fails | `RX START ERR` | readiness is set false; setup ends |

These paths are at `src-tx/main.cpp:400-408` and
`src-rx/main.cpp:299-325`.

Runtime transmit-start failures, receive-start failures after setup, malformed
packets, CRC/read failures, ACK timeouts, invalid ACK status, ignored packets,
remote ACK errors, retry exhaustion, duplicate commands, and successful
transactions are reported through Serial and sometimes the built-in LED. They
do not redraw the OLED. `showStatus()` is a Serial-only helper
(`src-tx/main.cpp:69-78`; `src-rx/main.cpp:66-75`).

## 7. Current transaction/display relationship

- Transaction phases do mutate `RuntimeState::State` in both roles.
- Transaction phase mutations do not redraw or flush the OLED.
- The OLED and Home status do not participate in packet validation, ACK
  classification, duplicate handling, retry decisions, sequence advancement,
  timing, or radio state selection.
- Ordinary radio traffic causes no display refresh.
- The radio-completion interrupt callback only sets `operationDone = true` and
  makes no display call (`src-tx/main.cpp:36-38`;
  `src-rx/main.cpp:33-35`).
- The OLED remains on the last setup-rendered Home or setup-error composition
  during ordinary runtime operation.

The current transaction/display relationship is therefore one-way only during
setup: radio initialization results select a startup Home/error string. Normal
transaction state is not presented on the OLED.

## 8. Current input behavior

### 8.1 Source search result

No application input is implemented. A repository-wide search of production
source, headers, libraries, variants, board definitions, and tests found:

- no GPIO0 reference;
- no application button, user-key, or button-event symbol;
- no `digitalRead()` call;
- no input `pinMode()`;
- no GPIO input interrupt;
- no debounce state or timing;
- no short-, long-, or double-press classifier;
- no screen, menu, or navigation state.

The only `pinMode()` calls configure `LED_BUILTIN`, `Vext`, and `RST_OLED` as
outputs during setup (`src-tx/main.cpp:383-385`;
`src-rx/main.cpp:282-284`). The only firmware interrupt registration is
RadioLib's `radio.setDio1Action(setRadioFlag)`
(`src-tx/main.cpp:411`; `src-rx/main.cpp:310`).

### 8.2 Variant and board scope

The custom `heltec_V4` variant does not define a button alias. It defines the
LED, serial, generic I2C/SPI/analog/touch pins, Vext, OLED, and LoRa pins
(`variants/heltec_V4/pins_arduino.h:9-68`). The board JSON selects that variant
but adds no application-button definition
(`boards/heltec_wifi_lora_32_V4.json:8-25`).

**Approved future behavior, not current behavior:** The v0.3.0 brief selects
GPIO0 as an active-low application button using `INPUT_PULLUP` and specifies
debounce and gesture rules. None of that behavior exists at this baseline.
Physical GPIO0 mapping, electrical behavior, switch bounce, and held-at-boot
behavior are not proven by the repository source and remain hardware-validation
items for later implementation steps.

## 9. Current runtime-state model

### 9.1 Fields and defaults

`RuntimeState::State` is hardware-independent
(`lib/runtime_state/src/runtime_state.h:1-83`). Its complete current field set is:

| Field | Type | Default/constructor value | Mutation owner and locations | Meaning |
|---|---|---|---|---|
| `role_` | `DeviceRole` | Constructor argument: `HUB` or `NODE` | Construction only; no setter | Immutable role snapshot for runtime/presentation use |
| `localId_` | `uint8_t` | Constructor argument from `DeviceConfig::LOCAL_ID` | Construction only; no setter | Immutable configured-local-ID snapshot |
| `peerId_` | `uint8_t` | Constructor argument from `DeviceConfig::PEER_ID` | Construction only; no setter | Immutable configured-peer-ID snapshot |
| `ready_` | `bool` | `false` | Hub sets true after successful radio initialization; Node sets true after radio initialization and false if initial receive start fails | Whether role firmware considers initial radio operation ready |
| `phase_` | `RuntimePhase` | Hub: `IDLE`; Node: `LISTENING` | Firmware orchestration at the transition points below | Presentation mirror of current radio/transaction-facing phase |
| `latestRssi_` | `float` | `0.0F` | Role firmware through `updateRadioMetrics()` after a received radio packet is read | Latest captured RSSI diagnostic; no validity marker |
| `latestSnr_` | `float` | `0.0F` | Updated with RSSI by `updateRadioMetrics()` | Latest captured SNR diagnostic; no validity marker |

`DeviceRole` contains exactly `HUB` and `NODE`. `RuntimePhase` contains exactly
`IDLE`, `TRANSMITTING`, `WAITING_FOR_ACK`, `LISTENING`, and
`TRANSMITTING_ACK` (`lib/runtime_state/src/runtime_state.h:7-18`).

The constructor takes role, local ID, and peer ID. It initializes Node phase to
`LISTENING` and Hub phase to `IDLE` (`lib/runtime_state/src/runtime_state.h:20-31`).
Getters expose role, both IDs, readiness, phase, RSSI, and SNR. Setters exist
only for readiness, phase, and the paired RSSI/SNR update
(`lib/runtime_state/src/runtime_state.h:33-72`).

### 9.2 Hub mutation points

| Location | Mutation | Exact point |
|---|---|---|
| `src-tx/main.cpp:103-106` | phase → `IDLE` | Scheduling the next transaction |
| `src-tx/main.cpp:118-127` | phase → `IDLE` | A failed attempt schedules a retransmission |
| `src-tx/main.cpp:191-200` | phase → `TRANSMITTING` | `radio.startTransmit()` succeeds |
| `src-tx/main.cpp:203-226` | phase → `WAITING_FOR_ACK` | `radio.startReceive()` succeeds |
| `src-tx/main.cpp:293-306` | latest RSSI/SNR replaced | ACK bytes were read successfully, before protocol decode is attempted |
| `src-tx/main.cpp:411-423` | ready → true | Radio initialization succeeded and callback was installed |

Hub readiness is never explicitly set false. Its default remains false if
radio initialization fails. No Hub mutation stores a retry count, sequence,
deadline, ACK status, packet, counter, error class, or display state in runtime
state.

### 9.3 Node mutation points

| Location | Mutation | Exact point |
|---|---|---|
| `src-rx/main.cpp:100-114` | phase → `LISTENING` | Immediately before `radio.startReceive()`; it occurs even if that call fails |
| `src-rx/main.cpp:145-169` | phase → `TRANSMITTING_ACK` | After the 100 ms pre-ACK delay and immediately before `radio.startTransmit()` |
| `src-rx/main.cpp:219-237` | latest RSSI/SNR replaced | Command decoded successfully, before command evaluation |
| `src-rx/main.cpp:310-324` | ready → true | Radio initialization succeeded and callback was installed |
| `src-rx/main.cpp:322-325` | ready → false | The initial setup call to `startListening()` fails |

Later receive restarts call `startListening()` and therefore set phase to
`LISTENING`, but their callers do not set readiness false on failure. No Node
mutation stores duplicate metadata, remembered status, packet history, counter,
error class, menu, navigation, or display state in runtime state.

## 10. Ownership invariants

The following established boundaries must remain true during v0.3.0:

1. `DeviceConfig` owns configured identity. It obtains `LOCAL_ID` and `PEER_ID`
   from required build flags and requires them to differ
   (`include/device_config.h:5-23`). Runtime state receives immutable
   construction-time snapshots; it does not redefine configuration.
2. `HubTransactionState` owns the active sequence, retry count and limit, ACK
   wait flag, ACK deadline, timeout action, terminal result classification,
   transaction completion, sequence advance, and retry reset
   (`lib/transaction_engine/src/transaction_engine.h:134-232`).
3. `NodeDuplicateTracker` owns the single-entry, in-memory duplicate key
   `(source, sequence, opcode)` and remembered ACK status
   (`lib/transaction_engine/src/transaction_engine.h:7-39`). Its state is
   volatile across restart.
4. Runtime state owns presentation/diagnostic readiness, phase, and last radio
   metrics. It is not consulted to decide retry count, timeout, sequence
   advance, duplicate classification, ACK construction, or transaction
   completion.
5. Firmware entry points own Arduino, RadioLib, OLED, GPIO, interrupts,
   `millis()`, delays, packet I/O, and Serial orchestration. Hardware-independent
   components do not call those APIs.

Transaction data intentionally absent from runtime state includes active and
last sequence, retry count/limit, ACK deadline/wait state, current command,
pending ACK, duplicate key, remembered ACK status, raw/decoded packet history,
last ACK status, success/failure result, and transaction counters.

## 11. Duplicated presentation code

The following presentation code is duplicated between Hub and Node:

- the 64-byte `rgLogo26x16` array;
- the complete `showHomeScreen()` implementation;
- OLED buffer clearing, colors, logo background, XBM draw, text alignment,
  fonts, coordinates, title, status draw, and final flush;
- the `SSD1306Wire` construction expression;
- the Vext/OLED reset and `display.init()` setup sequence.

The logo bytes and Home drawing operations are byte-for-byte or statement-for-
statement identical. The normal role difference is supplied only by the status
argument (`TX | READY` versus `RX | READY`). The Node has one additional setup
error status (`RX START ERR`).

Serial helpers `showStatus()`, `logVersionMetadata()`, and `logPacket()` are
also duplicated, but they are not OLED behavior and do not need to move during
this baseline step. This section identifies duplication only; it does not add
an adapter, refactor either role, or change the approved later implementation
sequence.

## 12. Baseline limitations

The pre-v0.3.0 firmware has:

- no application input or GPIO0 use;
- no button polling, input interrupt, debounce, or semantic gesture;
- no navigation, screen identifier, or menu;
- no display timeout, power-state policy, or wake behavior;
- no dirty flag, periodic refresh, refresh limit, or live screen updates;
- no runtime counters;
- no packet history or last-packet snapshot;
- no metric-validity marker, so `0.0F` is both the default and a possible
  numeric value;
- no typed health or error model beyond `ready_`, runtime phase, and the three
  setup OLED error/ready strings documented above;
- synchronous OLED buffer flushing through `display.display()`;
- no OLED presentation of ordinary transaction success, retry, timeout,
  duplicate, packet, RSSI, SNR, or phase changes.

Both role loops call `delay(1000)` whenever `runtimeState.isReady()` is false
(`src-tx/main.cpp:426-430`; `src-rx/main.cpp:328-332`). This is the current fatal
or not-ready loop behavior. It blocks that role's loop for one second at a time;
there is no input to service and no display refresh in that path today.

The Node also retains its intentional 100 ms pre-ACK delay
(`src-rx/main.cpp:147-151`). That transaction timing is not a display feature
and remains an invariant for later UI work.

## 13. Step 1 completion assessment

### 13.1 Verified facts

- The current OLED baseline is completely localized to duplicated setup-time
  rendering in the two firmware entry points.
- Ordinary radio and transaction processing does not redraw the OLED.
- No application-input implementation exists.
- Runtime-state fields and mutations are small, explicit, and separate from
  transaction authorities.
- Existing native tests already characterize deterministic runtime defaults,
  roles, identity exposure, readiness transitions, phase changes, paired
  metric updates, instance independence, volatile reset, and transaction-engine
  independence (`test/test_runtime_state/test_main.cpp:11-181`).

No new native characterization test is justified in Step 1. Pixel rendering,
Arduino `String`, the ThingPulse driver, GPIO electrical behavior, and physical
switch behavior are hardware-dependent. Duplicating bitmap bytes or startup
strings into a native test would freeze implementation details without testing
an existing hardware-independent contract. Adding screen or input types would
prematurely begin later implementation steps.

### 13.2 Approved future behavior, not yet implemented

The approved brief defines GPIO0/`INPUT_PULLUP`, input timing, semantic events,
six-screen navigation, display timeout/wake, dirty and live refresh limits,
counters, last inbound packet state, health/error presentation, and shared
rendering. None of those features is present or claimed by this baseline.

### 13.3 Hardware validation still required

Source inspection and native tests cannot prove:

- the exact physical V4 board revision on either test device;
- GPIO0 switch wiring, active level, boot-strapping behavior, or physical bounce;
- Vext electrical polarity beyond the source's current LOW output level;
- OLED pixel geometry, font rendering, contrast, or I2C transfer timing;
- whether future display refreshes or button activity create a radio receive gap;
- the visible result of each current setup/error screen on both physical boards.

### 13.4 Proceed-to-Step-2 assessment

**Assessment:** The source findings match the approved implementation brief and
support proceeding to Step 2 unchanged after this document is reviewed and
accepted. No contradiction requires a change to Step 2 scope or ownership.
Step 2 must still be implemented separately; this document makes no runtime
state API or behavior change.
