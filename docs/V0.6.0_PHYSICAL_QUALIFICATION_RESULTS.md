## 26. Step 15U -- Host HWCDC TX failure investigation

Step 15U was performed on 2026-08-17. Its disposition is **FAIL -- the tested
minimal HWCDC lost-wakeup backport did not eliminate the physical timeout**.
No remediation is accepted.

### 26.1 Exact REDLINE TX boundary

Qualification-only trace events were extended to record Host response
submission, each actual transport write result, and HostTransport frame
retirement. Normal production behavior remained compile-gated from these
events.

The extended `tx_structured_trace` build reproduced the intermittent failure:
remote PING requests `0x4000` through `0x400B` completed, while fresh request
`0x400C` produced no correlated PC response within eight seconds. No retry or
subsequent Host request was sent before the RAM capture.

The `0x400C` RAM trace proved:

- the 25-byte encoded OPERATION_RESPONSE was submitted to HostTransport;
- the production connection observation was true;
- `Serial.availableForWrite()` returned at least 255;
- HostTransport called `Serial.write()` requesting all 25 bytes;
- `Serial.write()` returned 25;
- HostTransport retired the frame as complete;
- the PC nevertheless received no correlated frame.

Thus the last proven REDLINE boundary is full acceptance by
`HWCDC::write()`, not physical CDC delivery. For this failure, REDLINE did not
prematurely retire a zero or partial write. The unresolved owner is below
HostTransport, in the framework HWCDC/USB-host delivery boundary.

### 26.2 Framework comparison

The installed framework is Arduino-ESP32 2.0.17, PlatformIO package
`3.20017.241212+sha.dcc1105b`. Its local `cores/esp32/HWCDC.cpp` SHA-256 is
`d0a8ca606c2729c8522a041113285dbf27033c22a5a6af8649a7305ffe84c449`.
Inspection confirmed unsynchronized task/ISR read-modify-write operations on
`SERIAL_IN_EMPTY`, an ISR empty-ring disable without a post-disable queued-data
recheck, one-shot not-connected interrupt arming, and no explicit re-arm after
the not-connected `flushTXBuffer(buffer,size)` write path.

Official Espressif arduino-esp32 commit
`2ecad233178bfbba9c584ffd9f67e941d84adbb7` (PR #12606, "fix(hwcdc): fix
glitches in writing") added shared TX critical-section protection, an
empty-ring recheck/re-arm, repeated disconnected-state re-arming, and other TX
robustness changes. The first stable tag containing it is Arduino-ESP32 3.3.9.
That full release changes ESP-IDF/framework generation and was not adopted as
a narrow dependency update in this investigation.

### 26.3 Rejected minimal backport experiment

A temporary repository-controlled build experiment copied the exact verified
2.0.17 core into each `.pio` environment and compiled a narrow backport of the
interrupt synchronization, empty-ring recheck, repeated not-connected re-arm,
and post-queue re-arm. The global PlatformIO package was never modified. The
experiment made no Host or Wire semantic change, added no queue or dynamic
allocation, and preserved native 615/615 and Python 19/19 results. Both normal
roles, characterization roles, HostTransport fixtures, valid configurations,
and trace build compiled; negative configuration fixtures retained their
expected failures.

The experimental production sizes were Hub 21,324 RAM / 366,005 flash and
Node 21,612 RAM / 364,901 flash. Compared with the entering candidate, these
were Hub +8 RAM / -228 flash and Node +16 RAM / -172 flash.

Both boards were flashed with the experimental normal firmware after explicit
antenna confirmation. Hub local PING passed 20/20 and Node local PING passed
20/20. In the required persistent rapid remote-PING matrix, requests `0x5200`
through `0x5209` passed in approximately 0.67--0.69 seconds, but request
`0x520A` produced no correlated response within eight seconds. Testing stopped
immediately, as required. Delayed remote, open-per-request remote, mixed
operations, retained replay, and reconnect matrices were **NOT EXECUTED**.

The narrow backport was removed from repository production configuration and
is not an accepted remediation. The boards remain flashed with the rejected
experimental binaries pending the next approved investigation action; no
further Host traffic was sent after `0x520A`. The qualification-only TX-edge
trace additions remain available. The HWCDC lost-wakeup race is a real defect
in the old source and is consistent with the symptom, but this experiment did
not prove it was the sole cause of REDLINE's intermittent loss. The release
blocker therefore remains an intermittent loss below the application write
boundary. Full Step 15 and Step 16 remain blocked.

### 27.6 Candidate binary reproducibility disposition

Independent clean Arduino 3.3.9 production builds produced identical binary lengths and identical reported linked RAM/flash usage but different whole-image SHA-256 values.

A byte-level A/B comparison showed only a small number of changing bytes:

```text
Hub:  70 differing bytes across 5 contiguous ranges
Node: 71 differing bytes across 6 contiguous ranges
```

The differing regions consisted of visible compile-time strings plus associated 32-byte hash fields and the final 33-byte checksum/digest region. Therefore the ordinary clean build embeds time-dependent metadata that propagates into image hashes.

Whole-image SHA-256 is consequently retained as an **artifact-specific fingerprint**, not as a deterministic source/build identity for this toolchain. The mismatch between later clean-build hashes and the recorded M6 artifact hashes does not invalidate the physical qualification.
