## 1. Purpose

This document records the production `v0.4.0` behavior and ownership boundaries
that v0.5.0 capability work must preserve. It is a source-derived review gate,
not a capability implementation proposal. No capability types, registry,
dispatcher, policies, hardware bindings, trigger, or transport behavior are
implemented by this step.

The labels **Verified current**, **Planned v0.5.0**, **Unresolved**, and
**Future milestone** distinguish implemented facts from plans.

| Item | Current value |

| Maximum packet size | 32 bytes |
| Maximum payload | 26 bytes |

The tested TEST fixture for Hub `0x01`, Node `0x10`, and sequence `0x2A` is:

```text

```

The matching successful ACK fixture is:

```text

```

## 7. Hub transport invariants

`HubTransactionState` owns sequence, retry count, ACK deadline, timeout
classification, and completion. Hub role firmware owns radio calls and
scheduling.

- The initial transaction is scheduled 2,000 ms after successful setup.
- A terminal success, remote error, or failure schedules the next transaction
  3,000 ms later.
- An eligible retransmission is scheduled 500 ms after the failed attempt.
- ACK timeout is 2,500 ms. The deadline is inclusive: at the exact deadline,
  timeout/retry action is due. Signed subtraction preserves `millis()` wrap.
- Maximum retransmissions are 2 after the initial attempt (3 total attempts).
- Sequence starts at 1, is copied into each attempt, advances exactly once on
  terminal completion, and wraps naturally as `uint8_t`.
- ACK matching order is type, source, destination, sequence, opcode, then
  one-byte payload length. Status validity is checked after structural match.
- Ignored or decode-invalid packets resume the existing ACK wait without
  resetting its deadline. A structurally matching ACK with an invalid status
  terminates the transaction as malformed.
- Completion updates runtime/peer presentation, enters radio standby, advances
  sequence, clears retry/wait state, and schedules the next transaction.
- Node absence causes timeout plus exactly two retries, terminal degraded state,
  sequence advancement, and continued periodic scheduling; a returning Node is
  recovered by a later transaction.

Future local capability work may run only at a role-approved idle/radio-safe
orchestration point. It must not enter transaction-engine internals or change
these timings and ordering.

## 8. Node transport invariants

The Node starts continuous receive during setup. Its DIO1 ISR only sets the
volatile completion flag; packet work remains in the main loop.

- Framing length (6..32), radio read/CRC, and codec validation occur before
  command evaluation.
- Evaluation order is destination, packet type, sender, duplicate key,
  supported opcode, then opcode-specific payload length.
- `NodeDuplicateTracker` holds one volatile entry keyed by source, sequence,
  and opcode, plus the ACK status. It is not persistent.
- Accepted, unsupported, and malformed new commands replace that single entry.
  Wrong-destination/sender/type packets do not.
- A duplicate regenerates a fresh ACK from current command metadata and the
  remembered status; encoded ACK bytes are not cached.
- Each ACK path preserves the deliberate 100 ms pre-ACK delay, then starts an
  asynchronous transmission.
- ACK source/destination are reversed from the command; sequence and opcode are
  copied; payload is one status byte.
- After ACK completion, the radio is placed in standby, transmit completion is
  recorded, and receive is restarted before OLED work is allowed.
- Wrong destination/sender/type is ignored and receive is restored. Unsupported
  opcode and malformed TEST payload receive their defined error ACK. Codec- or
  radio-malformed input is rejected before command evaluation and receive is
  restored.

Capability work must remain subordinate to receive, validation, duplicate,
ACK-generation/transmission, and receive-restoration ownership.

## 9. Runtime, UI, and input ownership

| Behavior | Current sole authority / boundary |
|---|---|
| Physical GPIO0 sample | Role firmware reads active-low GPIO0 configured `INPUT_PULLUP` |
| Debounce and semantic events | `DeviceInput::Button`: 30 ms debounce; PRESS, RELEASE, SHORT_PRESS, LONG_PRESS at 800 ms, VERY_LONG_PRESS at 3,000 ms; startup-held suppression |
| Screen/navigation/editor/timeout/wake | `DeviceUi::Controller` |
| Presentation content | Bounded snapshots from `DeviceUi` |
| OLED drawing, on/off, contrast application | `HeltecDisplay::Renderer` and role orchestration |
| Runtime health/phase/activity/radio metrics/packet history/counters/errors | `RuntimeState::State` |

The six normal screens remain Home, Radio, Device, Last Packet, Diagnostics,
and About. Short press advances; long press returns Home; very-long press on
About enters the settings editor. A wake gesture does not also navigate.
Rendering is dirty/rate-limited (100 ms minimum), live screens refresh at
1,000 ms, and the default inactivity timeout is 30 seconds.

`RuntimeState` may later receive a bounded copied capability diagnostic summary;
it must not own registry or handler state. `DeviceUi` may consume a bounded
presentation snapshot; it must not own descriptors, dispatch, or hardware.

**Invariant:** DeviceInput remains the semantic input authority. A future
DIGITAL_INPUT may consume only a deliberately exposed stable current-state
snapshot. Capability code may not configure, poll, debounce, classify, consume,
or generate button events.

## 10. Settings and persistence ownership

`DeviceSettings::Settings` owns six ordinary preferences: display timeout,
display contrast, LED enabled, diagnostics enabled, default screen, and button
feedback. Defaults are 30 seconds, contrast 207, LED enabled, diagnostics
enabled, Home, and feedback disabled.

- `DeviceSettings` owns Schema 1 defaults, validation/repair, exact 24-byte
  little-endian codec and CRC, generation comparison, dual-slot selection,
  save/read-back verification, migration dispatch, and reset recovery.
- `Esp32SettingsStorage` alone owns Preferences namespace `redline`, slots
  `cfg_a`/`cfg_b`, and marker `rst_pend`.
- `SettingsManager` owns loaded settings, active slot/generation, unsupported
  preservation, repair intent, and save/reset results.
- `SettingsIntegration::RequestQueue` is only a bounded settings save/reset
  request handoff. It is not a capability queue or event bus.
- `DeviceUi` owns the nine-item RAM-draft editor, Save/Cancel, reset arming and
  10-second confirmation policy, and inactivity dismissal.
- `HeltecDisplay` renders snapshots and applies contrast; it never reads NVS.
- Hub role firmware services persistence only while IDLE, not awaiting ACK or
  retry, with no radio event pending and no rendering.
- Node role firmware services it only after ACK completion or guarded quiet
  LISTENING maintenance, after standby ownership and event recheck, with no
  inbound/validation/ACK/duplicate/render obligation; receive is restored
  immediately afterward.
- Factory reset affects only ordinary settings and uses a verified marker-first,
  remove-both-slots, write/verify canonical slot A generation 1, remove/verify
  marker sequence. It does not clear global NVS or identity.
- LED enable is a master physical-output gate. Diagnostics disable affects
  presentation only; collection and screen position remain. Default screen is
  applied at boot/reset, not unexpectedly on Save. Contrast may preview with
  Cancel restoring the loaded value.

Capabilities must not become a second authority or persist descriptors, pins,
policies, bindings, runtime state, or per-capability configuration in Schema 1.

## 12. Existing LED arbitration

Both role entry points are the current physical LED authority. They compute:

```text
LED enabled setting AND (radio activity OR button feedback)
```

Radio ownership is asserted around Hub command transmission and Node ACK
transmission. Button feedback is a nonblocking 50 ms request for semantic input
events. Direct capability writes would bypass the master enable, overlap rules,
and radio/feedback owners and are forbidden. A future application-indicator
owner must be an additional input to this arbitration, not another pin writer.

## 13. Candidate capability integration seams

**Planned v0.5.0, not implemented:** The proposed directories fit the current
repository conventions:

- `lib/device_capabilities/` can remain hardware-independent and own the
  proposed `CapabilityId`, `CapabilityClass`, descriptor/value/operation/result
  vocabulary, immutable bounded registry validation/enumeration/lookup,
  authorization and safety policy contracts, strict dispatch order, narrow
  `LocalCapabilityHandler` interface, and capability-local diagnostics.
- `lib/heltec_v4_capabilities/` can privately own profile-local IDs, immutable
  descriptor/binding tables, pins, polarity, ADC setup and normalization,
  initialization, policy IDs, a DeviceInput snapshot adapter, an LED-arbitration
  adapter, and physical handler implementation. No pin crosses this boundary.
- `test/test_device_capabilities/` can use simulated handlers strictly as native
  development fixtures. Simulated entries must not silently appear in the
  production registry.

Candidate role-owned invocation seams are:

- **Hub:** after button/settings service only when the same facts used by
  `HubSettingsIntegration::persistenceSafe` establish IDLE, no ACK wait, no
  scheduled retry, no radio event, and no rendering. The role loop remains the
  scheduler; the transaction engine does not dispatch capabilities.
- **Node:** only in an explicitly admitted quiet LISTENING maintenance window or
  after an ACK is fully completed and receive has been restored, using the same
  event recheck and radio-ownership discipline as settings maintenance. Receive,
  validation, ACK, duplicate replay, and rendering obligations take priority.
- **UI/input:** future UI reads bounded copied summaries only. Raw callbacks,
  render callbacks, ISR context, and `DeviceInput` event generation are not
  invocation seams.
- **Persistence:** no capability invocation is routed through or generalized
  from the settings request queue.

No trigger mechanism is approved by this document. The seams identify safe
orchestration constraints only.

## 14. Unresolved hardware questions

- No ADC pin is approved. The board variant lists analog aliases, but the current
  repository does not establish an unowned, header-accessible V4.3 pin, ADC
  channel/attenuation, board loading, or maximum safe applied voltage.
- The exact V4.3 schematic/pinout and measured voltage plan must be reviewed in
  the later hardware-profile step before wiring or production registration.
- Sharing GPIO0 requires a new stable state snapshot that does not expose or
  perturb DeviceInput event state. If that seam cannot remain clean, use a
  separately verified input or keep the capability simulated during tests.
- Extending built-in LED arbitration requires explicit overlap and master-disable
  tests. Otherwise use a separately verified external indicator.
- The release notes retain deferred physical measurements for LED-disable/
  feedback behavior and exact Node persistence receive-gap duration. No hardware
  was flashed or wired in Step 1.

## 15. v0.5.0 non-goals confirmed

v0.5.0 does not implement arbitrary GPIO access; GPIO-number capability IDs;
runtime registration; registration from radio, serial, UI, or settings; dynamic
plugins; transferred procedures; arbitrary code execution; real relay/external
power switching; motors or hazardous actuators; Host Protocol; a serial command
console; radio-visible capability operations; `RESPONSE` semantics; the v0.6.0
structured operation protocol; settings-over-LoRa; capability persistence;
provisioning/security redesign; multi-Node behavior; routing; repeaters;
store-and-forward; mesh; or application workflows.

`LOCAL_PROCEDURE` is proposed vocabulary only unless a later approved step
changes that boundary. Simulated capabilities remain test/development fixtures
and are not production registrations.
