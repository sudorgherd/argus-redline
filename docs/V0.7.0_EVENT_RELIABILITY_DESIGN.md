# ARGUS REDLINE v0.7.0 Event Reliability Design

**Status:** Normative detailed design; implementation entry candidate  
**Milestone:** `v0.7.0` — Node-Originated Events and Reliable Delivery  
**Architecture authority:** `V0.7.0_ARCHITECTURE_BASELINE.md`  
**Implementation status:** NOT STARTED  
**Entry interfaces:** Wire Protocol `1`, Configuration Schema `1`, developmental Host Protocol `0.1`, hardware profile `HELTEC_V4`

## 1. Purpose

This document freezes the v0.7.0 Event identity, persistence, queue, Wire,
admission, retry, arbitration, Hub custody, and Host-delivery design. It is
sufficiently specific for an implementation brief to order code changes
without reopening fundamental lifecycle decisions.

This document does not implement firmware and does not modify Host Protocol
0.1. A later Host Protocol 0.2 specification must encode the requirements in
Sections 19 and 20.

## 2. Design Goals and Invariants

The implementation MUST satisfy these invariants:

1. Every successfully created Event enters durable Node custody before it is
   eligible for transmission.
2. Important queued Events survive Node reset and power loss. For v0.7.0 all
   admitted Events use the persistent store; there is no RAM-only Event class.
3. Event identity is persistent, stable across retries/reboot, and independent
   of the eight-bit Wire sequence.
4. Node custody is released only by an exactly correlated successful Hub
   admission response.
5. Hub success is sent only after authoritative Hub acceptance is durable.
6. Exact identity plus exact canonical content is a duplicate. The same
   identity with different content is a mismatch.
7. Malformed, unsupported, or mismatched input cannot poison acceptance state.
8. Node queue, Hub ledger, retries, storage, payloads, and service time are
   statically bounded.
9. Existing v0.6.0 COMMAND/ACK/RESPONSE behavior remains functional.
10. Codecs own external bytes; persistent stores own durable records; state
    machines own transitions; integration owns RadioLib, USB CDC, time, NVS,
    display, button, and hardware access.
11. ISR behavior remains flag-only. No codec, state-machine, storage, display,
    or protocol-response work occurs in interrupt context.
12. Event reliability is a benign-loss property, not authentication or
    cryptographic replay protection.

The implementation MUST use fixed arrays and bounded buffers for Event state.
It MUST NOT introduce a generic scheduler, unbounded log, database, filesystem
growth, or heap-dependent queue.

## 3. Event Ownership Model

Custody transfers are explicit. Durable Hub acceptance begins Hub custody; it
does not wait for the Node to receive the admission ACK. Until that ACK is
exactly correlated, both devices intentionally retain durable copies:

```text
local producer
    |
    | durable Node record committed and read back
    v
NODE OWNS
    |
    | Hub durably accepts exact Event
    v
NODE AND HUB BOTH RETAIN DURABLE CUSTODY
    |
    | Node receives exact correlated ADMITTED response
    | and durably releases its record
    v
HUB OWNS
    |
    | Host POLL_EVENTS retrieves non-destructively
    | + Host CONSUME_EVENT is durably committed
    v
HOST / APPLICATION OWNS
```

An attempted transmission never transfers custody. Node custody MUST NOT be
released on timeout, malformed response, wrong endpoint, wrong sequence, wrong
opcode/family, wrong Event identity, backpressure, unsupported-family response,
or identity/content mismatch.

The temporary dual-custody handoff window is required for lost-ACK and reboot
recovery. Hub admission establishes Hub responsibility immediately; exact
ADMITTED authorizes the Node to end its overlapping responsibility. Host
polling is not the Hub/Host ownership point. Host disconnect, serial
transmission, or retained Host response creation does not imply consumption.

## 4. Event Identity

The canonical Event identity is:

```text
Source_Device_ID : uint8    (Wire source field)
Event_Epoch      : uint32   little-endian
Event_ID         : uint32   little-endian
```

`Event_Epoch + Event_ID` is stored in each Node record and transmitted in each
attempt. `Source_Device_ID` is supplied by the Wire header. Retransmission MUST
reuse all three values.

### 4.1 Durable allocator

Each Node has separate dual-copy Event identity metadata. Each encoded copy is
exactly 28 bytes:

| Offset | Size | Field |
|---:|---:|---|
| 0 | 4 | magic `0x45494431` (`EID1`) |
| 4 | 2 | Event identity schema `1` |
| 6 | 2 | record length `28` |
| 8 | 4 | metadata generation |
| 12 | 1 | custody source device ID |
| 13 | 3 | reserved zero |
| 16 | 4 | Event epoch |
| 20 | 4 | next unreserved Event ID |
| 24 | 4 | CRC-32/ISO-HDLC over bytes 0..23 |

Multi-byte fields are little-endian. Reserved bytes MUST be zero. Metadata is
not Configuration Schema 1. Each copy uses the same inactive-copy write,
commit, read-back, byte validation, wrap-safe generation selection, and
equal-generation conflict rules as other Event-store metadata.

IDs are reserved in blocks of 32 to limit metadata wear. Before using any ID in
a new block, the allocator MUST write and read back the inactive metadata copy
with `next_unreserved_id` advanced by 32. Only then may it allocate IDs from the
reserved half-open range. After reboot, unused IDs in a reserved range are
skipped; reuse is forbidden.

On first initialization, `event_epoch` is a nonzero 32-bit value obtained from
the platform hardware entropy source and durably committed before allocation.
The random value is not authoritative until persisted. If entropy or metadata
commit fails, Event creation fails closed.

Persistent Event custody is bound to the `custody source device ID` under which
it was created. Recovery MUST compare that nonzero metadata value with the
current configured local device ID before reconstructing or transmitting any
Event. If any Event slot is nonempty and the values differ, or the stored
context cannot be proven, recovery enters `IDENTITY_CONTEXT_MISMATCH`, preserves
all records, transmits nothing, and rejects new Event creation. Retained Events
MUST NOT be re-identified or silently migrated.

If all Event slots are authoritatively FREE, the store MAY adopt a different
current local device ID by committing a fresh metadata context with a newly
generated nonzero epoch and reset unreserved-ID state before any allocation.
It MUST NOT carry the previous epoch/reservation state into the new source
context. This keeps Source_Device_ID out of each fixed 56-byte Event record
without allowing recovered canonical identity to change silently.

`Event_ID` values 1 through `0xFFFFFFFF` are valid. Zero is reserved. If the
next reservation would cross `0xFFFFFFFF`, the Node MUST durably advance the
epoch, set `next_unreserved_id` to 33, and reserve IDs 1..32 before using ID 1.
Epoch zero and wrap from `0xFFFFFFFF` to zero are forbidden; epoch exhaustion
fails Event creation closed.

If both metadata copies are invalid while any Event slot is nonempty, the store
MUST enter `IDENTITY_RECOVERY_REQUIRED`, preserve all bytes, transmit nothing,
and reject new Events. It MUST NOT guess an epoch/counter or erase queued
Events. Administrative recovery is outside v0.7.0.

Allocation ordering is:

```text
reserve ID range durably (when needed)
-> choose next never-used ID in RAM
-> build Event record
-> commit/read back Event record
-> publish enqueue success
```

An allocated ID whose Event-record commit fails is burned and never reused.
This identity is a reliability identifier, not provisioned identity, a secret,
an authenticator, or security freshness.

## 5. Event Record and Canonical Content

Canonical Event content is the exact tuple:

```text
Source_Device_ID
Event_Family             (Wire opcode)
Event_Epoch
Event_ID
Event_Flags
Lifetime_Budget_Seconds
Event_Body_Length
Event_Body[0..length)
```

The transient Wire sequence, attempts used, remaining lifetime, storage slot,
record generation, and CRC are not canonical content. Canonical content is
immutable from successful enqueue until terminal reclamation.

`Event_Flags` currently defines only bit 0, `IMPORTANT`. Bits 1..7 MUST be zero.
All v0.7.0 Events are persistently stored regardless of the flag; the flag is
semantic metadata for future policy and MUST NOT weaken custody.

Lifetime budget is 1..86,400 seconds. Event body length is 0..12 bytes. Every
family defines one exact body length and reserved-value rules.

## 6. Persistent Node Event Store

The Node Event store is a dedicated NVS namespace, separate from ordinary
settings. It contains dual identity-metadata copies and eight logical Event
slots. Each logical slot has A/B copies; no settings key or record is reused.

### 6.1 Capacity and record geometry

`NODE_EVENT_CAPACITY` is 8. Each encoded slot copy is exactly 56 bytes:

| Offset | Size | Field |
|---:|---:|---|
| 0 | 4 | magic `0x45565431` (`EVT1`) |
| 4 | 2 | Event-store schema `1` |
| 6 | 2 | record length `56` |
| 8 | 4 | record generation |
| 12 | 1 | durable state |
| 13 | 1 | Event flags |
| 14 | 1 | Event family/opcode |
| 15 | 1 | body length |
| 16 | 4 | Event epoch |
| 20 | 4 | Event ID |
| 24 | 4 | lifetime budget seconds |
| 28 | 4 | remaining active-runtime seconds |
| 32 | 1 | attempts used |
| 33 | 3 | reserved zero |
| 36 | 12 | body bytes, unused tail zero |
| 48 | 4 | reserved zero |
| 52 | 4 | CRC-32/ISO-HDLC over bytes 0..51 |

Durable states are `FREE=0x00`, `QUEUED=0x01`, `FAILED=0x02`, and
`EXPIRED=0x03`. Other values invalidate that copy. Runtime TX/wait/backoff
states are never written as durable ownership states.

A valid FREE record is one exact canonical representation. Magic remains
`EVT1`, schema remains `1`, record length remains `56`, and record generation
is the valid generation of that copy; generation is not required to be zero.
Durable state is `FREE=0x00`. Every Event-owned field MUST be zero: Event
flags, family/opcode, body length, Event epoch, Event ID, lifetime budget,
remaining active-runtime lifetime, and attempts used. Reserved bytes 33..35,
all 12 body bytes, and reserved bytes 48..51 MUST also be zero. The CRC remains
CRC-32/ISO-HDLC over bytes 0..51 and therefore covers the complete canonical
FREE representation. Any FREE record with a nonzero Event-owned, body, tail,
or reserved field is invalid.

FREE carries no retained Event identity, canonical Event content, lifetime,
attempt history, or tombstone semantics. Reclamation to FREE is a normal
durable slot mutation and uses the normal next record generation. This is
distinct from FAILED and EXPIRED, which retain Event content as durable
terminal records until a separate mutation reclaims the slot to FREE.

### 6.2 Commit and recovery rules

A slot mutation writes the inactive copy with generation+1, complete bytes and
CRC, closes/commits the NVS operation, reads it back, decodes it, and compares
all bytes. Only then does it become authoritative. The older valid copy remains
the fallback. Generation comparison uses wrap-safe half-range ordering; equal
generation with different bytes is corruption and fails the slot closed.

Allocation selects the lowest-numbered FREE logical slot, but delivery order is
the persistent Event identity, not slot number. For the one-Node v0.7.0 scope,
lexicographic `(Event_Epoch, Event_ID)` order is creation/FIFO order. Epoch
advancement is ordered after every ID in the preceding epoch.

Terminal transition first commits FAILED or EXPIRED. That terminal record is
then eligible for a separately committed FREE mutation. A torn terminal/free
write therefore recovers either the owned QUEUED record or a terminal record,
never a fabricated success. A successful Hub admission commits FREE directly;
if that commit fails, Node custody remains and retransmission is safe because
the Hub deduplicates.

No retry transition writes a complete record except the write-ahead attempt
increment and lifetime checkpoints described below. Ordinary waiting/backoff
does not write flash.

### 6.3 Wear boundary

The design limits writes by reserving identity blocks, writing attempts once
per delivery attempt, checkpointing lifetime no more often than once
per 60 active seconds, and avoiding writes for volatile state transitions.
The implementation brief MUST characterize NVS write/erase behavior and show
that worst-case Event activity stays within an explicitly documented endurance
budget. No claim of infinite endurance is permitted.

## 7. Boot Recovery

Boot recovery completes before Event transmission or Event creation:

1. Read and validate both identity metadata copies; select the newest valid
   copy or fail closed as Section 4 requires.
2. Read both copies of all eight Event slots.
3. Select the newest valid copy per slot. One invalid/torn copy falls back to
   the other. Two invalid copies make that nonempty/indeterminate slot a storage
   fault; the system preserves it and disables Event delivery/creation.
4. Validate Event identity uniqueness, canonical body, attempts `<=5`, and
   remaining lifetime `<=` original lifetime.
5. Reconstruct QUEUED entries in ascending `(Event_Epoch, Event_ID)` order.
6. Charge the 60-second reboot recovery debit to each QUEUED Event before it is
   eligible. Commit the decreased value; if remaining time is 60 seconds or
   less, commit EXPIRED instead.
7. Count recovered/expired/corrupt records and expose degraded state.
8. Reclaim valid FAILED/EXPIRED terminal records only after their recovery
   outcome has been observed by runtime diagnostics.

TX, WAIT_ADMISSION, and BACKOFF are runtime-only; reset reconstructs any owned
Event as QUEUED. Attempts already written before transmission remain charged.
Recovery never reorders Events and never resets attempts or lifetime.

## 8. Runtime Queue Policy

RAM contains an eight-entry static index over durable QUEUED records, not a
second custody store. Ordering is strict FIFO by ascending `Event_Epoch`, then
`Event_ID`. Only the head-of-line Event may enter the delivery state machine;
younger Events MUST NOT bypass it.

There is no Event priority in v0.7.0. When all eight slots are owned, enqueue
uses newest-reject: the new Event receives no Event ID, no record is changed,
and the producer receives `QUEUE_FULL`. Existing Events are never evicted.

After terminal reclamation the next enqueue may reuse the physical slot, but it
must use a new durable Event identity.

## 9. Node Event Delivery State Machine

| State | Durability | Entry/action | Exit |
|---|---|---|---|
| `QUEUED` | durable | Node owns committed record | arbitration eligibility -> READY; expiry/exhaustion -> terminal |
| `READY` | runtime | head is eligible; radio remains in receive | grant -> TX_PREPARE; synchronous work -> QUEUED |
| `TX_PREPARE` | runtime | persist attempts+1, allocate Wire sequence, encode | commit+encode success -> TX; failure -> BACKOFF/FAILED |
| `TX` | runtime | one nonblocking `startTransmit()` | TX done -> WAIT_ADMISSION; start failure -> BACKOFF/FAILED |
| `WAIT_ADMISSION` | runtime | receive with fixed deadline | exact response -> RELEASED or failure/backoff; timeout -> BACKOFF/FAILED |
| `BACKOFF` | runtime | receive/service normally until deadline | deadline -> READY; expiry/exhaustion -> terminal |
| `RELEASED` | terminal action | commit slot FREE after exact success | load next head |
| `FAILED` | durable terminal | commit FAILED; diagnose; reclaim | FREE |
| `EXPIRED` | durable terminal | commit EXPIRED; diagnose; reclaim | FREE |

The Node MUST restore receive after every TX completion, start failure, timeout,
ignored response, and terminal transition. A storage failure leaves the Event
owned, disables further Event transmission, and degrades locally.

Only an ACK satisfying every rule in Section 13 and status `ADMITTED` enters
RELEASED. `CAPACITY` enters BACKOFF unless the attempt budget is exhausted.
`IDENTITY_CONTENT_MISMATCH` or `UNSUPPORTED_EVENT` enters FAILED. A correlated
`MALFORMED_EVENT` enters FAILED because retransmitting immutable bytes cannot
repair it. Uncorrelated/malformed responses are ignored until timeout.

## 10. Retry, Backoff, and Attempt Budget

`MAX_EVENT_ATTEMPTS` is 5. An Event attempt is consumed when the durable
write-ahead attempt increment successfully commits, before RF transmission is
started. The count is read back before calling `startTransmit()`. A later
RadioLib start failure, ambiguous start outcome, or reset therefore still
consumes that attempt.

The attempt budget is deliberately not a proven RF-emissions count. It is a
conservative bound on armed delivery work, preventing reboot or ambiguous
radio-start failures from resetting delivery limits.

Admission timeout is 2,500 ms from successful TX completion. Time comparison
uses wrap-safe unsigned monotonic arithmetic. Timeout never extends on unrelated
traffic.

After attempt number `n` fails, the base backoff is:

```text
n=1: 1,000 ms
n=2: 2,000 ms
n=3: 4,000 ms
n=4: 8,000 ms
```

Add runtime-only jitter in `0..250 ms`, derived from platform entropy. Jitter
is not persisted, identity, or security material. Backoff is a deadline, never
blocking `delay()` or busy wait. UI, receive, storage safe points, input, and
Host service continue.

Capacity/backpressure consumes the attempt and uses the same backoff. It grants
no retry exemption. After attempt 5 ends without exact success, the Event
becomes FAILED. Retry never resets Event lifetime.

## 11. Event Expiry and Time Authority

v0.7.0 uses a **remaining powered-runtime custody budget**, not wall time.
Lifetime begins at durable enqueue. It decreases while firmware is powered and
the Event remains Node-owned, including queue wait, TX, ACK wait, and backoff.
Powered-off elapsed time is unknown and is not claimed.

Sources select a compile-time-approved budget from 60..86,400 seconds. The
original budget is canonical; remaining seconds are storage state. The Node
charges elapsed active time in RAM and commits remaining time at each 60-second
boundary. RAM state prevents transmission immediately when the budget reaches
zero even if the terminal checkpoint has not yet been written. Boot recovery
additionally debits 60 seconds before eligibility.

Up to one checkpoint interval of uncommitted active-runtime consumption may be
lost at each abrupt shutdown. Each subsequent boot applies the mandatory
60-second recovery debit, conservatively compensating for that uncertainty and
preventing repeated short reboot cycles from resetting lifetime. The debit does
not estimate or claim knowledge of powered-off elapsed time. This conservative,
deterministic model is appropriate without a trusted clock.

When remaining time reaches zero, EXPIRED is durably committed before reclaim.
Retry, backpressure, or reboot never restores budget. Expired Events cannot TX.

## 12. Wire Protocol 1 EVENT Geometry

`EVENT=0x05` is assigned as an additive Wire Protocol 1 packet type. Existing
values `COMMAND=0x01`, `ACK=0x02`, `ERROR=0x03`, and `RESPONSE=0x04` retain
their meanings. The six-byte header and 32-byte packet maximum are unchanged.
Legacy decoders safely reject unknown type 0x05; no existing byte is
reinterpreted. Therefore Wire Protocol remains `1`.

EVENT uses the normal header:

| Header field | EVENT meaning |
|---|---|
| type | `EVENT=0x05` |
| source/destination | Node and configured Hub routing IDs |
| sequence | transient attempt correlation; may change on retry |
| opcode | Event family |
| payload length | 14..26 |

EVENT payload:

| Offset | Size | Field |
|---:|---:|---|
| 0 | 4 | Event epoch |
| 4 | 4 | Event ID |
| 8 | 1 | Event flags |
| 9 | 4 | lifetime budget seconds |
| 13 | 1 | body length `N` |
| 14 | N | Event body, `0<=N<=12` |

Payload length MUST equal `14+N`. Epoch/ID are nonzero, reserved flag bits are
zero, lifetime is 60..86,400, opcode is a registered Event family, and body
length/schema must exactly match that family. Multi-byte fields are
little-endian. No C++ struct is serialized directly.

## 13. Event Admission Response Geometry

Hub admission reuses outer packet type ACK but defines an Event-specific
nine-byte payload, distinguishable from the existing one-byte COMMAND ACK:

| Offset | Size | Field |
|---:|---:|---|
| 0 | 1 | Event admission status |
| 1 | 4 | echoed Event epoch |
| 5 | 4 | echoed Event ID |

Statuses are:

```text
ADMITTED                    0x00
CAPACITY                    0x01
IDENTITY_CONTENT_MISMATCH   0x02
UNSUPPORTED_EVENT           0x03
MALFORMED_EVENT             0x04
```

The ACK reverses source/destination and copies the attempt sequence and Event
family opcode. Node acceptance requires ACK type, exact reversed endpoints,
exact active sequence, exact family, payload length 9, known status, and exact
epoch/ID. Status alone can never release custody.

Hub MAY send MALFORMED_EVENT only if routing, family, payload bounds, and the
full nonzero identity fields are safely parseable. Otherwise it silently
discards. Unsupported family may be correlated after common envelope
validation. No rejection mutates acceptance state.

ADMITTED may be sent only after durable new acceptance or for an exact
canonical duplicate already present. CAPACITY means no custody transfer.

## 14. Hub Event Admission State Machine

Processing order is normative:

```text
Wire framing/version/type/bounds
-> destination and configured source
-> common Event envelope and reserved fields
-> family/body schema
-> exact identity lookup
-> exact canonical-content comparison
-> capacity allocation
-> durable ACTIVE commit and read-back
-> ADMITTED transmission
```

Outcomes:

| Input | Hub action |
|---|---|
| New valid Event + capacity | durably create ACTIVE, then ACK ADMITTED |
| Exact ACTIVE duplicate | no mutation; ACK ADMITTED |
| Exact CONSUMED duplicate | no mutation; ACK ADMITTED |
| Same identity, different canonical content | ACK mismatch; increment diagnostic |
| Valid new Event, no slot | ACK CAPACITY; no mutation |
| Unsupported family | ACK UNSUPPORTED when correlatable; no mutation |
| Malformed Event | ACK MALFORMED when correlatable, otherwise discard |
| Wrong endpoint/type/version | discard; no Event-state mutation |

ACK start/transmit failure leaves durable acceptance intact; retransmission is
then an exact duplicate and regenerates ADMITTED.

## 15. Hub Acceptance Ledger and Deduplication

The Hub ledger is a dedicated persistent store with 8 logical dual-copy slots,
separate from settings and Node storage. `HUB_EVENT_CAPACITY=8`. Each encoded
slot copy is exactly 56 bytes:

| Offset | Size | Field |
|---:|---:|---|
| 0 | 4 | magic `0x48455631` (`HEV1`) |
| 4 | 2 | Hub Event-store schema `1` |
| 6 | 2 | record length `56` |
| 8 | 4 | record generation |
| 12 | 1 | ledger state |
| 13 | 1 | source device ID |
| 14 | 1 | Event family/opcode |
| 15 | 1 | Event flags |
| 16 | 1 | Event body length |
| 17 | 3 | reserved zero |
| 20 | 4 | Event epoch |
| 24 | 4 | Event ID |
| 28 | 4 | lifetime budget seconds |
| 32 | 4 | admission ordinal |
| 36 | 12 | Event body, unused tail zero |
| 48 | 4 | reserved zero |
| 52 | 4 | CRC-32/ISO-HDLC over bytes 0..51 |

All multi-byte fields are little-endian. Reserved bytes and unused body bytes
MUST be zero and are covered by the CRC. Encoding/decoding is field-wise and
independent of C++ structure padding. Each logical slot retains the same
inactive-copy write, commit, read-back, generation selection, and torn-write
fallback semantics as the Node store.

States:

- `EMPTY=0x00`: available; admission ordinal and all Event fields are zero.
- `ACTIVE=0x01`: Hub owns Event and must retain it for Host delivery.
- `CONSUMED=0x02`: Host consumption is durably proven; exact canonical content is
  retained temporarily as a tombstone.

Other state values invalidate that record copy. ACTIVE and CONSUMED records
require a nonzero admission ordinal.

`admission_ordinal` is persistent global Hub admission order. Zero is reserved.
It monotonically advances once for each newly admitted Event. Exact duplicates
do not allocate a new ordinal, and ACTIVE->CONSUMED retains the original value.
POLL returns the ACTIVE record with the oldest admission ordinal. ACTIVE records
MUST NOT be evicted. CONSUME commits ACTIVE->CONSUMED before reporting Host
success. A repeated consume succeeds only while matching ACTIVE/CONSUMED proof
exists.

The Hub admission-ordinal allocator uses two exact 24-byte metadata copies:

| Offset | Size | Field |
|---:|---:|---|
| 0 | 4 | magic `0x48414F31` (`HAO1`) |
| 4 | 2 | admission-ordinal schema `1` |
| 6 | 2 | record length `24` |
| 8 | 4 | metadata generation |
| 12 | 4 | next unreserved admission ordinal |
| 16 | 4 | reserved zero |
| 20 | 4 | CRC-32/ISO-HDLC over bytes 0..19 |

Multi-byte fields are little-endian and reserved bytes MUST be zero. The
inactive metadata copy is written completely, committed, read back, decoded,
and byte-compared before it becomes authoritative. Boot selects the newest
valid A/B copy using wrap-safe half-range generation ordering. One invalid copy
falls back to the other; equal generations with different bytes or two invalid
copies fail ordinal allocation closed and preserve all ledger records.

Ordinal zero is reserved. Fresh metadata sets `next_unreserved_admission_ordinal`
to 1. Ordinals are reserved in blocks of 32 by durably advancing the exclusive
high-water mark before a new ordinal can be placed in a ledger record. Skipped
ordinals after reset are permitted; reuse is not. New admission orders its
writes as allocator reservation when required, then ACTIVE record commit/read-
back, then ADMITTED ACK. Thus ordinal allocation cannot make an uncommitted
Event acknowledgeable. A reservation that would cross `0xFFFFFFFF`, generation
ambiguity, or unsafe metadata recovery fails new admission closed with local
storage diagnostics; existing custody remains available for recovery/Host
delivery and no ordinal is reset or wrapped.

Exact duplicate comparison includes every canonical field from Section 5.
Hashes MAY accelerate lookup but cannot be sole proof.

### 15.1 Tombstone reclamation

Strict Node FIFO makes a bounded exact rule possible: after the Hub durably
admits a later Event from the same source, the Node necessarily received
success for every earlier Event before it could transmit the later Event.
Therefore CONSUMED records from that source that are older in the same epoch may
be reclaimed after the later admission commits. A CONSUMED record in an older
epoch may also be reclaimed after a valid Event in a newer epoch commits.

If no later Event arrives, a CONSUMED tombstone remains. When a later valid
Event arrives and no EMPTY slot exists, the Hub MAY atomically replace the
oldest earlier CONSUMED record from that source: it writes the new ACTIVE Event
to the inactive copy of that same logical slot and makes it authoritative only
after commit/read-back. A torn replacement therefore recovers either the old
CONSUMED proof or the new ACTIVE Event. Without an earlier reclaimable
CONSUMED record, the Hub returns CAPACITY. This favors correctness over
availability while avoiding a full-ledger deadlock.

## 16. Hub Reboot and Duplicate Boundary

Hub acceptance state **is persistent** in v0.7.0. Boot recovers the admission-
ordinal allocator metadata, then scans both copies of all ledger slots,
validates exact geometry, CRC/schema/reserved bytes/content, identity and
nonzero ordinal uniqueness, selects the newest valid generation, and
reconstructs ACTIVE and CONSUMED records in ascending admission-ordinal order.
Ambiguous/corrupt nonempty slots or unsafe allocator metadata fail Event
admission closed and preserve bytes; they are not treated as free.

The mandatory lost-ACK/reboot case resolves as follows:

```text
Node stores E
Hub durably admits E as ACTIVE
admission ACK is lost
Node reboots and recovers E as QUEUED
Hub reboots and recovers E as ACTIVE
Node retransmits exact E
Hub classifies exact duplicate, does not deliver twice, and ACKs ADMITTED
Node durably releases E
```

If the Host consumed E before reboot, Hub recovers CONSUMED and still ACKs the
exact retransmission without redelivery. This is reliability deduplication, not
security anti-replay.

## 17. Hub Capacity and Backpressure

The ledger holds eight total ACTIVE/CONSUMED records. Accepted ACTIVE Events
are never dropped for new input. When no EMPTY or safely reclaimable CONSUMED
slot exists, a valid new Event receives CAPACITY.

Capacity does not establish custody and does not extend Node attempt/lifetime
budgets. Host consumption can change ACTIVE to CONSUMED; safe tombstone
reclamation follows Section 15. Queue pressure and capacity responses are
locally visible and diagnostic.

## 18. Radio Arbitration

RadioLib has one foreground owner. The ISR sets only the existing completion
flag. Arbitration occurs only at explicit state-machine boundaries.

### Node

The default Node posture is receive. Event TX is eligible only when:

- runtime is ready and radio phase is LISTENING;
- no received-radio flag is pending;
- no COMMAND ACK, structured RESPONSE, duplicate replay, storage operation,
  or rendering operation owns the relevant safe point;
- the FIFO head is READY and not expired; and
- attempts remain.

An eligible Event first acquires standby, rechecks the ISR flag, and yields to
received traffic if the flag became set. A Hub COMMAND admitted before Event TX
retains priority through its ACK and RESPONSE. Once nonblocking Event TX has
started it is not preempted; an arriving COMMAND may be lost and relies on the
existing Hub retry. After TX the Node immediately returns to receive for the
admission response.

### Hub

One existing Host-driven COMMAND transaction retains priority when active.
While waiting for its ACK/RESPONSE, a received EVENT is validated and may be
durably admitted only at an explicit safe point that does not corrupt the
active transaction; its admission ACK is queued as bounded immediate radio
work, then the active wait resumes with its original overall deadline (no
extension). If integration cannot safely interleave the response on current
RadioLib hardware, it may defer Event admission and send CAPACITY only when it
can truthfully receive/respond; it must not destroy the Hub transaction.

When idle, Event admission ACK has priority over starting a new Host COMMAND.
No path may concurrently call RadioLib. All waits/backoffs are deadlines, not
busy waits or architectural `delay()` calls.

## 19. Hub-to-Host Event Delivery

v0.7.0 uses synchronous Host polling, not unsolicited serial injection.

### POLL_EVENTS

- Host-local Hub operation; never sent over radio.
- Returns at most one ACTIVE Event: the record with the lowest/oldest durable
  admission ordinal.
- Returns success with an explicit `available=false` when none exists.
- Returns the complete source/family/identity/flags/lifetime/body record when
  available.
- Is non-destructive and does not transfer custody.
- Repeated polls may return the same Event.

### CONSUME_EVENT

- Host-local Hub operation identifying source+epoch+Event ID exactly.
- If matching ACTIVE, durably commits CONSUMED and then reports success.
- If exact matching CONSUMED remains, reports idempotent success without write.
- If identity is absent, returns NOT_FOUND; mismatch/corruption never succeeds.
- Host disconnect or response loss does not imply consumption. A retried Host
  request uses existing retained-request/result lifecycle plus ledger proof.

Persistent Hub custody therefore survives Hub reboot before and after polling.
Only durable consumption permits ACTIVE ownership release.

## 20. Host Protocol 0.2 Requirements

The future Host Protocol 0.2 specification MUST:

- retain Host Protocol 0.1 COBS/CRC framing, 128-byte payload bound, parser
  recovery, request IDs, and one-operation lifecycle;
- negotiate Event category/feature support without changing true 0.1 behavior;
- define an Event operation category plus POLL_EVENTS and CONSUME_EVENT;
- encode the complete identity and canonical Event content with explicit
  little-endian fields, not native structs;
- define available/no-Event, NOT_FOUND, storage failure, and malformed request
  results;
- fit one Event in one bounded response and never batch in v0.7.0;
- preserve non-destructive polling and explicit idempotent consumption; and
- state that Host frame delivery is not application processing proof.

This design does not assign Host numeric category/opcode/message values; Host
Protocol 0.2 owns those assignments and compatibility fixtures.

## 21. Event Producers and Registry Boundary

Wire opcode is the Event-family registry. Initial assignments and fixed body
sizes are:

| Opcode | Family | Exact body |
|---:|---|---|
| `0x40` | BUTTON | `button_event:uint8` |
| `0x41` | SENSOR_THRESHOLD | `capability_id:uint16, value_type:uint8, value:uint32, relation:uint8` |
| `0x44` | MANUAL_CHECK_IN | `reason:uint8` |

### 21.1 BUTTON (`0x40`)

The body is exactly one byte, `button_event`. It reuses the existing
`DeviceInput::ButtonEvent` numeric semantics:

| Value | Meaning |
|---:|---|
| `0x01` | `PRESS` |
| `0x02` | `RELEASE` |
| `0x03` | `SHORT_PRESS` |
| `0x04` | `LONG_PRESS` |
| `0x05` | `VERY_LONG_PRESS` |

`NONE=0x00` is not an Event and MUST NOT be encoded. All other values are
malformed. The Host Protocol 0.2 representative BUTTON body `0x02` therefore
means `RELEASE`.

### 21.2 SENSOR_THRESHOLD (`0x41`)

The body is exactly eight bytes:

| Offset | Size | Field |
|---:|---:|---|
| 0 | 2 | nonzero logical capability ID |
| 2 | 1 | value type |
| 3 | 4 | observed value bits |
| 7 | 1 | threshold relation |

Allowed value types are `UNSIGNED_32=0x02`, `SIGNED_32=0x03`,
`NORMALIZED_U16=0x04`, `FIXED_Q16_16=0x05`, and `ENUM_U16=0x06` from the
capability vocabulary. UNSIGNED_32 is an unsigned little-endian value;
SIGNED_32 and FIXED_Q16_16 preserve their exact signed 32-bit bit pattern;
NORMALIZED_U16 and ENUM_U16 use the low 16 bits and require the high 16 bits to
be zero. NONE and BOOLEAN are invalid for this family.

Threshold relation is closed:

| Value | Meaning |
|---:|---|
| `0x01` | `CROSSED_BELOW` — the compiled threshold became false-to-true on its below side |
| `0x02` | `CROSSED_ABOVE` — the compiled threshold became false-to-true on its above side |

Other relations are malformed. The threshold value and debounce/hysteresis
policy remain bounded compiled producer policy; they are not carried as a
predicate or script. Capability IDs are logical, never GPIO numbers.

### 21.3 MANUAL_CHECK_IN (`0x44`)

The body is exactly one byte, `reason`. The v0.7.0 closed registry contains one
value:

| Value | Meaning |
|---:|---|
| `0x01` | `USER_REQUEST` — a bounded local user action requested a check-in |

Zero and all other values are malformed. USER_REQUEST carries no panic,
duress, incident, or product-workflow meaning.

All multi-byte values are little-endian. No family accepts values outside its
closed registry or body geometry.

Status change, device error, and compiled local policy remain conceptual future
producers. Their Wire opcode values and body schemas are unallocated in v0.7.0;
they MUST NOT be emitted under an invented or reserved schema.

Producers call one bounded creation interface and receive ENQUEUED, QUEUE_FULL,
INVALID_EVENT, or STORAGE_FAILURE. They do not allocate identity, serialize
Wire packets, access storage/radio, or control retries.

The release slice MUST include button and at least one deterministic simulated
or safe sensor-threshold producer plus manual check-in. Other families may be
implemented only with bounded compiled semantics. No panic/duress, product
workflow, script, downloaded code, or general automation runtime is introduced.

## 22. Diagnostics

All counters are saturating `uint32` and increment exactly at the owning event:

| Counter concept | Increment point |
|---|---|
| enqueue accepted | durable Node record commit succeeds |
| queue full/rejected | valid creation request finds no FREE slot |
| persistence failure | required Node/Hub commit or read-back fails |
| Event recovered | boot reconstructs one QUEUED Node record |
| storage corruption | one logical record has no safely selectable state |
| Event attempt | write-ahead attempts increment commits |
| Event expired | EXPIRED terminal commit succeeds |
| attempt exhausted | FAILED commit after final attempt succeeds |
| Hub capacity rejection | Hub emits correlated CAPACITY |
| identity/content mismatch | Hub finds same identity with different content |
| duplicate retransmission | Hub exact-matches ACTIVE/CONSUMED input |
| successful admission | new ACTIVE durable commit succeeds |
| admission acknowledged | Node accepts exact ADMITTED response |
| Host poll returned Event | POLL encodes one ACTIVE Event |
| Host consumption | ACTIVE->CONSUMED durable commit succeeds |

Failed diagnostic persistence must not be invented: these runtime counters are
volatile unless a later explicit diagnostic store is designed. Durable Event
and ledger records remain the recovery authority. Hub unavailable becomes true
after the FIFO head completes one failed admission attempt (timeout or
CAPACITY), remains true through retry/backoff, and clears only on exact ADMITTED
or a successful existing Hub-originated exchange with the configured peer.

## 23. Security Disposition

Wire Protocol 1 remains unauthenticated and unencrypted. A forged Event may be
accepted; a forged exactly correlated ADMITTED response may cause premature
Node release. Persistent IDs, CRCs, deduplication, and tombstones are integrity
and reliability mechanisms, not authentication, encryption, trusted identity,
or anti-replay security.

F-02 peer authentication, F-03 authentication-first discard/response
governance, and F-04 authenticated persistent freshness/replay protection remain
open for later milestones. Source IDs and Event identity are not credentials.
v0.7.0 reliability is specified for benign loss, duplication, reboot, and
backpressure, not an adversarial radio peer.

## 24. Compatibility and Versioning

- Firmware begins from released v0.6.0 and will report v0.7.0 only when the
  milestone is implemented and released.
- Wire Protocol remains 1 because EVENT 0x05 and its ACK payload are additive;
  old decoders reject the unknown type and existing bytes are unchanged.
- COMMAND, ACK, ERROR, RESPONSE, TEST, structured opcodes, one-byte COMMAND ACK,
  and ACK-versus-RESPONSE meanings remain unchanged.
- Event ACK is distinguished by the active Event wait and exact nine-byte
  payload; it cannot complete a COMMAND transaction.
- Configuration Schema remains 1. Event stores have independent schema 1 and
  separate namespaces/records.
- Host Protocol 0.1 remains unchanged. Host Event operations require separately
  specified/negotiated Host Protocol 0.2.
- HELTEC_V4 remains the hardware profile and one-Hub/one-Node qualification
  scope.

## 25. Explicit Non-Goals

- RAM-only or reboot-destructive Event custody.
- Authentication, encryption, security anti-replay, or provisioning.
- Production panic/duress or product-specific workflow semantics.
- Multi-hop, routing, relays, mesh, or multi-Node contention policy.
- Arbitrary priority scheduling, bulk storage, databases, or unbounded logs.
- Scripts, bytecode, downloaded policies, transferred procedures, or RCE.
- Unrestricted hardware/GPIO control or new unauthenticated side effects.
- Unsolicited Host serial Event injection or Event batching.
- Trusted wall-clock expiry or powered-off elapsed-time claims.
- Life-safety or unlimited-delivery guarantees.

## 27. Physical Qualification Requirements

The implementation brief MUST define controlled two-board HELTEC_V4 scenarios
with recorded firmware/interface versions, identities, counters, OLED state,
serial evidence, and pass/fail results for:

1. Node Event creation/admission with Hub present.
2. Hub absent through at least one timeout/backoff, then restored.
3. Selective loss of admission ACK with exact retransmission and one Hub Event.
4. Node reboot/power cycle with a pending Event and eventual delivery.
5. Node reboot during TX/wait/backoff with attempts not reset.
6. Hub reboot after durable admission but before Node receives success.
7. Hub reboot with ACTIVE and CONSUMED records retained.
8. Host disconnect after poll and before consume; reconnect and retrieve again.
9. Lost Host consume response followed by idempotent retry.
10. Node queue saturation/newest rejection and later recovery.
11. Hub ledger saturation/CAPACITY without accepted-Event loss.
12. Multiple sequential FIFO Events with unique persistent identities.
13. Existing Hub COMMAND traffic interleaved with Node Event traffic.
14. UI/input/storage service and receive restoration during Event activity.
15. Existing v0.6.0 PC-to-Node operation and legacy TEST/ACK regression.

Power interruption fixtures must identify the intended write boundary. If a
precise torn-write boundary cannot be induced physically, native fault
injection is the authoritative logic proof and the physical limitation must be
recorded rather than claimed as passed.
