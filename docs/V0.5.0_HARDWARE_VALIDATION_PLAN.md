# ARGUS REDLINE v0.5.0 Hardware Validation Plan

**Status:** Preparation plan; no v0.5.0 hardware test or production implementation has started.

## Objective

Validate a low-risk local capability slice on the two established Heltec WiFi LoRa 32 V4.3 boards while preserving TEST/ACK traffic, UI responsiveness, singular GPIO ownership, and Wire Protocol `1`.

## Available hardware baseline

| Role | Board | Known release baseline |
|---|---|---|
| Hub/TX | Heltec WiFi LoRa 32 V4.3 | v0.4.0 production behavior |
| Node/RX | Heltec WiFi LoRa 32 V4.3 | v0.4.0 production behavior |

Exact COM ports and hardware IDs must be re-enumerated at test time rather than copied from an earlier session. Device role, configured IDs, firmware identity, and Wire Protocol must be recorded before capability testing.

## Safe first vertical slice

1. Registry enumeration and lookup with simulated handlers on both roles.
2. One digital input READ returning only an owner-supplied stable current-state snapshot, normally BOOLEAN pressed/not pressed, or a dedicated verified input.
3. One logical indicator SET through existing LED arbitration, never direct pin ownership.
4. One analog input read from a board-powered bounded potentiometer/divider after a safe ADC pin is verified.

No relay, external-power control, motor, servo, PWM load, hazardous actuator, or arbitrary pin command is permitted.

## Required extra components

- Breadboard and insulated jumper wires.
- Prefer a board-powered 10 kΩ linear potentiometer or resistor-divider set approved after the ADC limit is known.
- Current-limiting resistors suitable for any external indicator used instead of the built-in LED.
- Multimeter for source-voltage verification.
- Optional dedicated momentary switch and pull resistor if GPIO0 cannot be shared safely through DeviceInput state.

No separate external power supply is required for the preferred first ADC test. Any separately powered source requires explicit voltage, isolation, common-ground, and power-order review before connection.

## Wiring and electrical cautions

- Do not invent or select an ADC pin from memory. Verify the repository board definition, Heltec V4.3 schematic/pinout, existing firmware ownership, and ADC capability before wiring.
- Record the chosen pin, ADC channel, attenuation, maximum input voltage, divider values, ground reference, and measured input voltage alongside each returned raw and/or normalized value.
- Never exceed the ESP32-S3 or board-specific ADC input limit. Start at zero volts and increase only within the approved bounded range.
- Never drive a pin configured as an output from an external source.
- Never allow a separately powered source to drive an unpowered board input.
- GPIO0 is active-low input and an ESP32-S3 boot strap. Do not hold it during reset; do not add competing polling or reconfiguration beside DeviceInput.
- Confirm built-in LED pin, polarity, and existing radio/button ownership before any physical indicator operation.
- Disconnect the signal source before powering down or changing wiring. Power down before changing external wiring. Physical actions remain operator-executed one step at a time.

## Ownership cautions

DeviceInput remains sole owner of GPIO0 timing and classification. DIGITAL_INPUT READ returns only an owner-supplied stable current-state snapshot, normally BOOLEAN pressed/not pressed. Capability code must not call `digitalRead`, alter mode, debounce independently, or expose, reproduce, consume, or generate PRESS, RELEASE, SHORT_PRESS, LONG_PRESS, VERY_LONG_PRESS, startup suppression, debounce, or wake-tail events. Existing DeviceInput classification remains a separate regression concern. If DeviceInput cannot supply a clean stable snapshot without coupling capability state to its event state, keep DIGITAL_INPUT simulated or use a separately verified dedicated input.

The existing LED output is the OR of approved operational and feedback ownership. A capability may add an application-indicator state only through that arbitration. LED-disabled settings must remain authoritative. If this cannot be done without ambiguity, keep the output simulated or use a separately verified external LED.

## Simulated-first sequence

1. Validate descriptor table, count, order, IDs, classes, operation flags, and no pin exposure using native tests.
2. Dispatch READ/SET to a fixed simulated handler and verify structured values, denials, busy, and hardware-failure propagation.
3. Compile both roles with local capability integration but no radio exposure.
4. Confirm simulated capability work cannot block Hub transaction or Node receive/ACK ownership.
5. Review the exact physical binding and wiring before enabling a real handler.

Any registry-validation failure, duplicate ID, handler call after denial, unbounded operation, direct pin leak, or radio ownership ambiguity stops progression.

## Physical test sequence

1. Flash production-role firmware containing registry-only integration and simulated handlers; verify identities, v0.5.0 development identity as approved later, Wire Protocol `1`, READY state, Node listening, and normal TEST/ACK.
2. Exercise deterministic local enumeration and lookup. Verify the bounded descriptor summary and absence of GPIO numbers/application labels.
3. Exercise DIGITAL_INPUT READ without competing with DeviceInput: read stable idle, pressed, and released snapshots and require the expected BOOLEAN state only. Separately regress existing UI short-, long-, and very-long-press behavior and startup-held suppression; these events are not capability output.
4. Exercise one explicit local indicator invocation through the approved arbitration layer. Verify radio indication, button feedback, capability-controlled state, master LED disable, and overlap behavior without blocking.
5. Disconnect the signal, power down, and wire the preferred board-powered approved potentiometer/divider. After restoring power, verify each input voltage with a meter and record it with the returned raw and/or normalized value. Test minimum, a representative midpoint, and the approved maximum without exceeding the reviewed ADC range. Use a separately powered source only after the explicit voltage/isolation/ground/power-order review.
6. Run each local capability operation while normal TEST/ACK exchanges continue. Record ACKs, retries, timeouts, UI gaps, operation duration, denial status, and handler count.
7. After capability actions, observe at least 30 consecutive matching TEST/ACK exchanges.
8. Confirm no repeated operation loop, stuck output, blocked Node receive state, repeated local dispatch without a new explicit local invocation, watchdog output, or reset.
9. Reset both boards, then perform a normal power-cycle regression. Registry contents must return from the compiled profile; no capability persistence write should occur.

## Expected observations

- Serial startup retains role, device IDs, firmware identity, Wire Protocol `1`, and READY/listening evidence.
- Enumeration reports a fixed count and deterministic logical IDs.
- DIGITAL_INPUT READ reports only a stable BOOLEAN current-state snapshot; DeviceInput events remain observable only through their existing UI/input behavior.
- Each explicit local invocation yields one concise structured status/value and one handler attempt at most.
- Analog evidence pairs measured input voltage with returned raw and/or normalized value at minimum, midpoint, and approved maximum.
- Unsupported, type-invalid, out-of-range, unauthorized, and interlocked operations do not call hardware.
- OLED, if approved, shows only a bounded count/last-status summary and remains legible.
- Radio traffic does not expose new capability packets in v0.5.0.

## Radio coexistence target

- Preserve periodic Hub TEST and Node ACK ordering, sequence matching, retries, timeout policy, duplicate replay, and receive restoration.
- Observe at least 30/30 matching exchanges after capability actions.
- Record retries, ACK timeouts, malformed packets, mismatches, duplicates, receive gaps, watchdog output, resets, and RSSI/SNR range.
- A short run is regression evidence, not endurance evidence.

## Failure observations and stop conditions

Stop and diagnose before further physical action if any of these occurs:

- Wrong role, device ID, firmware identity, or Wire Protocol.
- OLED corruption, UI blocking, or button-classification regression.
- Missed/mismatched ACK, unexpected retry, duplicate behavior change, or Node receive restoration failure associated with an operation.
- More than one handler execution per explicit local invocation, or repeated local dispatch/output without a new explicit local invocation.
- DIGITAL_INPUT exposes or alters DeviceInput events, debounce, startup suppression, or wake-tail behavior, or existing UI short/long/very-long classification regresses.
- Raw GPIO appearing in a descriptor, local API, UI, serial output, or operation input.
- Authorization/interlock denial followed by handler activity.
- ADC voltage outside the reviewed range, unstable ground, unexpected heating/current, or board reset.
- LED arbitration conflict or direct capability ownership bypass.

## Deferred hardware

- Relay-controlled or external power.
- Motors, servos, PWM loads, sirens, hazardous outputs, and high-current indicators.
- Production sensors, power monitors, GNSS/location, local storage capabilities, and procedures.
- Multi-Node, repeater, routing, mesh, and store-and-forward testing.
- Host Protocol, serial console, and radio capability operations.
- Extended endurance, destructive electrical testing, and fault injection beyond approved low-risk scenarios.
