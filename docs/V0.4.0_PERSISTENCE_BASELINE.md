# ARGUS REDLINE v0.4.0 Persistence Baseline

**Step:** 1 — Characterize baseline

**Baseline commit:** `0dae7d5`

**Production behavior changed:** No

## Purpose and scope

This document records the v0.3.0 behavior that v0.4.0 persistent-settings work
must preserve. It characterizes the absence of persistence, current defaults,
LED and UI ownership, boot order, and timing boundaries before any production
implementation begins.

This step does not add a settings model, storage codec, NVS adapter, recovery
manager, factory reset, editor, firmware integration, or tests. The approved
v0.4.0 scope remains ordinary persistent settings and configuration recovery
only, as defined by the [v0.4.0 implementation brief](V0.4.0_IMPLEMENTATION_BRIEF.md).

## Persistence absence and volatile state

The current production graph contains no Arduino `Preferences`, ESP-IDF NVS,
EEPROM, filesystem, settings schema, record codec, migration, recovery, or
factory-reset implementation. No production component reads or writes settings
at boot or during `loop()`.

The following state is currently volatile and begins from firmware-defined
defaults after each restart:

- UI screen, awake/sleep state, render scheduling, and input timing;
- health, phase, radio metrics, last inbound packet, activity, counters, and
  errors;
- Hub sequence, retry count, ACK deadline, and transaction state;
- Node single-entry duplicate metadata and remembered ACK status;
- peer reachability/seen presentation state.

Compile-time local and peer IDs remain owned by `DeviceConfig`; they are not
settings and must not become persistent ordinary configuration in v0.4.0.
Wire Protocol, transaction state, and duplicate state likewise remain outside
persistence.

## Current defaults

| Behavior | v0.3.0 default and source |
|---|---|
| Display timeout | 30 seconds, owned by `DeviceUi::Controller` |
| Initial screen | Home, owned by `DeviceUi::Controller` |
| Display state | Awake and initially dirty, so the first eligible UI service renders |
| OLED contrast | ThingPulse 128x64 initialization value `0xCF` (207); firmware does not currently apply a separate setting |
| Radio LED | Enabled unconditionally by firmware around Hub command transmit and Node ACK transmit |
| Diagnostics | Visible in the six-screen navigation order; counters continue collecting |
| Button feedback | No separate feedback behavior or setting |
| Button input | Active-low GPIO0 with `INPUT_PULLUP`, 30 ms debounce, and 800 ms long press |

The six-screen order is Home, Radio, Device, Last Packet, Diagnostics, About,
then Home. A short press advances one screen. A long press returns to Home when
on another normal screen. A gesture that wakes a sleeping display is suppressed
from navigation.

## Ownership boundaries

| Concern | Current owner |
|---|---|
| Compile-time local and peer identity | `DeviceConfig` and PlatformIO build flags |
| Wire Protocol 1 bytes and validation | `Protocol` |
| Hub retry, sequence, ACK wait, and completion | `HubTransactionState` |
| Node duplicate classification and cached ACK status | `NodeDuplicateTracker` |
| Volatile health, activity, packet, metric, counter, and error observations | `RuntimeState::State` |
| Debounce and semantic button events | `DeviceInput::Button` |
| Screen order, timeout, wake suppression, dirty state, and render scheduling | `DeviceUi::Controller` |
| Bounded role-aware presentation snapshots | `DeviceUi::buildPresentation()` |
| OLED drawing and display power calls | `HeltecDisplay::Renderer` |
| GPIO, LED writes, OLED/radio initialization, `millis()`, and orchestration | Hub and Node `main.cpp` |

The built-in LED is production-firmware-owned. The Hub sets it high immediately
before `radio.startTransmit()` and low when transmission completes or start
fails. The Node does the same around ACK transmission. Input classification,
UI policy, display rendering, runtime state, protocol, and transaction-engine
components do not write the physical LED.

## Current boot order

Both roles currently perform the following order:

1. Start Serial at 115200 baud.
2. Configure the built-in LED, Vext, OLED reset, and GPIO0 button pins.
3. Drive the LED low and Vext low, then wait 100 ms.
4. Pulse OLED reset low for 20 ms and high for 20 ms.
5. Initialize the OLED.
6. Initialize the radio SPI bus and start the SX1262 at 915 MHz.
7. On successful radio initialization, install the DIO1 completion callback.
8. Establish the role-specific ready state and service the initial UI render.

The Node additionally starts receive mode before marking itself ready. The Hub
marks itself ready and schedules its first command for 2000 ms later. On radio
initialization failure, either role renders the error state and does not enter
normal transport service.

There is currently no storage phase in this sequence. The v0.4.0 integration
point defined by the brief belongs after OLED initialization and before radio
initialization, but Step 1 does not add it.

## Timing and radio/UI ordering

### Shared input and UI timing

- GPIO0 debounce is 30 ms and long press is emitted at 800 ms of stable hold.
- OLED inactivity timeout is 30,000 ms.
- UI renders are rate-limited to at least 100 ms apart.
- Radio, Last Packet, and Diagnostics live screens refresh every 1,000 ms while
  awake.
- Display sleep affects OLED work only; radio processing continues.
- Both loops service button input before transport work and UI work.

### Hub timing and order

- The first command is scheduled 2,000 ms after successful setup.
- Successful or terminal transactions schedule the next command 3,000 ms later.
- A failed attempt schedules an eligible retry 500 ms later.
- ACK wait timeout is 2,500 ms.
- A transaction permits exactly two retries after the initial attempt.
- After command transmission completes, the LED is cleared and ACK receive is
  started before later UI service in the loop.
- Normal loop order is button service, Hub transport service, then UI service.

### Node timing and order

- The Node enters receive mode during setup before it becomes ready.
- For an accepted, unsupported, malformed, or duplicate command that requires an
  ACK, the Node preserves the existing 100 ms pre-ACK delay.
- The Node sets the LED high immediately before ACK transmission and clears it
  when transmission completion is serviced.
- After ACK completion, radio standby/finish handling and receive restart occur
  before OLED I/O is allowed.
- While an ACK is actively transmitting, UI service is explicitly deferred.
- Normal loop order is button service, completed radio-operation service, then
  UI service only when not transmitting an ACK.

The radio DIO1 callback for both roles only sets a volatile completion flag.
Rendering and all other orchestration occur outside the interrupt context.

## Constraints carried into later v0.4.0 steps

- Ordinary settings must not change Wire Protocol 1, IDs, topology, radio
  parameters, retry/ACK policy, sequence handling, or duplicate semantics.
- Runtime counters, metrics, packet history, errors, peer state, sequence,
  retries, and duplicate state must remain volatile.
- Storage and display operations must remain outside interrupts and radio packet
  callbacks.
- Hub storage work must not interrupt an active transaction or ACK wait.
- Node storage and UI work must not delay ACK completion or receive restart.
- First boot must continue safely from defaults without requiring a write.
- Hardware characterization, not this document, must establish safe NVS timing.
