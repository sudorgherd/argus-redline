# ARGUS REDLINE v0.6.0 Implementation Brief

## Structured Operations, Responses, and Host Protocol

**Planning status:** PREPARED

**Implementation status:** NOT STARTED

**Entry gate:** successful completion of required v0.5.x qualification

**Planned firmware release:** `v0.6.0`

**Initial Host Protocol:** developmental `0.1`, independently versioned

## 1. Purpose and entry assumption

v0.6.0 adds the bounded machine interface and structured operation/response
layer above the completed v0.5 capability foundation. It proves one complete
computer-to-Hub-to-Node-to-computer transaction without making embedded
firmware the owner of application meaning.

This brief may be reviewed before its entry gate is met. Implementation Step 1
must not begin until required v0.5.x qualification has completed successfully.
Once implementation begins, the following are stable prerequisites rather
than temporary validation questions:

- the v0.5 descriptor vocabulary and immutable bounded `CapabilityRegistry`;
- opaque `CapabilityId`, `CapabilityValue`, `OperationResult`, and
  `OperationStatus` contracts;
- caller authorization and safety/interlock policies;
- the `HELTEC_V4` profile and role-safe local capability dispatch;
- capability diagnostics and bounded RuntimeState/UI snapshots;
- singular DeviceInput and LED-arbitration ownership.

Any v0.5 qualification failure is corrected and requalified in the v0.5.x
line before this baseline is accepted. v0.6.0 is not designed around an
unresolved v0.5 hardware state.

## 2. Architectural boundary

ARGUS REDLINE is a resilient field communications and capability substrate
whose current physical transport is LoRa. The governing rule remains:

> Applications own meaning. REDLINE owns transport.

Host applications and services own workflows, databases, rich UI, automation
policy, third-party integration, application schemas, and interpretation.
REDLINE firmware owns identity, bounded host framing, request validation,
radio mechanics, retries, duplicate behavior, constrained capability exposure,
authorization/interlock gates, and local state necessary to report truthful
transport outcomes.

The layers remain separate:

```text
host application or development utility
        ↓
physical USB/serial transport
        ↓
Host Protocol 0.1 framing and message codec
        ↓
structured REDLINE operation service
        ↓
Hub radio transaction ownership / local capability dispatch
        ↓
Wire Protocol and LoRa transport
```

Physical transport, framing, message encoding, operation semantics, and radio
transport are independent concerns. The Step 12 characterization command
surface is fixed test scaffolding; it is not reused or expanded into Host
Protocol.

## 3. Independent compatibility lifecycles

v0.6.0 tracks these authorities independently:

| Lifecycle | Entry baseline | v0.6 rule |
|---|---|---|
| Firmware | `v0.5.x` qualified | Becomes `v0.6.0` only at release finalization |
| Wire Protocol | `1` | Retain unless the radio-visible schema review deliberately approves a new version |
| Host Protocol | none | Introduce developmental `0.1` |
| Configuration Schema | `1` | Remain `1` unless an explicit persistent-setting gate is approved |
| Hardware profile | `HELTEC_V4` | Remain unchanged |

Host Protocol `0.1` is represented as separate fixed `uint8_t` major and minor
fields: major `0`, minor `1`. Firmware version inference never substitutes for
Host Protocol negotiation. A firmware release does not implicitly change Host
Protocol, Wire Protocol, Configuration Schema, or hardware profile.

Radio-visible structured operations and RESPONSE behavior are assigned to
v0.6.0 by the roadmap. Step 9 must decide compatibility deliberately. The
recommended default is Wire Protocol `2` if existing Wire 1 peers would reject
or misinterpret any new packet type or schema; retaining Wire 1 is acceptable
only with documented additive compatibility and mixed-version tests. No step
may silently reinterpret Wire 1.

## 4. Host Protocol 0.1 framing

Use binary COBS framing with `0x00` as the frame delimiter. COBS is recommended
because it provides deterministic delimiter recovery, bounded worst-case
expansion, simple native tests, and no scanning ambiguity after malformed
input. Newline-delimited text is rejected as the machine protocol because
parsing and escaping are less deterministic. Raw length-prefix-only framing is
rejected because a damaged length has no reliable synchronization boundary.
SLIP is viable but has variable escape handling without a material advantage
for this bounded frame.

The decoded Host Protocol 0.1 envelope is:

```text
major version       uint8_t
minor version       uint8_t
message type        uint8_t
flags               uint8_t, zero in 0.1
request ID          uint16_t little-endian
payload length      uint16_t little-endian
payload             0..128 bytes
CRC-16/CCITT-FALSE  uint16_t little-endian over header + payload
```

The decoded maximum is 138 bytes. The encoded buffer must use a compile-time
bound sufficient for worst-case COBS expansion plus the delimiter; the codec
must assert that bound rather than allocate dynamically. CRC detects malformed
content independently of USB transport guarantees. It is integrity checking,
not authentication.

Parser requirements:

- consume partial frames across service calls without blocking;
- decode multiple back-to-back frames from one input span;
- discard an oversized encoded candidate through the next delimiter;
- recover at the next delimiter after bad COBS, length, CRC, or version;
- reject unknown major versions and unsupported message types explicitly;
- allow a compatible minor version only through documented negotiation rules;
- clear partial framing state on transport reset/disconnect;
- never retain pointers into the input buffer or use unbounded strings.

## 5. Message and operation model

Host message types are a small fixed vocabulary:

```text
HELLO_REQUEST / HELLO_RESPONSE
OPERATION_REQUEST / OPERATION_RESPONSE
PROTOCOL_ERROR
```

Exact numeric values are frozen in Step 2 and tested thereafter. HELLO reports
Host Protocol version, firmware, Wire Protocol, Configuration Schema, hardware
profile, role, device ID, and the structured operation categories implemented
by this firmware. It does not enumerate application features.

An `OPERATION_REQUEST` contains:

```text
request ID          from the envelope
operation category uint8_t
target device ID   uint8_t
operation code     uint8_t
target ID          uint16_t (CapabilityId for capability category)
value              exact v0.5 CapabilityValue encoding when required
```

Flags remain zero unless a concrete 0.1 requirement is approved. No caller
chooses a GPIO, pin mode, pointer, memory address, handler, policy ID, or raw
function. Typed value encoding is field-by-field and never copies compiler
struct memory.

Minimum operation categories:

- device: `PING`, `GET_DEVICE_INFO`, `GET_STATUS`;
- capability: `ENUMERATE`, `DESCRIBE`, `READ`, `SET`;
- compiled local procedure: `RUN_PROCEDURE`, only for an explicitly registered
  known procedure if its separate safety review passes;
- diagnostic snapshot: bounded read-only status needed to validate the path.

`TRIGGER` remains structurally representable but is not exposed unless an
approved registered v0.6 target requires it. No operation is included merely
because the Host Protocol could carry it. General opaque application payloads,
events, multi-Node orchestration, and later roadmap operations remain deferred.

## 6. Structured responses and error separation

An `OPERATION_RESPONSE` contains:

```text
request ID          from the envelope
operation category uint8_t
target device ID   uint8_t
operation code     uint8_t
result class       uint8_t
operation status   uint8_t when result class is capability
typed value        bounded and present only when defined
transport detail   bounded enum/fields only when result is radio transport
```

Response encoding is deterministic and correlated by the exact 16-bit request
ID. `OperationStatus` is reused for capability results. A second capability
status vocabulary is prohibited.

Failures remain distinguishable:

- frame/protocol failure: invalid COBS, length, CRC, version, or message type;
- request validation failure: malformed fields, unsupported operation, bad
  target, bad value type, or range;
- authorization/safety denial: existing `UNAUTHORIZED` or
  `INTERLOCK_ACTIVE` semantics;
- capability result: existing `OperationStatus` and typed value;
- radio transaction result: accepted, busy, timeout, remote rejection,
  mismatch, or other transport-owned terminal result;
- local runtime/hardware failure: existing `HARDWARE_UNAVAILABLE`, `BUSY`, or
  `OPERATION_FAILED` where semantically applicable.

Transport delivery is never represented as an application outcome. ACK means
transport acknowledgment; RESPONSE carries a structured operation result.

## 7. Radio-facing scope

The required vertical slice is:

```text
PC request
→ Hub Host Protocol parser
→ one Hub-owned radio transaction
→ Node structured request validation
→ existing capability dispatcher or bounded device operation
→ structured Node response
→ Hub transaction completion
→ correlated Host Protocol response
```

The host requests intent; firmware owns sequence numbers, radio timing,
retries, ACK timeout, duplicate suppression, response matching, and receive
restoration. Host request IDs do not replace Wire sequence ownership. The Hub
maintains the bounded correlation between its one active host request and its
one active radio transaction.

Node execution remains subordinate to packet validation, duplicate handling,
ACK construction/transmission, and receive restoration. Duplicate structured
requests must not repeat a physical action. The exact cached transaction/result
metadata and late/mismatched response rules are frozen with the Wire decision.
No host parser runs from ISR context or inside protocol codec internals.

## 8. Concurrency, backpressure, and lifecycle

Use one outstanding accepted Host operation and one terminal response slot in
v0.6.0. This matches the existing single Hub transaction owner and proves the
architecture without a general scheduler.

- HELLO may be answered only when doing so cannot disturb radio ownership.
- A new operation while another is active or a terminal response is awaiting
  emission receives a correlated `BUSY`/rejected response and is not queued.
- Responses preserve acceptance order; with one slot, reordering is impossible.
- Host parsing consumes a bounded byte budget per loop and never blocks radio,
  OLED, DeviceInput, settings persistence, capability safe points, or Node ACK.
- Local operations use existing role-safe capability execution seams.
- Radio work uses existing transaction ownership and timers.
- No general job queue, event bus, task, or background thread is introduced.

Disconnect does not cancel accepted radio work. A completed result remains in
the one terminal slot for emission after reconnect. A partial inbound frame is
discarded on disconnect. Device reset clears volatile Host Protocol state; a
host that cannot prove an old request outcome treats it as ambiguous rather
than resubmitting a physical action blindly. Repeating the same request ID
while it is active or retained must not invoke the operation again. The stable
cross-reset idempotency lifecycle remains assigned to the later host-service
milestone.

The device continues normal radio, UI, input, and settings behavior with no
host connected.

## 9. Authorization and safety

A physical USB connection is an authority boundary, not proof of a user or
cryptographic identity. Host Protocol 0.1 adds `CallerClass::HOST_LOCAL` only
through an explicit v0.6 capability-model extension and policy review. The
recommended initial rule is a compile-time local-host policy that permits only
the documented operation surface and remains distinct from
`FUTURE_REMOTE`.

Radio-originated Node execution remains a separate caller/trust context and
must pass the same descriptor operation support, authorization, and interlock
gates. Unknown caller classes, operations, policies, targets, and malformed
values fail closed. v0.6.0 does not claim authenticated USB users or implement
the later network security system.

## 10. Diagnostics, UI, settings, and resources

Host Protocol diagnostics are separately owned and use saturating counters:

```text
framesReceived
framesAccepted
malformedFrames
unsupportedVersions
unsupportedMessageTypes
requestsDispatched
responsesEmitted
busyOrRejectedRequests
transportResets
```

No unbounded log is added. Host counters do not reuse radio or capability
counters. RuntimeState may receive a copied bounded snapshot only if production
integration requires it.

Default UI impact is none: no new screen, host browser, capability invocation
menu, or host application UI. A bounded existing-row status change requires a
separate approval and must not wake the display.

Configuration Schema remains `1`. Host request IDs, parser state, active work,
responses, and diagnostics are volatile. No Host Protocol runtime state is
written to settings. Any persistent setting requires an explicit schema and
recovery gate.

Final v0.5.0 production baseline:

```text
Hub:  RAM 20,428 bytes; Flash 354,193 bytes
Node: RAM 20,452 bytes; Flash 351,809 bytes
```

Every meaningful step reports both role sizes and deltas. Review is required
for any single step adding more than 1 KiB RAM per role or 16 KiB flash per
role, and for any unexplained change. These are review thresholds, not budgets
to consume. Avoid large serialization libraries, heap-backed parser stacks,
and application frameworks.

## 11. Native-first implementation sequence

### Step 1 — Baseline and entry-gate verification

- **Objective:** confirm successful v0.5.x qualification, clean main-derived
  branch, exact versions, ownership map, tests, and binary sizes.
- **Likely files:** a v0.6 baseline document only.
- **Invariants/tests:** rerun native suite, fixtures, both production builds,
  protocol/settings/capability compatibility fixtures, and `git diff --check`.
- **Completion gate:** no unresolved v0.5.x qualification item or ambiguous
  baseline; production-code diff zero.
- **Non-goals:** no Host Protocol types or firmware edits.

### Step 2 — Host Protocol vocabulary and lifecycle

- **Objective:** define Host Protocol 0.1 version, message types, operation
  categories, result classes, fixed numeric values, and known/unknown checks.
- **Likely files:** `lib/host_protocol/`, focused native tests, brief update only
  for an approved design correction.
- **Invariants/tests:** exact values, unknown/reserved rejection, no dependency
  on Arduino, radio, UI, settings, or capability hardware.
- **Completion gate:** lifecycle remains independent from Firmware/Wire/Schema/
  profile; no code path or parser yet.
- **Non-goals:** no codec, transport, dispatch, or production integration.

### Step 3 — Bounded frame codec

- **Objective:** implement field-wise envelope and COBS/CRC codec with exact
  compile-time limits.
- **Likely files:** `lib/host_protocol/`, codec tests.
- **Invariants/tests:** minimum/maximum frames, exact lengths, CRC vectors,
  round trips, malformed length, COBS errors, bad version, unknown type, no raw
  struct serialization, heap, exceptions, or strings.
- **Completion gate:** deterministic encode/decode and size assertions pass.
- **Non-goals:** no streaming parser or operation semantics.

### Step 4 — Structured request and response model

- **Objective:** encode/decode HELLO and operation request/response payloads,
  including typed capability values and distinct failure classes.
- **Likely files:** host protocol plus a narrow structured-operations library.
- **Invariants/tests:** request correlation, valid/invalid targets, wrong types,
  range errors, all `OperationStatus` mappings, no duplicate capability model.
- **Completion gate:** every exposed operation has a documented bounded schema.
- **Non-goals:** no handler/radio execution or application payload.

### Step 5 — Streaming parser and recovery

- **Objective:** consume bounded byte spans across service calls and emit at
  most one validated frame event per bounded service budget.
- **Likely files:** `lib/host_protocol/`, parser tests.
- **Invariants/tests:** every split point, partial frame, concatenated frames,
  empty delimiters, oversized input, malformed recovery, disconnect/reset,
  fuzz-like deterministic byte corpora.
- **Completion gate:** next valid frame is recovered after every malformed case
  without buffer overrun or unbounded loop.
- **Non-goals:** no Arduino Serial, dispatch, queue, or response execution.

### Step 6 — Physical host transport adapter

- **Objective:** isolate nonblocking ESP32-S3 USB/Serial byte input/output from
  the pure parser/codec through fixed buffers.
- **Likely files:** `lib/host_transport/`, compile fixtures; role mains later.
- **Invariants/tests:** bounded read/write budgets, disconnect/reconnect state,
  partial-output handling, no human CLI or characterization-command reuse.
- **Completion gate:** adapter compiles for both roles and remains mockable
  natively; radio ownership is untouched.
- **Non-goals:** no operation bridge or active production service.

### Step 7 — Local capability bridge

- **Objective:** map host capability enumerate/describe/read/set requests into
  the v0.5 registry, typed validators, role-safe dispatcher, and diagnostics.
- **Likely files:** `lib/host_operation_service/`, capability integration tests.
- **Invariants/tests:** invalid ID, unsupported operation, wrong type, range,
  authorization, interlock, unavailable hardware, BUSY, exact result mapping,
  handler count, no GPIO exposure.
- **Completion gate:** simulated and HELTEC_V4 profile paths return correlated
  structured responses without parallel capability semantics.
- **Non-goals:** no radio bridge, UI caller, arbitrary policies, or analog enable.

### Step 8 — Device information and status operations

- **Objective:** implement PING, GET_DEVICE_INFO, GET_STATUS, HELLO negotiation,
  and bounded diagnostic snapshot reads.
- **Likely files:** host operation service, version/runtime snapshot adapters.
- **Invariants/tests:** exact version authorities, role/ID/status snapshots,
  copied ownership, counter saturation, no mutable RuntimeState exposure.
- **Completion gate:** local Hub and applicable Node requests are deterministic
  and application-neutral.
- **Non-goals:** no settings writes, application state, database, or rich UI.

### Step 9 — Wire operation and RESPONSE design gate

- **Objective:** freeze formal radio opcodes/payloads, ACK-versus-RESPONSE
  semantics, compatibility version, duplicate/result caching, and bounds.
- **Likely files:** design document first; protocol code only after approval.
- **Invariants/tests:** deliberate Wire version decision, old TEST/ACK fixture
  disposition, maximum 32-byte geometry, malformed/unknown behavior, late and
  mismatched response rules.
- **Completion gate:** explicit compatibility review approves Wire 1 additive
  use or Wire 2 migration before encoded bytes change.
- **Non-goals:** no silent Wire mutation, fragmentation, opaque application
  transport, EVENT, or multi-Node work.

### Step 10 — Radio structured-operation bridge

- **Objective:** map one accepted host request to one Hub-owned transaction,
  Node execution, structured response, and correlated host result.
- **Likely files:** protocol/transaction engine extensions, a narrow bridge,
  role-independent tests.
- **Invariants/tests:** timeout, retry, duplicate request/response, no repeated
  physical action, late/mismatched response, Node ACK ordering and receive
  restoration, host request ID separate from Wire sequence.
- **Completion gate:** deterministic native PC→Hub→Node→Hub→PC state model.
- **Non-goals:** no events, multiple active transactions, routing, or host app.

### Step 11 — Backpressure and host-link lifecycle

- **Objective:** implement one active request/one terminal response ownership,
  BUSY rejection, disconnect continuation, reconnect emission, and reset rules.
- **Likely files:** host operation service and lifecycle tests.
- **Invariants/tests:** overproduction, repeated request ID, response ordering,
  disconnect during radio transaction, reconnect, reset ambiguity, host absent.
- **Completion gate:** no duplicate execution and core device operation never
  depends on host presence.
- **Non-goals:** no general scheduler, multi-depth queue, persistent journal,
  or stable v0.12 host-service lifecycle.

### Step 12 — Diagnostics and RuntimeState boundary

- **Objective:** add separately owned saturating Host Protocol counters and a
  copied snapshot only where production presentation/validation needs it.
- **Likely files:** host protocol diagnostics, optional RuntimeState snapshot.
- **Invariants/tests:** exact status-to-counter mapping, saturation, copied
  ownership, no radio/capability counter mutation or automatic health changes.
- **Completion gate:** diagnostics observe but never alter parser, dispatch, or
  radio results.
- **Non-goals:** no unbounded log, persistence, new screen, or ErrorClass reuse.

### Step 13 — Production role integration

- **Objective:** service bounded host input/output in Hub and, only where
  applicable, Node loops without violating existing safe points.
- **Likely files:** `src-tx/main.cpp`, `src-rx/main.cpp`, host adapter/service.
- **Invariants/tests:** radio RX/TX, ACK, retry timers, OLED, DeviceInput,
  persistence, local capabilities, and quiet maintenance remain authoritative;
  no blocking Serial loop.
- **Completion gate:** both builds pass within reviewed size deltas and host
  absence preserves ordinary operation.
- **Non-goals:** no characterization console merge, UI invocation, task, or
  settings schema change.

### Step 14 — Host-side reference utility

- **Objective:** provide the smallest test/reference utility needed to encode,
  submit, correlate, and decode Host Protocol 0.1 during qualification.
- **Likely files:** repository-consistent host test/tool directory and fixtures.
- **Invariants/tests:** machine protocol only, deterministic vectors shared
  with firmware, no ARGUS workflow/business semantics or stable SDK claim.
- **Completion gate:** utility proves all initial operations and malformed test
  vectors reproducibly.
- **Non-goals:** no production service, database, rich UI, automation, or
  third-party SDK.

### Step 15 — Physical host and coexistence qualification

- **Objective:** validate both V4.3 boards, USB/serial lifecycle, complete
  structured radio vertical slice, and existing device behavior.
- **Likely files:** evidence worksheet/documentation only unless a defect is
  found and fixed in its owning layer.
- **Invariants/tests:** host connection to Hub and applicable Node; HELLO;
  enumerate/describe/read; authorized indicator SET; denials; correlation;
  timeout; disconnect/reconnect; host absent; concurrent radio traffic;
  OLED/input/settings regression; receive restoration.
- **Completion gate:** physical Host Protocol and radio/host coexistence pass
  with no unexplained reset, retry, duplicate action, UI gap, or ownership loss.
- **Non-goals:** no claim of endurance, security completion, general app
  transport, or later hardware features.

### Step 16 — Release audit and documentation

- **Objective:** run full regressions, audit ownership/prohibited surfaces,
  record final sizes and lifecycle versions, then update identity/docs.
- **Likely files:** version authority/test, README, overview, roadmap, release
  notes after all gates pass.
- **Invariants/tests:** native suite, fixtures, both builds, protocol vectors,
  physical evidence, `git diff --check`, and clean compatibility matrix.
- **Completion gate:** human review approves release candidate with no
  unrecorded deferral or incompatible change.
- **Non-goals:** no v0.7 EVENT work, v0.12 stable service work, v1.1 opaque
  application transport, tag, push, or release without separate authorization.

## 12. Required test matrix

Native coverage must include valid encode/decode; minimum and maximum frames;
every partial-frame split; multiple frames in one span; malformed and oversized
length; bad version; unknown message; invalid operation and capability ID;
wrong type and out-of-range value; authorization and interlock denial;
hardware unavailable and BUSY; request/response correlation; recovery after
malformed input; disconnect/reconnect; bounded backpressure; and saturation of
every diagnostic counter.

Radio bridge tests additionally cover timeout, retry, duplicate request,
duplicate response, late response, mismatched response, Node receive
restoration, host disconnect during transaction, and prevention of repeated
physical action. Tests remain deterministic and do not weaken existing TEST/ACK
or v0.5 capability fixtures.

## 13. Physical validation plan

Later v0.6 qualification uses the two established Heltec V4 boards. It must
validate host connection to Hub and Node where applicable, Host Protocol
negotiation, structured request/response exchange, capability enumeration and
description, input read, authorized indicator SET, denial behavior, radio
traffic while Host Protocol is active, request correlation, timeout result,
disconnect/reconnect, device operation with host absent, and OLED/input/settings
regression. No v0.6 physical result is claimed by this planning document.

## 14. Explicit non-goals

- No generic remote shell or human CLI as Host Protocol.
- No arbitrary GPIO, pin mode, memory, pointer, or function access.
- No remote code execution, uploaded procedures, or dynamic plugins.
- No application-specific ARGUS/BLACKSHEEP/NIGHTWATCH business logic.
- No embedded database, workflow engine, automation platform, or rich host UI.
- No dynamic runtime capability registration or capability persistence.
- No general opaque application payload transport; that remains v1.1.
- No stable Host service/API claim; that remains v0.12.
- No multi-Node orchestration, EVENT delivery, routing, repeater, mesh,
  store-and-forward, disconnected custody, or distributed-security expansion.
- No unrelated hardware feature, actuator, ADC, settings, or UI expansion.
- No v1 feature pull-forward.

## 15. Release gate

v0.6.0 is complete only when:

```text
[ ] The v0.5.x entry qualification was completed successfully before implementation
[ ] Host Protocol has an explicit independent 0.1 version
[ ] Framing and all buffers are bounded and deterministic
[ ] Malformed, partial, concatenated, and oversized input cannot destabilize firmware
[ ] Requests correlate deterministically with structured responses
[ ] ACK, RESPONSE, capability result, radio result, and protocol error remain distinct
[ ] Capability operations reuse v0.5 validation, authorization, and interlocks
[ ] No arbitrary GPIO, memory, function, shell, or runtime registration surface exists
[ ] The Wire Protocol decision is deliberate, documented, and compatibility-tested
[ ] Radio timeout, retry, duplicate, late, mismatch, and receive-restoration tests pass
[ ] Backpressure is bounded and cannot repeat a physical action
[ ] Host disconnect/reconnect does not disable core device behavior
[ ] Host Protocol diagnostics remain separately owned and bounded
[ ] Configuration Schema and Hardware Profile changes are explicit or remain unchanged
[ ] Full native suite and configuration fixtures pass
[ ] Production Hub and Node builds pass with recorded RAM/flash impact
[ ] Physical host-interface and PC-to-Node-to-PC validation passes
[ ] Radio/host coexistence and OLED/input/settings regression pass
[ ] Documentation and all five lifecycle versions are current
```

The next milestone does not begin merely because this plan exists. This brief
is ready for implementation only after its v0.5.x entry gate is recorded as
successfully complete.
