# ARGUS REDLINE v0.2.0-dev Two-Board Regression

Use this procedure for Step 11 of the v0.2.0 implementation brief. It is a desk regression of the current single-Hub/single-Node firmware, not a range test. Do not proceed to final v0.2.0 release preparation unless every required check passes or an explicitly best-effort check is recorded as unavailable.

## Test assumptions

- Hub: Heltec WiFi LoRa 32 V4 built with PlatformIO environment `tx`.
- Node: Heltec WiFi LoRa 32 V4 built with PlatformIO environment `rx`.
- Both boards have appropriate 915 MHz antennas attached before power-up or transmission.
- Both builds use the repository's current LoRa configuration, including `radio.begin(915.0)`.
- Serial monitoring uses 115200 baud.
- COM4 for the Hub and COM5 for the Node are configuration defaults only. Discover and verify the actual ports for this test before flashing.
- The workstation-local PlatformIO executable is `C:\Users\admin\.platformio\penv\Scripts\platformio.exe`.

## 1. Pre-test repository verification

Start in `C:\Users\admin\Documents\heltec-labs`. Fetching updates is read-only with respect to firmware files but updates Git's remote-tracking data.

```powershell
Set-Location 'C:\Users\admin\Documents\heltec-labs'
git fetch origin

$expectedBranch = 'v0.2.0-architecture-foundation'
$expectedCommit = '944f805'
$branch = git branch --show-current
$status = git status --porcelain
$head = git rev-parse HEAD
$upstream = git rev-parse '@{upstream}'
$latest = git log -1 --format='%h %s'

if ($branch -ne $expectedBranch) { throw "Unexpected branch: $branch" }
if ($status) { throw 'Working tree is not clean' }
if ($head -ne $upstream) { throw 'Branch is not synchronized with its upstream' }
if ($latest -ne '944f805 Consolidate firmware hardware orchestration') {
    throw "Unexpected baseline: $latest"
}

$firmwareDefinition = Get-Content 'lib/redline_version/src/redline_version.h' -Raw
$protocolDefinition = Get-Content 'lib/redline_protocol/src/redline_protocol.h' -Raw
if ($firmwareDefinition -notmatch 'FIRMWARE\[\]\s*=\s*"0\.2\.0-dev"') {
    throw 'Firmware identifier is not 0.2.0-dev'
}
if ($protocolDefinition -notmatch 'VERSION\s*=\s*1;') {
    throw 'Wire Protocol version is not 1'
}
```

Record the full value of `$head` in the test record. Stop if any check throws. Do not test a dirty, divergent, or unexpected build.

## 2. Full software validation

Use the MSYS2 compiler path only for this PowerShell session:

```powershell
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
$platformio = 'C:\Users\admin\.platformio\penv\Scripts\platformio.exe'

& $platformio test -e native
if ($LASTEXITCODE -ne 0) { throw 'Native tests failed' }

& $platformio run -e config_hub_valid
if ($LASTEXITCODE -ne 0) { throw 'config_hub_valid failed' }

& $platformio run -e config_node_valid
if ($LASTEXITCODE -ne 0) { throw 'config_node_valid failed' }

$invalidConfigurations = @(
    @('config_missing_local', 'ARGUS_LOCAL_DEVICE_ID must be defined by the build environment'),
    @('config_missing_peer', 'ARGUS_PEER_DEVICE_ID must be defined by the build environment'),
    @('config_equal_ids', 'Local and peer device IDs must be different')
)

foreach ($configuration in $invalidConfigurations) {
    $output = (& $platformio run -e $configuration[0] 2>&1 | Out-String)
    if ($LASTEXITCODE -eq 0) { throw "$($configuration[0]) unexpectedly succeeded" }
    if (-not $output.Contains($configuration[1])) {
        throw "$($configuration[0]) did not emit: $($configuration[1])"
    }
}

& $platformio run -e tx
if ($LASTEXITCODE -ne 0) { throw 'Hub build failed' }

& $platformio run -e rx
if ($LASTEXITCODE -ne 0) { throw 'Node build failed' }
```

Record all results. Stop before flashing if any required validation fails.

## 3. Discover ports and assign boards

1. Disconnect both boards.
2. Run `& $platformio device list` and note the baseline ports.
3. Connect one antenna-equipped board only, run `& $platformio device list` again, and identify its newly appearing port.
4. Physically label that board `Hub`; record its port as `$hubPort`.
5. Disconnect the Hub, connect the second board, repeat discovery, physically label it `Node`, and record its port as `$nodePort`.
6. Connect both boards and confirm both recorded ports appear simultaneously.
7. If a port is ambiguous, use Windows Device Manager or `Get-CimInstance Win32_SerialPort` and repeat the one-board-at-a-time check. Do not infer roles from COM4/COM5 alone.

Set the verified ports for this session, for example:

```powershell
$hubPort = 'COM4' # Replace with the discovered Hub port.
$nodePort = 'COM5' # Replace with the discovered Node port.
if ($hubPort -eq $nodePort) { throw 'Hub and Node ports must differ' }
```

## 4. Flash both boards

Close any serial monitor using either port before uploading.

```powershell
& $platformio run -e tx -t upload --upload-port $hubPort
if ($LASTEXITCODE -ne 0) { throw 'Hub upload failed; stop the regression' }

& $platformio run -e rx -t upload --upload-port $nodePort
if ($LASTEXITCODE -ne 0) { throw 'Node upload failed; stop the regression' }
```

Stop immediately if either upload fails. Do not continue with mismatched or partially updated firmware.

## 6. Normal TEST/ACK regression

Observe at least ten consecutive successful transactions.

For each sampled transaction, correlate the sequence on both monitors and verify:

1. Hub logs a COMMAND transmission with `type=1`, `src=1`, `dst=16`, `opcode=100`, and `payload=0`. These decimal values correspond to Hub `0x01`, Node `0x10`, and `TEST=0x64`.
2. Node logs receipt of the same type, endpoints, sequence, opcode, and payload length.
3. Node reports `COMMAND OK | ACK SEQ <n>` and logs an ACK transmission with `type=2`, `src=16`, `dst=1`, the same sequence and opcode, and `payload=1`.
4. Hub logs receipt of that ACK and reports `ACK MATCHED | SEQ <n> ...` rather than `ACK ERROR`, `ACK IGNORED`, or `ACK MALFORMED`.
5. The next new Hub command advances to the next eight-bit sequence value exactly once.
6. Both monitors print RSSI in dBm and SNR in dB for received packets, using the existing numeric formatting.
7. No board resets, hangs, stops transacting, or reports unexplained radio errors.

The OLED is not a per-transaction phase display in the current firmware. Verify that its implemented startup transition and stable home screen are unchanged: Hub remains legible as `TX | READY`, Node remains legible as `RX | READY`, the logo/title layout is intact, and neither display becomes garbled or unexpectedly changes during transactions. Use Serial output to observe transaction phases.

## 7. Retry, failure, and automatic recovery

Perform this after normal transactions have passed.

1. Record the sequence of a successful transaction and identify the next sequence expected.
2. Immediately after a successful exchange, remove power from the Node. Keep the Hub powered and its monitor open.
3. Observe the next Hub command at sequence `<n>`.
4. Confirm the initial attempt ends with `ACK TIMEOUT | SEQ <n>`.
5. Confirm `retry 1/2`, followed after the configured 500 ms retry delay by one `TX RETRY` using the same sequence `<n>`.
6. Confirm the second timeout reports `retry 2/2`, followed by a second `TX RETRY` using the same sequence `<n>`.
7. Confirm the third timeout produces `COMMAND FAILED | SEQ <n>`. There must be exactly two retransmissions after the initial attempt.
8. Only after terminal failure is visible, restore power to the Node without resetting the Hub.
9. Confirm the Node again reports its correct startup metadata and returns to `NODE READY`/`RX | READY`.
10. Confirm a later Hub transaction succeeds automatically. If the Node is still booting during the first scheduled transaction, allow subsequent scheduled transactions; do not reset the Hub.
11. Confirm the failed transaction's sequence was constant across all attempts and the first later new command uses `<n + 1>` with normal eight-bit wrap semantics.
12. Confirm successful TEST/ACK exchanges continue afterward without resets, hangs, or unexplained radio-state failures.

The expected timing is a 2500 ms ACK timeout, 500 ms before each retry, and 3000 ms from terminal completion to the next transaction. Serial-monitor timestamps may be used for approximate confirmation; the required behavioral checks are the timeout order, exactly two retries, terminal failure, and automatic recovery.

## 8. Duplicate-command regression

Mandatory native coverage already verifies the single-entry, in-memory duplicate key of source + sequence + opcode, remembered-status reuse, and regenerated ACK construction. Record the native test result from section 2.

The standard power-loss procedure above does not test duplicate handling: removing Node power makes the Node unavailable and clears its volatile duplicate state. Do not claim it as a duplicate test.

An exact physical duplicate requires either:

- a naturally lost Node-to-Hub ACK while the Node remains powered and receives the Hub retry; or
- controlled RF equipment or an external packet injector that can preserve the original source, destination, sequence, opcode, and payload.

If a duplicate occurs naturally, directly observable evidence is:

1. Hub retransmits the same command metadata.
2. Node reports `DUPLICATE | ACK SEQ <n>` without restarting.
3. Node regenerates an ACK from remembered transaction metadata/status.
4. Hub accepts the matching ACK.

Selective ACK suppression is best-effort unless a safe, repeatable lab method is already available. Do not disconnect an antenna from a powered transmitter, power-cycle the Node, alter production firmware, or add a production command merely to force this condition. If exact injection is unavailable, record physical duplicate injection as `NOT RUN — no repeatable selective ACK-loss or packet-injection method`; this alone does not fail Step 11 when mandatory native duplicate tests and all other required physical checks pass.

## 11. Stop conditions

Stop the regression and do not proceed to Step 12 if any of these occurs:

- either firmware build or upload fails;
- either board reports incorrect role, firmware identifier, Wire Protocol version, or hardware profile;
- either radio fails initialization;
- a normal TEST/SUCCESS-ACK exchange fails;
- packet endpoints, sequence, opcode, or payload behavior differs;
- the Hub performs a retry count other than exactly two retransmissions after the initial attempt;
- sequence advancement or reuse differs;
- automatic recovery after restoring the Node fails;
- either board resets, crashes, hangs, or enters an unexplained radio state;
- OLED or Serial output has a material regression that prevents correct role, readiness, transaction, or diagnostic interpretation.

Physical duplicate injection being unavailable is not by itself a stop condition when it is recorded as not run, mandatory native duplicate/regenerated-ACK tests pass, and every other required check passes. Any observed duplicate behavior that contradicts the native contract is a stop condition.
