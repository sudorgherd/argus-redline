# ARGUS REDLINE v0.6.0 Architecture Baseline

**Status:** Normative pre-implementation architecture baseline

**Documentation/design:** ACTIVE / PREPARED

**Implementation:** NOT STARTED

**Implementation entry gate:** v0.5.x hardware qualification gate satisfied August 16, 2026

## 1. Published baseline

v0.6.0 design inherits the published v0.5.1 release:

| Authority | Baseline |
|---|---|
| Firmware | `v0.5.1` |
| Wire Protocol | `1` |
| Configuration Schema | `1` |
| Hardware profile | `HELTEC_V4` |
| Native suite | 469/469 passing across 13 test programs |
| Hub production size | 20,428 bytes RAM; 354,193 bytes flash |
| Node production size | 20,484 bytes RAM; 351,829 bytes flash |

These are entry measurements, not v0.6 results or budgets. v0.6 firmware does
not exist merely because this design package exists.

## 2. Inherited capability substrate

v0.6 reuses the v0.5.x immutable bounded capability registry, opaque logical
capability IDs, typed `CapabilityValue`, `OperationResult` and
`OperationStatus`, descriptor operation support, authorization and interlock
gates, role-safe dispatch, capability diagnostics, singular DeviceInput and
LED-arbitration ownership, and fail-closed hardware availability behavior.

No host or radio operation may expose raw GPIO, pin modes, memory, pointers,
handler selection, or dynamic registration. The August 16 temporary GPIO4 ADC
characterization passed, but the ordinary production analog capability remains
`HARDWARE_UNAVAILABLE` pending a separate production-enablement decision.

## 3. Duplicate and admission invariant

The v0.5.1 duplicate cache is fixed-size, single-entry, volatile across reset,
and allocation-free. Its canonical request identity is exactly:

```text
source
+ sequence
+ opcode
+ payload length
+ meaningful payload bytes
```

Complete command admission and validation MUST occur before duplicate-cache
lookup or mutation. Admission includes framing/bounds, protocol version,
packet type, destination, configured sender, opcode, payload length, and all
opcode-specific structure. Malformed, unsupported, ignored, or wrongly
addressed requests MUST NOT consult or poison duplicate state.

v0.6 structured requests inherit this identity and order. If the cache retains
a structured result for replay, that result remains attached to the same one
canonical entry; it does not create an unbounded history or a second identity.

## 4. Transaction assumptions

The Hub owns one active radio transaction, sequence allocation, bounded retry
and timeout policy, matching, receive restoration, and the terminal outcome.
The Node owns receive validation, duplicate suppression, execution at the
approved safe point, response construction, and receive restoration. Host
request IDs correlate the local link only and never replace the Wire sequence.

An ACK is transport acceptance, not operation completion. A structured
RESPONSE is the operation result. Source, destination, sequence, and opcode
must match the active transaction. Late, mismatched, malformed, or duplicate
responses do not complete unrelated work. An ACK carrying an undefined status
is malformed and MUST NOT terminate the Hub transaction; the Hub continues to
wait for a valid transaction message until the normal deadline.

## 6. Security baseline

F-01 is remediated and qualified in v0.5.1. These findings remain open and
deferred:

- **F-02 — Medium:** forgeable radio metadata is treated as peer identity.
- **F-03 — Low:** repeated RF commands can force ACK work.
- **F-04 — Low:** captured ACKs can become valid after sequence reuse.

Wire Protocol 1 has no cryptographic peer identity, authenticated side-effect
authority, or persistent freshness. Source/device IDs are routing identifiers,
not authenticated identities. Duplicate suppression is volatile reliability
behavior, not replay protection. CRCs detect accidental corruption, not an
attacker.

`HOST_LOCAL` means the physical/local host interface and a locally permitted
capability policy; it is not cryptographic user identity. `REMOTE` means the
unauthenticated Wire Protocol 1 radio context at v0.6 entry. Read-only and
non-side-effecting REMOTE operations remain policy-controlled. General remote
`SET_INDICATOR` and `RUN_PROCEDURE` MUST remain denied for production use while
the radio transport is unauthenticated. Normal capability policy MUST NOT
convert unauthenticated REMOTE input into production side-effect authority.

A separately reviewed compile-time laboratory build MAY enable one explicitly
bounded qualification path. That path remains unauthenticated, MUST be
documented as such, and MUST NOT be represented as production authenticated
authority. v0.8 and v0.9 retain identity, authenticated transport, replay
protection, credential lifecycle, and related security ownership.

## 7. Readiness and authority

The v0.5.1 F-01 release qualification is complete. For progression into
v0.6.0 implementation, the project additionally requires completion and
disposition of selected hardware qualification work. The August 16 follow-up
completed GPIO4/ADC1_CH3 electrical characterization, its formal
post-characterization 30/30 radio regression, physical startup-held GPIO0
reproduction on both boards, and the designated endurance/broader fault
qualification. The v0.5.x hardware entry gate is complete. This does not alter
the validity or completed status of the published v0.5.1 release.

The completed gate no longer blocks v0.6.0 implementation from the
hardware-qualification perspective. Implementation remains NOT STARTED and
must proceed through the approved implementation brief and its remaining gates.

Within v0.6 authority:

- developmental Host Protocol 0.1;
- bounded structured device/capability operations and responses;
- an additive Wire Protocol 1 extension under its dedicated design;
- one-outstanding-operation host/radio integration;
- bounded diagnostics and a minimal reference utility; and
- tests and physical qualification of that exact slice after entry.

Outside v0.6 authority:

- authenticated RF identity, encryption, persistent freshness, replay windows,
  credential lifecycle, provisioning, or revocation;
- general unauthenticated remote side-effect authority;
- multiple active Nodes, events, routing, mesh, store-and-forward, or opaque
  application transport;
- a stable host service/API, application workflows, or business semantics;
- arbitrary hardware access, uploaded code, or dynamic procedures; and
- treating hardware-gate closure as evidence that implementation has started.
